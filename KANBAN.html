Developer handoff: exact commit/base, clean worktree, affected tests/pinned lint/format, resolved conflicts и limitations до Code QA. FQA получает один immutable epoch; каждый reviewed commit/image digest собирается один раз для трёх изолированных mutable стендов. Traceability требований остаётся в матрице fqa_lead.

Как движутся задачи и ответственность

  1. Очередь → разработка. root назначает владельца, отдельную ветку/worktree, точные пути и данные/стенд; разработчик принимает задание. C — взаимодействие/агент, D — runtime, E — перенос; F — исправления, G — общий состав, P — паритет, R — выпуск. Цифры — локальные номера карточек; это не номера аудита и не проценты.
  2. Разработка → локальные проверки. Разработчик обновляет свою ветку против интеграционной, сам разрешает конфликты и выполняет affected pinned format/lint и unit/real-PG/race проверки. Перед Code QA передаёт чистый worktree, точные commit/base, scope и gate evidence. root не принимает на себя очистку gates или разрешение конфликтов разработчика.
  3. Локальные проверки → Code QA. Свежий независимый агент получает требования, точный commit/diff и исходники; без авторского отчёта, истории и предыдущих findings. Код во время ревью неизменяемый. FAIL возвращает ответственность автору; существенное исправление получает свежий review.
  4. Code QA → мёрж. root выдаёт один merge slot. Проверенный commit мёржит root или назначенный разработчик; конфликты заранее разрешает разработчик; substantive post-review resolution требует свежего affected review. Не менять reviewed commit во время ревью. Другие разработчики продолжают свои ветки.
  5. Мёрж → интеграция → Functional QA. root проверяет затронутый общий состав, владелец стенда замораживает commit/config/data. Свежий source-blind QA проверяет EN/RU Telegram-like интерфейс. Во время QA стенд не перестраивается; данные независимых tests не конфликтуют.
  6. Functional QA → принято. Оба gates и обязательные checks доказали полный scope карточки/этапа. root обновляет PROGRESS; kanban_manager отражает статус и получателя. При неудаче задаётся конкретный scope исправления, прежний FAIL сохраняется.

Передача считается состоявшейся, когда получатель подтвердил задачу и получил конкретный commit или frozen stand. Если владелец ещё не назначен, root отвечает за очередь. Повторные неудачи или странно разросшееся решение требуют пересмотра и передачи другому разработчику.

Следующее обновление доски: после локального коммита/результата проверки, смены владельца, merge или stage gate. Сверять с реальным Git/отчётом; намерение и старый снимок не заменяют доказательство. Публикация и production отдельно авторизуются.
