# Shuttle: review, QA и план развёртывания — 2026-10-12

Первый исполнительный этап сообщений прошёл локальную ручную приёмку.
Это не приёмка полного бизнес-MVP и не разрешение заменить рабочий бот.
Ветка: `codex/shuttle`, HEAD `b130aa09`; исправления этой проверки и новые
отчёты пока не закоммичены. Проверялся весь собственный код Shuttle,
SQL, конфигурация и deployment. Старый Python-бот и остановленная Go-ветка
в эту проверку не входят и не изменялись.

## Review loop

Основные независимые циклы: обычное ревью — 2 прохода, качество/нейрослоп —
3 прохода, понятность и удобство кода — 2 прохода. Затем выполнено ещё
9 свежих проходов полного diff после QA-исправлений: всего 16 текстовых
ревью. Последний проход не нашёл actionable замечаний. Ревьюверы читали
код и документацию; тесты и ручную QA выполняли отдельно.

Исправлены подтверждённые проблемы:

- Callback ACK теперь ограничен одной секундой и не меняет результат durable
  acceptance. Неподдерживаемый callback получает HTTP 200 с ignored-result;
  ошибка сохранения по-прежнему получает 503.
- Ошибки БД в worker и delivery больше не исчезают за обычным snooze. Диагностика
  ограничена по частоте и содержит класс/SQLSTATE без сырых ошибок и пользовательских
  данных. Потеря singleton lock сообщает причину остановки worker.
- Для прерванных SIGKILL jobs настроен native River rescue на основе lease и
  attempt timeout. Стандартный час ожидания больше не используется. Rescue scan
  и retry scheduling отделены от секундного бюджета graceful shutdown.
- Административные права читаются только из claim проекта Shuttle API. Запрашивается
  правильный plural projects:roles scope. Ошибочный introspection client другого
  проекта не превращает одноимённую роль Loom в права Shuttle.
- Обычное сообщение после гарантированно отклонённого steering сохраняется и
  запускает собственный run после завершения прежнего. Проверены 429 и гонка с 409.
  Предыдущий неизвестный исход запрещает такую promotion.
- HTTP transport не повторяет mutation POST скрытно. Повтор контролирует durable
  worker, сохраняя неизвестный исход и тот же idempotency key.
- Отложенные результаты и prompts проверяют локальный отзыв и IAM-авторизацию
  в пределах TTL перед отправкой. Явный отказ блокирует доставку; временная
  недоступность без действительного кеша откладывает её. Denial-уведомления
  остаются доступны, в том числе после заблокированного вопроса в той же задаче.

Изменения не staged: исходный staged diff был пустым и остался пустым.
Новых commit, push, PR или deployment эта проверка не выполняла.

## Проверки и ручная приёмка

На текущем коде прошли все Go-пакеты и 19 интеграционных поведенческих тестов,
включая отдельные subcases для неизвестного исхода, отказа IAM и отзыва доступа.
Линтер: 0 замечаний. Linux `go test -race` прошёл для всех пакетов Shuttle;
`sqlc compile`, Docker build и `git diff --check` также прошли.
Команды и требования к тестовой БД описаны в [run guide](shuttle-run.md).

При одновременном запуске независимых наборов тестов локальный PostgreSQL
достиг лимита 100 соединений. Причина подтверждена SQLSTATE 53300.
Финальные прогоны выполнены последовательно с `-parallel 4`; это ограничение
тестового стенда, а не замена проверки product behavior.

Ручная QA использовала настоящий Linux-процесс из release image, отдельный
PostgreSQL, ограниченную runtime-роль и управляемые HTTP peers. Она не подменялась
запуском Go-тестов: **67/67 PASS**. Измеренная остановка — **419 мс**, exit 0;
восстановление незавершённой задачи после SIGKILL — **18 962 мс**, один run
с прежним operation key. Эти измерения не обещают такой срок при любой нагрузке.

Образ: `shuttle:review-qa-final`, локальный Docker image ID
`sha256:4c9ddb38e44c0aef98ff8fa868d547c7d8adccd08f0074655812a3ef9149fbc3`.
Это локальный QA image, а не опубликованный registry digest.

Подробные случаи, исходные FAIL, исправления и границы доказательства:
[ручная QA](shuttle-manual-qa-2026-10-12.md).
Отдельная [QA настоящего Zitadel v4.16.3](shuttle-real-iam-qa-2026-10-12.md)
подтвердила provisioning, оба grant, claims, JWT/JWKS/introspection, обновление
и expiry, warm/cold IAM downtime и изоляцию ролей двух проектов.
Она проверяет disposable IAM contract, а не production-политику или Loom.

Принадлежавшие этим проверкам контейнеры и IAM-секреты удалены. Безопасные локальные
evidence и исходные ошибки сохранены в ignored scratch. Другие контейнеры,
реальный Telegram, платные модели и production-данные не изменялись.

## Документация и сервер

Документация прошла 6 отдельных сверок с исходниками; финальная сверка не нашла
actionable замечаний. Уточнены реализованные, будущие и исторические возможности,
grant и role namespace, runtime-настройки, TTL, восстановление и границы QA.
Исторический отчёт первого commit сохраняет первоначальные измерения.

[Пошаговая инструкция для complynx.net](shuttle-server-rollout.md) основана на
read-only проверке сервера 2026-10-12. Она описывает подготовку Loom/IAM,
отдельные PostgreSQL database/roles, каталоги и секреты, Compose, Traefik,
тестовый webhook, Alloy/OTel, pilot, обновление, backup и rollback.
Её Compose-блок проверен с фиктивными env без запуска сервисов.
На сервере ничего не менялось.

## Открытые этапы

До production остаются настоящий Loom round trip и его IAM-outage continuity,
двустороннее provisioning/linking с zitadeltg, реальные Telegram/collector проверки
и согласование production IAM policy. Принятый локальный этап их не закрывает.

Ещё не реализованы HTML/Telegram WebApp auth pages, persistent Loom conversation
context, file ID/read API, выбор языка пользователем, регистрации, пассы/пары,
частичные платежи и подтверждения
амбассадором, аватарки, event time zones и включение модулей, миграция данных/истории,
бизнес- и административные agent manifests, operator reconciliation API и полный
набор dashboard/alert. Массаж и питание остаются следующими бизнес-этапами.
