## Findings

### Confirmed defects

### F1 (Low, coverage): several changed lines have no test that reaches them
If any of the following sanitizing calls were reverted, no test in this file would fail:
- **`ownership.go:23-24` and all of `tool_capabilities.go:26,35,39,52,54`.** Both `OwnsEventBookings` and `ToolCapabilities` call `requireActor` first (`catalog.go:117-122`). With a pool that always fails, that call fails before any changed line runs, and the new test calls neither method with a failing pool anyway.
- **`payment_history.go:74,78,89` and `payment_queue.go:58,83`**: the query, row-collect and commit paths after the first statement.
- **`takeover_read.go:47,66,70,81,84`**: every site after `Begin`.

The cause is that `Service.DB` is the concrete `*pgxpool.Pool`, so these paths can't be faked. The fix is a real-PostgreSQL integration test, as `AGENTS.md` expects, that forces a failure mid-transaction. For example, terminate the backend with `pg_terminate_backend`, or cancel after the first statement. Existing integration tests elsewhere may already cover this; I didn't check them because they are outside the scope I was given.

### Unresolved hypotheses (not caused by this change; noted for triage)
- **H1: unmapped missing rows in `TakeoverTarget`.** `readContacts` (`takeover_read.go:96-98`) and the receiving-admin query (`takeover_read.go:58-67`) pass `pgx.ErrNoRows` through with no domain mapping. That could happen if a legacy `receiving_admin` value has no matching `core.users` row, but I didn't verify whether a foreign key exists. The caller would then get a plain `ErrNoRows` rather than a problem response. This behaviour pre-dates the change and matches the "preserve NoRows" requirement, so it isn't a regression. It depends on the schema and the HTTP handler, neither of which I reviewed.
- **H2: actor absence in `LockReadAuthorities`.** When the actor doesn't exist, `read_authority.go:24-27` returns a raw `ErrNoRows` instead of `forbidden()`. The test pins this as the existing contract (test line 495), so it's intentional preservation; it's noted only for product awareness.
- **H3: `TestReadDatabaseTierStreamAndBounds` depends on how many single-row queries `authorize(..., commandAdminCancel, ...)` makes.** It gives three successful results followed by the count result. I couldn't find `authorizeBatchCancel` to confirm the count. If it's wrong, the "limit" subtest should fail loudly rather than pass silently, so the risk is brittleness, not false confidence.
