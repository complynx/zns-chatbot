## P1: Retain trusted token associations during exchange refresh

Location: `platform/internal/identity/zitadel.go:204` and `platform/internal/identity/exchange_cache.go:165`.

`subjectsForValue` searches completed `values` only. `resolve` deletes an expired exchange entry at `exchange_cache.go:49` before starting its replacement flight. That loses the trusted token-to-subject association while the refresh is pending. A definitive rejection of that token can therefore fail to invalidate the pending exchange, and its late success is cached at `exchange_cache.go:134`.

Source-derived reproduction:

1. Exchange Alice successfully, obtaining token T. Do not introspect T yet.
2. Let that exchange cache entry expire (or advance its stored deadline in a focused internal test).
3. Start another Exchange(Alice), and hold its successful provider response containing T behind a barrier. The expired value is now deleted and the replacement flight is pending.
4. Verify(T), with the provider returning `active:false`. `previousSubject` is empty, and `subjectsForValue(T)` finds no completed entry. Neither cache invalidation nor the flight retirement flag is applied for Alice.
5. Release the pending exchange response. The flight remains valid and caches T successfully. During an ensuing outage, Exchange(Alice) returns that definitively rejected token from the cache.

Preserve a bounded trusted association through refresh (or use equivalent denial/flight coordination) so this rejection can retire the relevant pending exchange without relying on rejected claims. Add a focused barrier test for the ordering above. Existing added tests exercise denial against a completed exchange entry or exchange inactivity against pending verification; they do not cover this ordering.
