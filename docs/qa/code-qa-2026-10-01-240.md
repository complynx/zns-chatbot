## Findings

### P1 — delayed retirement can overwrite a newer authorized card on the same Telegram message

Location: `platform/internal/botdelivery/pass_receipt_retirement.go:125-154`, particularly the parent validation at lines 141-147.

`lockPassReceiptRedaction` verifies the cleanup intent and its original parent, but does not verify that the target still contains that parent's payload. A later successful pass-card receipt for the same bot/owner/chat/message does not invalidate the cleanup. The redaction renderer then edits that exact message unconditionally.

Concrete permitted sequence: an original derived card is successfully edited onto existing message M and its receipt continuation is delayed. A newer manual `/passes` update replaces the view with a source-free state and queues an edit to M. Menu storage preserves message_id (`pass_menu.go:56-57`), so this uses the same real target. The manual card cannot begin while the original sent receipt has an unfinished continuation (`admission.go:221-230`). Revoke the original source and continue its receipt. The old view no longer matches, so retirement preserves the manual view, but it appends a cleanup to the shared lane and finishes the original continuation. The already queued manual card has an earlier lane sequence (`delivery/queries/queue.sql:28-31,47-56`), successfully edits M and completes. Cleanup then passes the original-parent check and replaces the authorized manual card with the unavailable notice and no buttons.

This violates the explicit preservation requirement for independently authorized manual/home cards. It also leaves the current view/hash describing the manual card while Telegram displays the cleanup notice. Existing tests preserve a different replacement message, or independently authorize the prior card before cleanup enqueue; they do not cover a successful newer payload on the same target before cleanup admission.

Fix at the immutable payload boundary: retirement admission must detect a newer successful payload for the same exact target, independently assess that payload's authority, and avoid retiring it when authorized. Keep queue and intent locks in canonical order. Add a PostgreSQL/transport regression that queues the manual edit before original continuation recovery, then delivers both in actual lane order.

### P2 — predecessor successful pass receipts block upgraded source-bound refreshes

Location: `platform/internal/botdelivery/pass_receipt_retirement.go:207-210,289-296`.

`previousPassReceipt` treats an existing successful receipt without `Receipt.Pass` as `ErrBinding`. Every successful pass card produced by the supplied base has exactly that format: base `pass_menu_render.go:175` records Kind/Revision/ViewHash/Tokens, and base Continuation has no Pass field. Migration090 adds only an index and deliberately preserves those old receipts.

After upgrade, a source-bound pass card that targets one of these existing messages invokes `previousPassReceipt` before admission (`admission.go:191-194`). It fails with ErrBinding even when the old and new cards are fully authorized. The worker treats this as terminal and cancels the legitimate refresh. In the source-revoked preparation path, the same rejection prevents saved-target cleanup. This is a normal predecessor state, not corrupt or forged receipt data.

The 087/088 upgrade fixtures preserve old receipt bytes but never exercise delivery/admission against a genuine old pass_card receipt. Add an explicit compatibility policy for the older successful receipt format, without inventing capability evidence from a changed mutable view, and prove authorized refresh plus denied-source cleanup from that predecessor state.
