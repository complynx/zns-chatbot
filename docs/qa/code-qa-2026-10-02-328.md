## Finding

**[P2] Fence confirmed negative replays independently of the mutable scheduling reason.**

Primary location: `platform/internal/orders/notification_delivery.go:169-186`. The same logic appears at `platform/internal/legacyfood/notification_delivery.go:211-228`, `platform/internal/massage/notification_delivery.go:223-240` and `platform/internal/passbooking/notification_delivery.go:254-271`.

Requirement: repeated canonical negative receipts must be inert; owner, queue, pacing, deadline and followers must remain unchanged. A typed conflict is acceptable.

The confirmed-generation marker participates only in an equality shortcut. That shortcut also requires `row.Failure == result.Outcome.Reason`. The handler otherwise permits another pending/deferred completion for the same generation, even after `last_confirmed_attempt` already identifies it. A supported non-wire deferral can therefore replace the scheduling reason without clearing the provider-confirmation marker. Replaying the original canonical negative then bypasses the shortcut and calls `finishNotification` again.

Source-proven sequence, with no additional Begin or provider send:

1. Admit generation G and recover its unresolved wire, leaving pending state, `last_uncertain_attempt=G` and no lease. Record the actual late canonical 429 as `{kind:"pending",reason:"telegram_rate_limit",retry_after:60}`. `notificationConfirmedOutcome` recognizes the recovered generation; the save sets `last_confirmed_attempt=G`.
2. Submit a same-generation supported preflight deferral `{kind:"pending",reason:"notification_preflight_unavailable",retry_after_missing:true}`. It passes Outcome validation, fails the equality shortcut because its reason differs, and is allowed by `notificationOutcomeAllowed` at `orders/notification_delivery.go:242-253`. It replaces `failure` while retaining `last_confirmed_attempt=G`.
3. Replay the exact original 429 for G. The marker still matches, but the failure string no longer does. This request is accepted and reaches `delivery.Finish` through `orders/notification_delivery.go:186,277-284`. `delivery.Schedule` computes the cooldown from the new database clock and extends both bot and chat pacing again (`platform/internal/delivery/pacing.go:89-117`; `platform/internal/delivery/policy.go:16-28`). It also changes the owner reason/deadline and queue projection. Shared pacing can delay unrelated followers despite no new send.

Supporting storage evidence: `platform/internal/orders/queries/notification_delivery.sql:43-54` overwrites the reason on accepted pending completions, retains an existing confirmation when `confirmed=false`, and has no confirmed-generation exclusion. Generated SQL agrees. The adapter itself uses `notification_preflight_unavailable` for preflight failures (`platform/internal/bot/notifications.go:108-115`); this is a supported outcome, not malformed input.

The existing replay cases cover unchanged `telegram_rate_limit` reasons and final exhaustion observation, where the code deliberately retains that reason. They do not exercise an intervening accepted non-wire scheduling outcome (`platform/integration/notification_uncertain_retry_test.go:824-930,1034-1049`). Fence an already confirmed negative generation before rescheduling, or reject stale non-wire completions after provider confirmation. Preserve legitimate cancellation and terminal receipt metadata behavior. Add a focused same-generation sequence that asserts full owner, queue, pacing and follower snapshots are unchanged on replay.

This sequence was traced from source; it was not executed. The exact API inputs and unconditional branch/storage behavior establish the source finding. Runtime reproduction remains required for the fix gate.
