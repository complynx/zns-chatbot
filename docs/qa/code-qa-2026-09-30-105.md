## Confirmed facts (positive)
1. **Restarts now keep the configured services.** The old code built a new `bot.Bot{DB, API, Host, TG, Model}` and dropped `Delivery`, `Logger`, `Observer`, the limits and so on. The new code copies the whole bot (`restarted := *f.b`) and swaps only `Model` (knowledge_authorization_test.go:345-356 and 389-394; saved_knowledge_attachment_recovery_test.go:108-110). Copying is safe: the `Bot` struct (bot.go:35-55) and `appclient.Host` (host.go:12-21) hold only values, pointers and functions, with no locks or in-memory state. The `UserToken` closure (platform_test.go:287-289) reads `result.b` at call time, so it follows the new bot.
2. **The copy keeps the fault-injecting transport on purpose.** `f.b.Host.HTTP` is set at line 79, before the copy, so the attachment counter keeps counting across the restart (lines 129 and 133).
3. **Recovered feedback now goes through real delivery.** `pumpBotDeliveries` (bot_delivery_fixture_test.go:25-64) calls the real `DeliverBotIntent` and stops early if an intent is neither Succeeded nor Cancelled. So if the reply was never delivered, `assertSavedKnowledgeDelivered` fails (saved_knowledge…:135-136, 173-179). It also checks there is exactly one durable `knowledge_reply` row with the catalog text (lines 167-172). This matches the recovery path: `savedKnowledgeReceipt`, then `FinalizeCommand`, then `knowledgeReceiptNotice` returning the `KnowledgeSaved` text (saved_plan_recovery.go:158-175; knowledge_receipt_notice.go:27-42).
4. **The revocation check is now meaningful.** `assertProviderRevocation` now calls `drainPassNotices` after `Render` and before `assertKnowledgeAnswerAbsent` (knowledge_authorization_test.go:399-401). Before, nothing had been delivered at that point, so checking that the answer was absent proved nothing.
5. **Replay adds no attachment or domain effect.** Attachments stay at 3 (line 146), domain effects stay at 1 (line 151), no replanning or assessment happens (lines 152-153), and there is one `knowledge_operations` row (lines 154-159).
6. **Hygiene is clean.** No `nolint`, `noqa` or exclusions were added. The only import changes are removing `bot`, which is now unused, and adding `strings` and `i18n`, both used. Complexity is modest.

## Findings
**F1 (Medium): the replay check can't catch a duplicate message.** saved_knowledge_attachment_recovery_test.go:145-149.
- After the replay `Handle`, the test pumps deliveries again and calls `assertSavedKnowledgeDelivered`. That helper only checks that *some* Bob message contains the notice (lines 173-179). The message delivered at line 135 already satisfies it.
- The row count at line 171 covers `bot.interactions`, not delivery intents or Telegram messages.
- So a replay that queues and sends a second message, card or notice would still pass. That breaks the requirement that a completed replay sends no additional effect.
- **Fix:** before the replay, save `chatMessages` (and ideally the number of delivery intents for this update). After the replay and pump, assert both are unchanged.

**F2 (Low): the same gap exists in `recoverKnowledgeOutage`.** knowledge_authorization_test.go:359-369. The second `handlePassVisible` only rechecks `calls == 1`, the quota keys and that the answer text appears. Nothing checks that no duplicate message was delivered.

**F3 (Low): the revocation scenarios don't check what the user sees.** saved_knowledge…:112-121.
- For `source_revoked` and `history_deleted`, the test checks there are no links and, via SQL, that the deleted original was not restored.
- It never pumps deliveries or checks that Bob's chat lacks "Remember this original request" or "Synthetic recovered knowledge".
- The successful path also doesn't check that the delivered card leaves out the stored knowledge body, which the rule at knowledge_receipt_notice.go:10 requires.
- **Fix:** add `NotContains` checks after a pump.

**F4 (Low, not introduced by these diffs): a vague error check.** Line 123 uses `require.Error` for Curate with `permission_revoked`, so any error passes, including infrastructure failures. It could assert the specific permission error.
