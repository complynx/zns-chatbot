**Code QA review request81 (AUD23)**: **not clean.** The main change is correct: in all four notification helpers, a known SQL failure now returns early, before anything is completed or deferred. Two things block acceptance: an unrelated refund-notification feature is included in the diff, and the post-send follow-up path still does not meet AUD23.

**What I read:** `AGENTS.md`, the scoped diff (with both full test files), current source for the 5 in-scope product files, `core/database_error.go`, `appclient/client.go`, `appclient/host.go`, `bot/bot.go`, `bot/orders.go`, `bot/order_refund_cards.go`, `orders/notifications.go`, and the first 60 lines of `bot/massage.go`.

### What is correct
- **Early return in the four defer helpers:** `deferOrderNotification` (`notifications.go` L57-60), `deferPassNotification` (`pass_notifications.go` L32-35), `deferMassageNotification` (`massage_notifications.go` L51-54) and `deferFoodNotification` (`legacy_food_notifications.go` L32-35). On a known SQL failure each returns before any `Complete*`/`Complete*Followup` host call.
  - SQL is only identified through `core.IsDatabaseFailure` (`database_error.go` L58-73): the `ErrDatabase` sentinel, a real PostgreSQL error, or a PostgreSQL connection error. HTTP errors only count when the server sets the database-failure header on a response with status ≥ 400 and a valid problem code (`client.go` L153-154).
  - Other provider failures, JSON errors, i18n errors and cancellation behave as before.
  - An access denial (403/404/410 problem) without that header still ends as `Cancelled`.
- **Unknown-send and replay are unaffected.** Every call to a defer helper happens before `Begin*Notification`, and the handling of the send gate and send result is unchanged.
- **Transactions:** none are added or changed in the bot paths.
- **`order_refunds.go`:** it has no hunk in the supplied diff, although it is in the frozen scope. I reviewed current source instead. L47-49 checks for a SQL failure before converting a problem into a domain message (L50-51), so a SQL failure marked on a 403 response is passed up rather than shown as `OrderRejected`. The refund test covers the 503+header, 403+header and plain 403 cases, and checks that no preference read (message rendering) happens.
- **`reconcileMassageViews`** (`massage_notifications.go` L189-223): now cleans up the errors from its own SQL query and row collection with `DatabaseOperationError` (cancellation still passes through). It uses the same `reconcileDatabaseFailure` pattern as `reconcileViews` in `bot.go` (L716-731).
- **Suppressions:** none added.

### Findings

**F1 — Medium: unrelated feature in the scoped diff.** `notifications.go` L137-145 adds a new `case "refund_request"` to `notificationText`.
- This is a change in what the user sees, not SQL propagation. Before, `refund_request` fell to the default `OrderNoticeUpdated` text. Now it shows `RefundNotice` + `refundText(...)` (`order_refund_cards.go` L82-104), which includes the task owner ID.
- If `Refund` is nil, the new code returns a generic error. That error goes to `deferOrderNotification` → `Deferred` with `Missing: true`. So a refund notice without a task is deferred indefinitely instead of getting the old default text.
- No test in scope covers it. I could not check that the `i18n.RefundNotice` catalog entry exists in en and ru, because I couldn't find the i18n catalog file.
- It should be removed from this change or reviewed as its own feature.

**F2 — Medium: the post-send follow-up path still records a deferral on SQL failure and returns raw driver errors.** In each file, the follow-up step runs a direct SQL query. On error, it still calls `notificationFollowupResult(err)`, which gives `Done=false, "notification_followup_unavailable"`, then calls `Complete*Followup`, then returns `errors.Join(err, completeErr)`:
- `notifications.go` L110-129, using `StoreOrderNotificationReceipt`
- `pass_notifications.go` L89-98 (and L135-136)
- `massage_notifications.go` L113-120 (and L161-172)
- `legacy_food_notifications.go` L99-115

Two consequences:
- **(a)** A known SQL failure still writes a deferral record. AUD23 says it should propagate *without* completing or deferring notification records.
- **(b)** `dbgen` returns driver errors unsanitized. Unlike `b.record` (`bot.go` L85-86), these calls don't use `DatabaseOperationError`, so PostgreSQL diagnostics go up the per-notice error chain. How far they leak depends on the excluded Deliver loop and the fatal handler (see Limits).

This is inside the scoped files, but there is some scope ambiguity: if "broader Deliver loops" was meant to exclude per-notice follow-up, this becomes a hypothesis-level gap. Whether a SQL-origin `Done=false` record is actually harmful is also a hypothesis: the follow-up stays retryable either way.

**F3 — Low: test gaps.** `notification_defer_database_internal_test.go` only passes the bare `core.ErrDatabase` sentinel and `io.EOF`. Missing:
- **The riskiest case:** a SQL-marked 403/404 problem (`core.DatabaseFailure(&ProblemError{Status:403})`). Before this change that became a permanent `Cancelled` (lost delivery).
- **An unmarked 403 still giving `Cancelled`** (access-denial behavior unchanged).
- **Endpoint and payload checks:** the test counts any request, not which completion endpoint was hit or what it carried.
- **Other changed paths:** nothing covers the `reconcileMassageViews` change or F1.

**F4 — Info.** The notification test builds `Host{Base}` with a zero-value `Signer`. That the `io.EOF` case reaches the fake server and returns no error assumes host request signing works with a zero signer. I did not verify this and did not run any tests.

### Limits
- **Not found:** `reconcileDatabaseFailure`, `startBotDelivery`/`finishBotDelivery`, `b.foodMarkup` and the i18n catalog. I tried these paths under `platform/internal/`, and none exist: `bot/{refunds,reconcile,views,database_failure,reconcile_views,errors,delivery,reconcile_all,bot_delivery,food,legacy_food,refund_views,order_refund_views}.go` and `i18n/ids.go`. Reading directories isn't supported. So I can't confirm how the fatal handler cleans up or classifies these errors, or whether `foodMarkup` returns unsanitized SQL errors into `deferFoodNotification`. If it did, the helper would now return them raw, where before they were absorbed — a hypothesis.
- **legacyfood and massage packages:** I relied only on the bot-side use of their types (`Notification`/`Notice` with `FollowupPending`, `ID`, `DeliveryAttempt`, and the completion/follow-up structs). Those packages are being edited separately, so I make no claim about their implementations.
- **Excluded:** the Deliver loops and `acknowledge` callers.
- I ran nothing: no tests, build, lint or runtime checks, and I make no claims about the whole repo.

**Verdict:** changes requested. Remove or separately review F1. Resolve F2, or explicitly confirm that the per-notice follow-up path is out of AUD23 scope. Adding the F3 tests is recommended. The defer-helper and refund-command changes meet the requirements.
