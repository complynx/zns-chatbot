**What the code gets right**
- **Event isolation** (`deadlines.go:41-52`): each event runs in its own transaction with a deferred rollback (lines 92-96). A failed event is counted and added to `failures`, and the loop moves on to the next event. Keyset paging (line 58) is unchanged.
- **Database origin is kept after an earlier domain error** (line 51): `errors.Join` keeps every failure, so `errors.Is(err, core.ErrDatabase)` still works after a domain error like `pass_tiers_invalid`. `errors.As` for `*core.ProblemError` also still works.
- **Database origin is kept at cancellation** (line 48): the event's own error is now joined with `ctx.Err()` instead of being dropped, so both `context.Canceled` and `ErrDatabase` can be detected. Earlier failures are also kept.
- **Sanitising**: every newly wrapped call (`deadlines.go` lines 82, 85, 94, 111, 114, 148, 155, 159, 190, 210) goes through `core.DatabaseOperationError`. That function maps any error to a fixed set of sentinels (`ErrDatabase`, `ErrDatabaseSerialization`, `context.Canceled`/`DeadlineExceeded`, or no-rows), so driver text cannot get through. The other paths the loop reaches (`readEvent`, `readBookings`, `persist`, `persistAdmissions`, `enqueuePassNotice`) also sanitise. The combined error text is limited to problem codes, fixed sentinel text and the static "persist pass booking" prefix.
- **Cancellation**: `ctx.Err()` is always joined when the context is done, so `errors.Is(err, context.Canceled)` still holds. `DatabaseOperationError` still returns bare `context.Canceled` or `DeadlineExceeded`, so a cancelled query is not mislabelled as a database fault.
- **Retry**: `ErrDatabaseSerialization` still wraps `ErrDatabase` and passes through unchanged.
- **Dependencies**: only the internal `core` package was added. There are no suppressions, lint exclusions or new third-party imports.

**Findings**

| # | Severity | Location | Finding |
|---|---|---|---|
| F1 | Medium (not confirmed) | `deadlines.go:48` with `core/database_error.go:58-63` | The project's own check `core.IsDatabaseFailure` returns **false** for any error that also contains `context.Canceled`, because it tests for cancellation first (line 59). So the cancellation-path error passes `errors.Is(err, ErrDatabase)` but fails `IsDatabaseFailure`. If the maintenance runner, logging or metrics use `IsDatabaseFailure`, the database origin is lost exactly in the "concurrent cancellation" case the requirement names. I could not find the code that calls `ProcessDeadlines`, so I can't say whether this matters in practice. The new test checks only `errors.Is`. Similarly, if a caller retries the whole run when it sees `ErrDatabaseSerialization`, one event's serialization conflict now marks the whole combined error, even when other events failed for domain reasons. The old first-error-only code behaved differently. Please check the callers. |
| F2 | Low | `deadlines.go:51` | `failures` grows by one nested join per failed event. With N failures, `Error()` copies about N² bytes, and `errors.Is` recurses N levels deep. The message also repeats `database unavailable` once per event, with nothing identifying the event. It stays private, but a database outage across many events means large log lines. Suggestion: collect failures in a slice and call `errors.Join(slice...)` once, or keep only one example of each error class plus the count. |
| F3 | Low | `deadlines.go:39` vs `:61` | If `maintenanceEvents` fails after some events have already failed, the error is returned without the `pass maintenance failed for %d events` wrapper. Origin is kept, but the message format is inconsistent. This was also true before the change. |

**Test strengths**
- The event IDs sort so the domain failure (`bad-domain`) is processed before the SQL failure (`bad-sql`), which is the order the requirement is about.
- The trigger produces a real PostgreSQL error through the production `persist` path.
- The sequence proves the trigger actually fired, because `nextval` survives a rollback.
- The test checks that the private trigger text is absent and that the healthy `dance` event still committed.
- The fixture creates a separate database per test (the parallel tests each insert `dance`), so the trigger and sequence do not leak into other tests.
