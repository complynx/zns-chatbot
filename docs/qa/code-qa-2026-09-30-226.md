## Finding

[P2] `final/platform/internal/agenthost/knowledge_context.go:137-138`: selecting a concrete ConnectError does not isolate one connection failure. pgconn ConnectConfig itself builds a ConnectError around `errors.Join(allErrors...)` (pgx v5.11.0 pgconn/pgconn.go:150-164). A concrete ConnectError can therefore contain both a positive dial failure and matching caller cancellation. Passing that whole wrapper to DatabaseOperationContextError still lets its cancellation branch (platform/internal/core/database_error.go:59-60) discard the positive failure.

Concrete static reproduction: make the test's injected DialFunc return `errors.Join(io.EOF, context.Canceled)`; pgconn wraps this as a ConnectError (possibly also through perDialConnectError). Give SanitizeKnowledgeReads an already canceled caller and `errors.Join(denial, connection)`. IsDatabaseFailure returns false because cancellation is present; the typed connection branch passes the wrapper unchanged; DatabaseOperationContextError finds matching cancellation and returns context.Canceled rather than ErrDatabase. The same condition can occur when pgconn aggregates multiple host/dial attempts. Joining a cancellation-owned ConnectError before a separate EOF-owned ConnectError also selects only the first wrapper. Expected by scope: positive connection failures win even when joined with cancellation.

Fix: inspect joined connection causes for positive non-cancellation failures before allowing matching caller cancellation, preserving public sentinel sanitization. Add focused coverage for a mixed-cause concrete ConnectError and both orders of two ConnectError siblings. Keep pure matching caller cancellation nonfatal.
