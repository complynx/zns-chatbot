## Findings

### P1 — successful send receipt retires the previous target, leaving the newly sent private card visible

Candidate locations: `platform/internal/botdelivery/receipts.go:58-80`, `platform/internal/bot/delivery_worker.go:229-238`, `platform/internal/bot/pass_menu_redaction.go:82-96`.

When an edit is refused, `sendBotIntent` changes the intent to a send on its next attempt. That send can succeed, with revocation detected when the actual successful receipt is applied. `ApplyReceipt` returns `pass_source_stale` before projecting the successful message ID. `retireStalePassCard` then tombstones the saved view and `renderRedactedPassMenu` selects `bot.pass_views.message_id`, which still identifies the previous card. The successful receipt's `observed.MessageID` is never used for cleanup. The new private card remains in Telegram. If the previous target was deleted, the queued cleanup is rejected as an edit-only missing-target effect; the receipt can nevertheless complete because the new query only requires a matching cleanup intent to exist. The initial-send case has the same problem with saved `message_id=0`: no cleanup is queued and the sent receipt remains pending.

Preserve transport success, but durably bind retirement to every actual successful private message covered by that receipt, including a new send target. Do not acknowledge its continuation on the strength of a cleanup for another target. Add a receipt-boundary revocation test after a successful fallback send, and an initial-send receipt case. Existing new receipt tests only revoke after `editMessageText` and therefore cannot prove this path.

### P2 — generic stale receipt becomes a revocation and can retire an authorized menu

Candidate location: `platform/internal/botdelivery/receipts.go:58-75`.

`sourceDenied` includes every `ErrStale`, including a harmless view-binding race. For example, `prepareFamily` reads menu A; a concurrent render stores menu B at the same revision with the same valid derivation; `lockViewBinding` then observes B and returns `ErrStale` because it differs from A. The added receipt query still finds the exact revision/source and returns `pass_source_stale`. The worker treats that specific code as revocation and skips the source-validity check in `retireStalePassCard`, so it redacts the valid view, removes callbacks and queues a retirement edit. This differs from the preparation path, which rechecks the immutable source before acting on generic stale.

Retain the distinction between source/capability denial and obsolete binding at the receipt boundary. Revalidate the original source and current capability when needed instead of synthesizing `pass_source_stale` solely because an exact view exists. Add a successful-receipt case with a same-revision, same-source view update while its family binding is checked; the authorized menu must remain visible.
