## Findings

1. **P1 — Bind refund cards to current refund authority at wire admission.** `platform/internal/bot/order_refund_cards.go:62-64` queues each refund through `deliverOrderCard` without a task/version/authority reference. `bot/delivery_cards.go:143-149` assigns generic family `orders`; `botdelivery/family_authority.go:102-103` accepts that family with no domain authority check. `DeliverBotIntent` renders before calling Begin, and Begin checks only that generic reference. Thus an ambassador can be reassigned, lose their pass-admin role, or cease to be the authorized reader after rendering and before Begin; the stale refund amount, customer identity and confirmation button are still admitted to their Telegram chat. Confirmation itself rechecks authorization, but disclosure has already occurred. Carry the exact refund task/version and current-read authority into the card reference and recheck it transactionally at Begin, preserving an authorized tombstone path. Add a deterministic render-to-admission revocation test for this card.

2. **P1 — Preserve sent/uncertain request evidence across temporary routing loss.** `platform/internal/orders/refund_routing.go:76-85,95-104` only protects the currently linked notification. Trace: route pending task to ambassador A; finish its request as sent; temporarily revoke A's role (or make the booking unavailable); next route saves ambassador NULL and notification_id NULL; restore A; next route enqueues a fresh notification for the same obligation and same A. The original sent delivery remains in the database but is never consulted. The same loss of evidence occurs for an uncertain request; changing chat or assignment also bypasses the delivery-state guard before it is read. This violates the supplied no-resend-sent/uncertain requirement and can repeat a manual money-refund request. Retain delivery evidence per obligation and recipient across route changes; create replacement requests only when the relevant previous request is known unsent. Test sent and uncertain -> unavailable -> same ambassador restored, including a service restart, while retaining recovery for cancelled/failed known-unsent requests.
