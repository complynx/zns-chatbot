## Findings

1. **P1 — Known SQL failures still escape the runtime's safe/fatal boundary.** `platform/internal/bot/credit_cutover_diagnostics.go:53-55` returns the raw `QueryRow(...).Scan` error. `Bot.Run` returns it directly during initial validation (`bot.go:589`), and `creditCutoverRunResult` (`credit_cutover_diagnostics.go:61-69`) does not sanitize it. A PostgreSQL error containing private diagnostics therefore escapes as the runtime result instead of `core.ErrDatabase`. During later polling, a generic SQL transport error such as `io.EOF` follows `poll -> handlePollError` and is treated as an ordinary retry because `core.IsDatabaseFailure` intentionally does not classify generic transport errors. Cancellation can additionally discard this unmarked SQL failure in `creditCutoverRunResult`. Normalize at the known SQL call in `validateCreditCutover`; cover startup and polling with concrete SQL and generic transport faults, including cancellation after failure. Related source dependencies `startTelegramPolling` (`telegram_menu.go:64-77`) and reconciliation SQL reads (`bot.go:688-710`, for example) also return raw SQL errors through the same Run boundary; complete normalization at those known SQL operations without classifying mixed provider results as SQL.

2. **P2 — Dispatch keeps starting work after detecting fatal database failure.** `platform/internal/bot/delivery_dispatch.go:51-55` replaces a SQL failure with `ErrDatabase` but appends it and resumes selection; only after the pass finishes can `startBotDelivery` cancel the runtime. With a row-specific SQL fault and another healthy delivery head, the healthy send still executes, and up to 99 further delivery attempts/provider waits may delay the required restart. The receipt batch similarly continues after SQL failures at `delivery_worker.go:166-171`. Return the accumulated failure immediately once positive SQL provenance is detected, preserving ordinary provider failures as nonfatal and leaving unattempted durable work for recovery. Add a three-head control with provider failure, SQL failure, then a healthy head; assert the third is not dispatched. The added dispatcher test cancels its own context at the SQL fault, so it does not detect this behavior.
