## Finding

**P1 — Receipt-application transport failures can still bypass fatal shutdown.** `platform/internal/bot/delivery_worker.go:186-203` relies on SQL provenance from `ApplyBotDeliveryReceipt` before deciding whether to stop or schedule a retry. Its application dependency returns unmarked SQL errors at `platform/internal/botdelivery/receipts.go:32-34`, `45-46`, `72-75` (also direct projection SQL). A connection failure such as EOF or a closed-connection error at the advisory-lock statement is returned raw. `platform/internal/appclient/bot_delivery.go:101-103` then passes it through `orderApplicationError`; `platform/internal/appclient/local_orders.go:49-53` maps generic transport errors to an ordinary `internal_error`, because `core.IsDatabaseFailure` deliberately does not infer SQL origin from transport errors. If the retry-scheduling query succeeds on another pool connection, `continueBotIntent` returns only the ordinary application error, the receipt batch continues, and Run remains alive after a known SQL failure. This violates AUD23 even though the sent receipt itself remains durable.

Normalize errors at the actual receipt SQL boundaries, preserving domain outcomes and cancellation, before the application boundary erases origin. Add a focused receipt-application transport injection test through `Host.LocalBotDelivery` (for example, close the SQL connection immediately before the advisory-lock query for a sent identity intent), and prove the batch stops before another receipt or delivery. This is a dependency gap exposed by the assigned worker slice, not a claim that the unwrapped statements were introduced by this diff. The existing receipt transport test exercises `finishBotIntent`, not `Service.ApplyReceipt`; the continuation test supplies an already marked ErrDatabase, so neither covers this chain.

## Other reviewed evidence

- Run defers delivery stop/join after lock cleanup is registered, so LIFO cleanup joins delivery before advisory unlock and pool release. Fatal delivery results are read after joining, retaining late bounded completion failures.
- Polling classifies SQL failure before examining context cancellation. Inbox insert/cursor updates and acknowledgement/delete remain transactional.
- Dispatch stops after a classified SQL error; ordinary provider failures retain subsequent-head progress. The runtime converts classified failures to the closed database sentinel.
- Known send results are persisted with a bounded cancellation-independent context carrying the live principal. Recovery preserves uncertain attempts instead of blindly resending them. Receipt application reauthenticates the owner.
- Assigned tests cover cancellation ordering, stop/join, direct SQL transport boundaries, admission failure, startup failure, and restart without duplicating a completed send. These are source-level observations, not test pass claims.
