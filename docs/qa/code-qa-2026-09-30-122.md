## Findings

### P1 — Malformed retained JSON is classified as a database failure during reconciliation

Location: `platform/internal/agenthost/memory_read_store.go:106-110`, also `126-129`.

The reconciliation query executes `jsonb_array_elements(content)` before application decoding. A retained `knowledge_reads` or `script_runs` row with content `{}`, a JSON scalar, or JSON null causes PostgreSQL to reject that expression. The new error boundary converts that data-shape failure into `core.ErrDatabase`; both local error adaptation and HTTP response marking preserve its database provenance. Consequently corrupted retained data can invoke SQL fail-fast behavior rather than produce the required non-SQL malformed-data error. The added failure-origin test inserts exactly `{}` but only calls `ReserveKnowledge`, whose separate Go decoding correctly avoids this problem; it does not cover reconciliation.

Make the selection safe for non-array JSON and send malformed candidates through application validation without labeling those errors as database failures. Do not broadly suppress PostgreSQL errors. Add reconciliation coverage for malformed retained values through both transports, alongside a real SQL failure control.

### P2 — The HTTP completion response has a smaller aggregate budget than accepted stored reads

Location: `platform/internal/appclient/memory_read_state.go:76-84`; persistence and returned aggregate at `platform/internal/agenthost/memory_read_store.go:200-214`.

Each request/result can fit the 1 MiB input bound independently, while `CompleteKnowledge` returns both retained read slots. For example, reserve two small proposals and complete each with a result containing roughly 600 KiB of text: both completion envelopes pass validation, but the second returned slice exceeds 1 MiB. The local path returns success without checking response size; HTTP commits the same result and then `requestAuthorizedLimit` rejects its response. The caller sees an error after successful persistence only in HTTP mode. This is a concrete accepted-input transport mismatch; it does not require increasing the two-read budget. Existing bounds tests exercise only oversized input.

Define and enforce one aggregate output contract on both paths. Either give the aggregate an explicitly bounded allowance sufficient for its accepted slots/framing, or reject oversized aggregate state before commit consistently. Add an aggregate boundary test that verifies return behavior and persistence in both modes.
