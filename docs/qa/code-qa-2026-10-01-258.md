## Findings

1. **P1 — Clock remains stale across turn-rotation allocator wait.** `platform/internal/passbooking/service.go:193-200`, `admin_assignment.go:131-142`, `deadlines.go:119-130`, and `admission_prepare.go:74-79` observe registration time before calling `refreshRegistrationTurns`. That helper can subsequently block at `admission_retention.go:47` on advisory lock 782619, then uses the original time for rotation deadlines. Callers also retain that time for their snapshots. Concrete sequence: an expired captured turn exists; an intake transaction holds allocator lock 782619; admin assignment obtains its event/profile locks, observes a time before event finish, and blocks rotating that turn; the operator advances the clock past event finish; allocator releases; assignment still allocates and persists using its pre-wait observation. Normal command sales/tier decisions and maintenance deadlines have the same gap. A second turn that expires during the wait also remains absent from the previously selected expired IDs. Refresh configured time after allocator acquisition, recompute applicable turn selection/rotation deadlines and return the authoritative observation to callers before event/sales/tier/allocation decisions. Preserve the nil production path. Add a blocked rotation scenario, distinct from the already covered application-position allocator wait.

2. **P1 — Actual allocation and state validation happen after database admission.** `platform/cmd/zns/registration_fixture_clock.go:61-75` checks environment constants and platform only. `main.go:105-120` opens/pings the configured database and calls `runtimeapp.Run`; `runtimeapp/admission.go:61-76` acquires session advisory ownership on that database. Only inside the admitted app factory do `registration_fixture_clock.go:90-95` compare the actual database allocation and read/validate state. Therefore fully valid clock environment plus a wrong configured database URL can acquire runtime ownership on an unrelated database before rejecting allocation. Missing, malformed or insecure state can also acquire ownership before failing. This violates the requirement to reject before incorrect database authority or side effects. Parse/compare the effective configured connection allocation and validate the initial private publication before database opening/admission; perform the necessary live fixture guard before acquiring runtime authority. Keep nil-clock startup unchanged. Current preflight test covers wrong environment case and unsupported OS, not wrong effective database allocation or unavailable publication on Linux.

3. **P2 — Unsupported writer commands silently ignore configured clock variables.** `platform/cmd/zns/registration_fixture_clock.go:52-67` rejects only `api` and `bot`; every other non-app command returns success without checking even partial or malformed configuration. With `REGISTRATION_CLOCK_FILE` set, `zns migrate`, `fixture`, `product-fixture` and `export-fixture` continue to database opening and their normal writer dispatch. The requirement is that this synthetic reader configuration applies only to the combined app and unsupported commands fail visibly before side effects. Reject configured clock environment for unsupported writer/runtime commands before database dispatch. Add command-boundary coverage for these paths; preserve normal commands when all five variables are absent.
