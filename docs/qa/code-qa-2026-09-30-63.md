## Findings

### F1 (Medium, partly unverified): the error after a failed savepoint rollback is both a refusal and a database failure
- **Where:** `platform/internal/derivedmutation/registration_native.go:173-174`, `errors.Join(err, core.DatabaseOperationError(rollbackErr))`.
- **Mechanism:** Suppose `err` is a refusal `*core.ProblemError` (400/403/404/409) and the savepoint rollback fails with an SQL error. The joined error then satisfies both `errors.As(*ProblemError)` and `errors.Is(ErrDatabase)`.
  - Locally this is safe: `nativeRegistrationRefusal` checks `IsDatabaseFailure` first (`:146`), so the candidate is not completed as `rejected`.
  - Further up, the error goes out through `ResolveRegistrationIntake` to `passbooking.Service.Execute` (`service.go:56`) and `derivedmutation` `ExecutePassBooking`/`AssignPass` (`registration.go:45, 69`). Any caller or HTTP mapper that checks for a `ProblemError` before checking for a database failure would report a domain 409/403 to the client and would not stop the runtime.
  - `Error()` also becomes `"<code>\ndatabase unavailable"`.
- **Evidence gap:** I could not find the HTTP problem mapper with Read alone (the obvious guessed paths don't exist), so the precedence issue is a hypothesis. The test at `native_database_internal_test.go:50` only checks `IsDatabaseFailure` and `!nativeRegistrationRefusal`.
- **Suggested fix:** When the rollback fails with an SQL error, return only the SQL-classified error and drop the refusal. Use the join only to keep SQL provenance when the rollback error is a context error (the "SQL then canceled rollback" case). Add a test asserting that `errors.As(err, *ProblemError)` is false in the refusal-plus-rollback-EOF case.

### F2 (Low): join can carry unsanitized helper text
- **Where:** the same line as F1.
- **Mechanism:** The old code returned only `rollbackErr`. The new code also includes the capture `err` text. On the rollback-failure path, a helper that returns an unsanitized driver error (for example from `registrationnative.Check` or `CaptureNative`, which I did not read) now appears together with `ErrDatabase` in `Error()`.
- **Impact:** This is not a new leak class, because the rollback-success path (`:176`) already returns `err` as is. It does widen that exposure to one more path. It would be resolved by the F1 fix.

### F3 (Low, test quality): new tests don't cover several requirement points
1. **Destination expiry under DB failure.** `destination_database_test.go` checks that healthy aliases survive, but not that a failed alias keeps its old binding with the old expiry after a DB-origin failure, or that an absent failed alias is removed. The code does this (`bindings.go:83-85`); the new test doesn't prove it.
2. **Native resolver SQL paths.** There is no unit or integration test for SQL failure at:
   - `PendingNativeCandidates` (`registration_native.go:33-35`)
   - the outer `Begin` (`:68-70`)
   - `Commit` (`:105`)
   - the savepoint `Commit` (`:171`)

   Only the completion-update path is covered, by the integration test.
3. **Knowledge authority `SharedMemory`.** `authority_database_internal_test.go:478-482` does not exercise `SharedMemory` (the `epochOwner=""` branch). It shares code with `PrivateMemory`, so this is minor.

### F4 (Low, unverified hypothesis): the source-graph fake may not isolate the leaf under test
- **Where:** `native_database_source_internal_test.go:311-316`.
- **Mechanism:** The fake returns the injected error from every `QueryRow` except the `EXISTS ... core.users` query, and `Query` returns empty rows. The errors are only attributable to the in-scope leaves if `readsource.LockValidity` → `lockProposalValidity`/`lockEvents`/`lockActors` use `Query` and not `QueryRow`.
- **Evidence gap:** I could not locate those functions; the guessed file names don't exist. The `ErrNoRows` → `source_stale` assertion suggests the leaf is reached, but I couldn't confirm it.
- **Suggestion:** Match the leaf SQL text explicitly in the fake, or assert that the leaf query was issued.

`derivedmutation/registration.go:48-51` and `:76-79` return raw `s.DB.Begin` errors, which can carry driver diagnostics and lack SQL provenance. The file is outside this stage's scope; I'm noting it for a later stage and have not counted it against this diff.
