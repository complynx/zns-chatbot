## Finding

### [P2] Completed suggestions still fall through to command execution

Location: `platform/internal/bot/saved_plan_recovery.go:179-184`.

The new completion marker skips only the immediate `FinalizeCommand` call. It then always calls `knowledgeReceiptNotice`. For an authorized `knowledge.Suggest`, the original operation result contains the proposal's initial `pending_filter` state: `knowledge/mutations.go:64-89` creates that state, and `knowledge/service.go:208-228` returns the stored operation result. The receipt authorization and evidence projection do not refresh that proposal state. `bot/knowledge_receipt_notice.go:19-21` therefore returns `found=false`, even when the new completion check found an existing durable `knowledge_reply`.

Consequently, replay of a successfully completed suggestion falls back through `bot/order_agent.go:17-20` to the saved plan's normal execution. `interaction/knowledge_coordinator.go:62-71` calls the command endpoint and `FinalizeCommand` again. This repeats original-source attachment after completion, contrary to the requested replay boundary. The domain idempotency receipt prevents a second suggestion from being created, but does not prevent the repeated endpoint or attachment work. If the first handled turn persisted a pending-filter reply after a deferred assessment, the same fallback can also invoke the assessor again because a deferred attempt does not store a verdict (`interaction/knowledge_assessment.go:44-77`; `bot/knowledge_execute.go:70-73`).

Make the completed branch finish as a handled replay without entering the pending-filter continuation. Preserve receipt authorization and redaction before selecting any saved reply. Keep the pending-filter continuation for a genuinely unfinished turn. Add a `Suggest` completed replay case that counts attachment and command/assessment calls, plus a deferred-assessment reply case if that terminal reply is included in the completion contract. The current attachment integration matrix contains only `MemoSet` and `Curate` (`saved_knowledge_attachment_recovery_test.go:42`), so it cannot catch this branch.

## Other assessed behavior

- For memo and curate receipts, the marker is owner/update/kind scoped and is checked only after `Host.KnowledgeReceipt`. A failed marker read returns an error rather than treating the turn as unfinished. The unit test covers scoping and database failure.
- Normal reply persistence follows successful original-source finalization. `finishAgentPlan` records the reply before rendering, so an interruption after recording but before delivery can resume rendering without repeating attachment for the covered commands.
- Receipt lookup retains request-hash matching, current command authorization, original authority checks, history generation checks, and output tombstone handling (`knowledge/command_receipt.go`, `command_boundary.go`, `causal_replay.go`). The marker does not bypass those checks.
- The revised integration tests retain the configured Bot while replacing the model. They count attachment attempts and command endpoint calls, assert source ownership, inspect the durable reply and its actual visible card, compare visible state across replay, and check quota/model/assessment stability. These are meaningful checks for the covered commands.

## Limitations

This is source review, not runtime or functional acceptance. Concurrent recovery and the loss window between attachment commit and reply persistence were inspected, but not executed. The marker read and attachment are not one transaction: two unfinished recoveries or a lost response after attachment commit can still attempt attachment again; the existing domain attachment uses transactional, conflict-safe insertion. This review does not claim exactly-once network calls before a completion marker exists. The scoped tests also do not exercise concurrent recovery, loss immediately after attachment commit, or revocation after an already recorded reply.
