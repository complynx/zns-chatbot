## Finding

**[P2] Freeze the complete page effect set before replay** — `platform/internal/bot/admin_message_page.go:112–121`.

`queueAdminMessagePage` recomputes the number of chunks from a newly read live page on each processing attempt. The persisted delivery boundary keeps the first body for an existing effect (`platform/internal/botdelivery/results.go:31–38`), but accepts previously absent effects. Consequently, replaying the same owner/update after delivery states/failures change across a 1,800-rune boundary can introduce extra sends.

Concrete sequence: the first attempt saves a page of at most 1,800 runes under `admin_page:<id>:<offset>`, with navigation. After a transient later error or restart, the same ingress is processed again. New delivery failure details make the page exceed 1,800 runes. The retry saves `admin_page:<id>:<offset>:chunk:0` as a new send while the existing final effect remains the original full page. The new chunk repeats content already present in that saved final page and follows it in the shared lane. With partially saved longer pages, changing chunk boundaries can also combine bodies from different snapshots. This violates stable effects/replay and the claimed final-chunk navigation ordering.

Freeze the page snapshot and complete chunk/effect manifest for an ingress before enqueueing, and resume that saved manifest on retries. Add a regression at the real saved-result boundary that changes the review response between attempts, crosses a chunk boundary, and verifies unchanged saved bodies, unchanged effect count and order, and one navigation card. The added test currently replays an identical mock page and compares HTTP requests; it does not exercise first-body persistence with a changing page.
