**Senior Code QA review: SQL-origin error sanitization in delivery and conversation fence**

**Verdict: changes requested.** I found no correctness, locking or transaction regression in the changed production code. It is changes requested because the tests don't exercise about half of the new SQL-origin error paths, which the requirements asked for. There is also a moderate, unconfirmed privacy concern about cancellation errors that still carry raw driver text.

I only read source. I ran no tests or builds, so nothing here shows that anything passes at runtime.

### What I checked

- **Sanitizer:** `core.DatabaseOperationError` (`platform/internal/core/database_error.go:17-23`) passes through `nil`, `pgx.ErrNoRows`, `context.Canceled` and `context.DeadlineExceeded`. Every other error, including an untyped `io.EOF`, becomes the bare `core.ErrDatabase`. That value wraps nothing, so no driver text survives on this path.
- **Only direct SQL results are converted:** every new call wraps the error straight from a sqlc query or a `tx.Exec`/`Begin`/`Commit` call. Errors coming back from helpers are passed through, not converted again: `readQueue`, `lockQueue`, `lockPacing`, `extend`, `lockControlPacing`, `projectQueue`, and `ReserveControl`/`ScheduleControl` inside `Admit`/`Observe`.
- **Non-SQL errors stay untouched:** `ErrSettings`, `ErrQueueReference`, `ErrQueueState`, `ErrQueueBinding`, the `"delivery destination missing"` and `"invalid control pacing outcome"` errors, and `history_stale` are all unchanged.
- **No-rows handling still works:**
  - `readQueue` (`queue.go:220-225`) returns `pgx.ErrNoRows` unchanged.
  - So the no-rows checks in `Register` (`queue.go:46`), `lockQueue` (`queue.go:233`), `LockReferences` (`queue_locks.go:32`) and `ReadReference` (`queue_locks.go:79`) still work.
- **`projectQueue`** (`queue.go:263-266`): a row count other than 1 is still checked before conversion. On success it returns `DatabaseOperationError(nil)`, which is `nil`.
- **Locking and transactions:** lock order, the `FOR UPDATE` statements and the Begin/Commit/deferred-Rollback structure are unchanged. Only the returned error values changed.
- **Test step counts match the real query sequence:** I checked them against `dbgen/queue.sql.go` and `dbgen/pacing.sql.go`. Reserve makes 7 calls (Ensure, Lock, Ensure, Lock, Clock, Extend, Extend), ReserveControl 6, ScheduleControl with `Paused` 4, and Register's first three calls are Exec, QueryRow, QueryRow. `require.Equal(step, tx.calls)` also proves that execution stops at the first failure.

### Findings

**F1 – Medium (tests): about half of the changed SQL-origin paths are never tested**

`delivery/database_error_test.go:71-100` covers only Register (steps 1–3), ReadReference, Candidates, Reserve, ReserveControl and ScheduleControl. These changed lines are never run by any failure test:
- `queue.go:54` (AllocateDeliverySequence) and `queue.go:61` (InsertDeliveryEntry). With the fake transaction, `readQueue` succeeds and returns an empty row, so `Register` stops at `ErrQueueBinding`. It never reaches the allocate or insert steps.
- `queue.go:107` and `:115` (fairness and lane-served in `Begin`), `:127` and `:134` (`queueAdmission`), `:240` and `:245` (`lockQueue` lane/entry locks), and `:266` (`projectQueue`). Nothing calls `Begin`, `Finish` or a `Project` that reaches SQL.
- `queue_locks.go:52` and `:66` (`LockReferences` lock failures).
- `pacing.go:74` (`Schedule`).
- `control.go:40, 48, 56, 64` (pool `Begin`/`Commit` in `Admit`/`Observe`). These need a real pool, so a unit test can't reach them; there is no integration test for them either.

The delivery fault loop (`:106`) also never injects `pgx.ErrNoRows` through lock paths such as `Begin`/`Finish`/`Project`. So the no-rows → `ErrQueueReference` mapping in `lockQueue` (`queue.go:233-235`) has no test, and neither does the raw pass-through at `:245`.

**F2 – Medium (privacy, not confirmed): cancellation errors keep raw driver diagnostics**

Scoped call sites affected: `control.go:40, 56` most directly, and in principle every wrapped call site.

- **Mechanism:** `DatabaseOperationError` returns the original error whenever `errors.Is(err, context.Canceled/DeadlineExceeded)` is true. That includes errors that wrap a context error.
- **The concern:** pgx/pgconn can return wrapped context errors whose text contains connection details. The likely case is a pool `Begin` that fails with a `*pgconn.ConnectError` whose message names the user, database and possibly the host.
- **Why it's not confirmed:** I did not read the pgx source in this review, and I did not trace whether callers ever show `err.Error()` to users.
- **Possible fix:** in the cancellation branch, return `ctx.Err()` or `context.Canceled`/`context.DeadlineExceeded` itself. This keeps the cancellation meaning without the driver text. It would be a change to the core helper, which is outside the scoped files.

**F3 – Low (behaviour kept from before, inconsistent): unexpected no-rows is returned raw from lock and pacing queries**

- `lockQueue` maps a no-rows from `readQueue` to `ErrQueueReference` (`queue.go:233`). But if the `FOR UPDATE` re-read finds nothing at `:242-245`, it returns raw `pgx.ErrNoRows` to `Begin`/`Finish`/`Project`.
- The same raw pass-through applies to `LockPacing`, `DeliveryClock`, `AllocateDeliverySequence` and `AdvanceDeliveryFairness`. In normal operation these can't return no rows.
- This matches the old behaviour (not a regression) and fits "preserve no-rows". However, a caller that treats `ErrNoRows` as "not found" could misclassify these cases. Mapping `:245` to `ErrQueueReference` would be more consistent.

**F4 – Low (weak test assertions)**
- `fence/database_error_test.go` injects `pgx.ErrNoRows` into `Exec`, which never returns that error in practice. The assertion only proves the value passes through untouched; it doesn't test a realistic no-rows case.
- The delivery test has no no-fault success run, unlike the fence test. So it never asserts that a fully successful Reserve/ReserveControl/ScheduleControl returns `nil`.
- The negative tests (`:120-141`) mostly hit validation that fails before any SQL (`ErrSettings`, and `ErrQueueState` for a disallowed state). They don't test domain outcomes that happen after SQL, such as `projectQueue` count ≠ 1 → `ErrQueueReference`, or `queueTransition` rejection → `ErrQueueState`.

**F5 – Info (behaviour kept from before)**

`Begin` returns a `gate` with `Ready: true` together with a non-nil error (`queue.go:111-115`), and `lockPacing` returns partly filled rows with an error. This is not new, but callers must check the error before `Ready`.

### Uncertain / not verified
- **`HistoryGeneration`:** I couldn't find the generated conversation `dbgen` source file, so I did not confirm that it uses `QueryRow` with a single `*int64` scan. The fence test's step counts and fake `Scan` depend on that.
- **Lost SQLSTATE:** converting errors to `ErrDatabase` removes SQLSTATE codes such as 40P01 (deadlock) and 40001 (serialization failure). If any caller outside the scoped files retries on those codes, that retry would stop working. I could not search for such callers.
- **Go version:** `t.Context()` and `errors.AsType` need a recent Go toolchain. I did not check `go.mod`.

### Dependencies and suppressions
- The only new dependency is the internal `core` package in `control.go`, `pacing.go`, `queue.go`, `queue_locks.go` and `fence/owners.go`; `generation.go` already imported it. The tests add `io`, `pgconn` and `testify`.
- There are no lint suppressions. The ignored rollback error `_ = tx.Rollback(ctx)` is unchanged from before.
