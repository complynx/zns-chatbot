**What the fix relies on** (`platform/internal/core/database_error.go`)
- `DatabaseOperationError` (lines 21–38) lets nil and `pgx.ErrNoRows` through unchanged. It turns cancellation, deadline and serialization errors into their plain sentinels, and turns every other error into `ErrDatabase`, so driver text is dropped.
- `IsDatabaseFailure` (lines 58–70) returns true for `ErrDatabase`, and also for a raw `*pgconn.PgError` or `*pgconn.ConnectError`. It returns false for other transport errors.

### F1 — HIGH (verified from source): `PaymentProof` can turn a database failure into `forbidden` or pass raw driver errors through
`payments.go:218–227`, together with `Payment` at `payments.go:196–201`.

- When the proof query finds no row, `PaymentProof` calls `Payment`. If `Payment`'s own query also finds no row, it calls `legacyFreePayment` (`legacy_payments.go:22–25`), and then `absentOwnerPayment` when the actor is the owner (`payment_absence.go:30–31`). Both return raw query errors, and `Payment` passes them on as they are at line 201.
- The new check at lines 220–222 only catches errors that `IsDatabaseFailure` recognises. That gives two bad outcomes:
  1. **Database failure becomes `forbidden`.** Some query failures are neither `PgError` nor `ConnectError`: a closed connection, a network read/write error wrapped by pgconn, a closed pool. `IsDatabaseFailure` returns false for these, so line 227 returns `forbidden()`. The requirement says an infrastructure failure must never become forbidden.
  2. **Raw diagnostics leak.** A raw `PgError` (message, detail, constraint) or `ConnectError` (connection parameters in its text) makes `IsDatabaseFailure` true, and line 222 returns it unsanitised. That breaks the "no raw driver diagnostics" rule. Cancellation errors from these paths are also returned raw rather than as the plain `context.Canceled` / `context.DeadlineExceeded`.
- **Why tests miss it:** `TestAdminDatabasePaymentProofSecondaryFailure` only injects failures into the first `SELECT p.kind,p.id` query, which is wrapped at line 203. The legacy and absent-owner lookups are never reached with a failure, and the actor ("visitor") is never the owner.
- **Suggested fix:** wrap the actual SQL calls in `legacyFreePayment` and `absentOwnerPayment` with `DatabaseOperationError`, keeping their `forbidden` / `pass_payment_missing` results unwrapped. Then have `PaymentProof` return `DatabaseOperationError`-style sentinels, not whatever error `Payment` gave it. Add failure-injection tests for both lookups.

### F2 — MEDIUM (verified): `Payment` still returns raw driver errors from known SQL calls
`payments.go:197–201`.

- Leaving the mixed `legacyFreePayment` result unwrapped is correct, since wrapping it would also turn `forbidden` into a database error. But the SQL calls inside those two helpers are known query sites, and they still carry no database marker and no sanitising.
- Those helper files are outside the listed scope, but the in-scope `Payment` and `PaymentProof` depend on them. Whether a higher layer cleans these errors before they leave the service is outside what I reviewed.

### F4 — LOW: a missing row that should always exist comes back as bare `pgx.ErrNoRows`
Because `DatabaseOperationError` lets `ErrNoRows` through, integrity breaks surface as a plain "no rows" error with no database marker:
- `adminReplay` second read (`admin_assignment.go:228–231`): the operation row exists but the assignment row is missing.
- `lockAdminProfile` SELECT right after its INSERT (`admin_assignment_profile.go:31–34`).
- `adminCreate` telegram lookup (`admin_assignment_profile.go:124–126`).
- The `FOR UPDATE` re-reads at `admin_batch_prepared.go:120` and `admin_batch_runtime.go:180`.

This behaves the same as before. It's only a problem if some higher layer treats `ErrNoRows` as not-found or forbidden, and I couldn't check that.

### F5 — LOW (uncertain): database constraint codes are now hidden
Constraint violations on these writes (for example unique-key violations) now become `ErrDatabase`:
- `recordAdminAssignment` (`admin_assignment.go:271–294`)
- `Persist` (`admin_batch_prepared.go:106–115`)
- `freePayment` (`admin_assignment_payments.go:53–74`)
- `submitProof` (`payments.go:60–72`)

For example, two concurrent `RunBatch` calls with the same key could hit a unique-key violation in `Persist`, since `prepareRuntimeBatch` takes no lock. If anything above this package mapped those codes to a conflict, that mapping is now gone. Without directory listing I couldn't confirm whether such a mapping exists.

### F6 — LOW / question: `PaymentCompletionReceipt` always uses the accept action
`payment_completion_receipt.go:67–75` sets `Action: commandProofAccept` for both accept and reject. It may be deliberate as a shared payment-review action, but I couldn't confirm it against how `ReadAuthority` is consumed. The database-error handling in this file (lines 57–62) is correct.
