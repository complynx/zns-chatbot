## Actionable findings

1. **P1 — local order SQL transport errors lose provenance.** platform/internal/appclient/local_orders.go:49-53 recognizes only the marker or concrete pgconn PgError/ConnectError through IsDatabaseFailure. The local service returns raw database errors, including orders/service.go:232-234 (Begin), :281-282 (query), and :247 (Commit). A connection EOF/reset during an established SQL operation is neither PgError nor ConnectError; it becomes an unmarked internal_error. Run therefore cannot take its SQL termination branch and can retry within the same runtime if connectivity is restored. This is particularly important for uncertain commit outcomes. Preserve SQL provenance at the service's known database-operation boundaries, then sanitize through the existing wrapper; do not globally classify EOF/network errors as SQL. Add focused established-connection/commit-failure coverage in addition to the PgError trigger case.

2. **P1 — inbox registration persistence bypasses SQL marking.** platform/internal/bot/inbox.go:34-35 returns saveRegistrationIngress errors unchanged. That helper performs SQL inside the same batch transaction: registrationingress/ingress.go:67-70 executes the advisory lock and INSERT; registrationnative/native.go also queries SQL for applicable callbacks. An established-connection EOF/reset here bypasses inboxDatabaseError, IsDatabaseFailure rejects it, and Run follows its retry path if the separate lock connection and reconciliation remain usable. Thus the known inbox batch SQL surface is not completely covered. Mark errors at those concrete SQL calls while keeping binding/validation errors distinct; exercise this ingress path with a transport fault and require immediate runtime return without a second attempt.
