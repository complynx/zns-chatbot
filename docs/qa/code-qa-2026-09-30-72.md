## Requirement checks (scoped methods)
- **Known SQL errors are sanitized and fatal.** Every changed return sits right after a direct pgx `QueryRow`/`Scan`, `Exec`, `Begin` or `Commit` and passes through `core.DatabaseOperationError`. That function returns bare sentinels, so driver text cannot leak. In the render paths, callers return the error unchanged. `RenderPassMenu:58` only redirects `ProblemError` stale codes, and `ErrDatabase` is not one of those.
- **Only SQL errors are marked.** Helper, provider and domain returns are left as they were: `botCardHash`, `json.Marshal`, `derivedReplyVisible`, `NotificationContext`/`Preferences`/`Translate` and `queueBotCard`. The JSON decode in `massageState:62-64` and `passMenuRecord:31-33` now happens after `Scan`, so decode errors stay unmarked. The test checks this at test lines 71-76.
- **NoRows and defaults are kept.**
  - `massageState:56-58` and `passMenuRecord:25-27` return the default state before any error is sanitized.
  - `registrationReplyPayload:144-146` and `renderRedactedPassMenu:81-83` return early on NoRows.
  - `deliverMassageCard`/`deliverPassMenu` still pass `pgx.ErrNoRows` through, because `DatabaseOperationError` keeps it unchanged.
  - `renderRedactedPassMenu:84-85` with no error and `MessageID==0` still returns nil.
- **JSON identity.** Zeroing the value before `json.Unmarshal` (`massage.go:62`, `pass_delivery_authority.go:31`) matches how I understand pgx v5's JSON scan to work: it zeroes the destination, then unmarshals. So stored `{}` or `null` does not inherit the missing-row default. The test checks this at lines 62-83. I could not read the pgx source to confirm (see Limitations).
- **Cancellation.** `DatabaseOperationError` returns `context.Canceled`/`DeadlineExceeded` only when the error itself wraps them. It does not check `ctx.Err()`, so a real `PgError` stays `ErrDatabase` even if the context is cancelled afterwards. Nothing in scope wraps an already-marked error before sanitizing, so a known DB failure cannot be turned into a cancellation.
- **Transactions.** In `redactPassMenu:29-50`, the UPDATE and DELETE run in one transaction, with rollback deferred. `RowsAffected()==0` returns nil before commit, so a newer revision wins without error. Buttons are deleted in the same transaction as the tombstone is written, so stale callbacks cannot outlive redaction. If the commit outcome is unknown and it did commit, the next `RenderPassMenu` takes the `saved.Redacted` path (`pass_menu_render.go:54-55`) and never reuses the old body.
- **Suppressions and dependencies.** None added. The only new imports are `encoding/json` and the internal `core` package.
