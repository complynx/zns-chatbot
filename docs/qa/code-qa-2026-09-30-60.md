### P1 — Classify the media cleanup error at its SQL origin

Location: `platform/cmd/zns/api.go:130-134` (also startup at lines 99-100). Dependency: `platform/internal/media/media.go:90-93`.

The new tick calls `databaseFatal(err)` for `Media.PruneExpired`, but that service returns the raw error from `s.DB.Exec`. `core.IsDatabaseFailure` recognizes database markers and concrete PgError/ConnectError types; it intentionally does not classify a generic transport error. If an established connection drops during this DELETE and pgx returns EOF or unexpected EOF, this positively known SQL failure therefore takes the optional warning path, and the tick proceeds to other SQL work instead of notifying the fatal latch. A recovered connection on the next operation means the application can continue without the required supervisor restart. The startup path also returns this raw SQL error directly, so PostgreSQL diagnostics are not reduced to the safe marker there.

Classify `PruneExpired` at the direct SQL operation with `core.DatabaseOperationError`, preserving ordinary cancellation, and retain the existing mixed-error classifier for operations that also produce provider/domain errors. Add focused evidence for an established-connection drop during media cleanup and for sanitized startup failure. The present maintenance test uses a failed dial, which creates a recognized ConnectError and cannot expose this gap.
