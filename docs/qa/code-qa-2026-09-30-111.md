## Finding

**P1 — Preserve SQL provenance for database-local deadlines.** `platform/internal/bot/credit_cutover.go:19-21` and the other new SQL wrappers call `core.DatabaseOperationError`, which returns bare `context.DeadlineExceeded` at `platform/internal/core/database_error.go:28-29`. `classifyInboxResult` at `platform/internal/bot/inbox_retry.go:67-88` sees no SQL marker and, when the poller's parent context remains live, classifies that error as `inboxFail`. A database connection timeout can therefore consume the handler-failure budget instead of stopping the runtime. The same issue affects the new media SQL boundaries, for example `platform/internal/bot/media_intake.go:97-98`. When the subsequent bookkeeping connection is available, repeated SQL-local deadlines can quarantine an otherwise valid update; if bookkeeping also fails, the runtime stops but only incidentally because that second operation fails.

Source-level reproducing mechanism: use a live parent context and make a pool operation fail with an error wrapping `context.DeadlineExceeded` (a pool `BeforeConnect` fault provides a deterministic seam, as used for EOF in the existing tests). Route that error through `bindBudget` or a media SQL read, then through `classifyInboxResult`. The wrapper strips origin, `core.IsDatabaseFailure` returns false, and classification returns `inboxFail`. A concrete `pgconn.ConnectError` wrapping a deadline also loses its concrete type at the sanitizer. For cancellation, the analogous origin loss defers rather than enforcing the stated SQL-fatal rule.

Required correction: retain sanitized positive SQL provenance at known database boundaries even when the driver error wraps a local cancellation/deadline; preserve the intended parent-cancellation behavior and keep provider deadlines distinguishable. Add a focused live-parent SQL-deadline control alongside the existing provider-deadline, EOF and cancelled-parent cases. This is a source-confirmed classification defect; the proposed reproducer was not executed in this review.

## Source facts checked

- Whole-batch inserts, registration ingress and `telegram_received` update share one transaction before dispatch. Row ID is checked against decoded payload ID before calling the handler.
- Claims persist a lease without incrementing failures; the pending-chat anti-join blocks later same-chat rows regardless of cooldown. Passes are bounded. The fifth conclusively recorded ordinary failure quarantines the row; quarantine retains payload and releases the pending barrier.
- Typed SQL markers precede domain terminal outcomes in inbox classification. Failed outcome writes return SQL errors without successfully recording a failure. Parent cancellation and cutover configuration failures do not increment the budget.
- Structured rate limits and local control admission use persisted deadlines without converting large intervals through `time.Duration`. Invalid/unrepresentable values park at infinity. Pending infinity continues to block its chat; quarantine does not.
- Media SQL byte scans and application JSON decoding are separated. NoRows, SQL/JSON null and fallback behavior have explicit focused test cases. SQL query/scan/row-collection/exec wrappers sanitize driver diagnostics, subject to the deadline finding above.
- Migration 087 is additive, guards chat-key casts, indexes pending chat heads and grants UPDATE to the established runtime roles. The operator document requires stopping old writers and forbids unsafe rollback to readers that ignore retry/quarantine state; it describes retained-payload/effect reconciliation and compatible-reader recovery.
- The scoped changes do not replace authentication, history deletion fences, business receipts or delivery reconciliation. No dependency changes, suppressions or gate weakening were found in the supplied authored scope.
