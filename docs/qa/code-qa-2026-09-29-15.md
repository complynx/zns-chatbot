## Findings

### F1 — Medium (test gap): the 90-hour test never runs the Go deadline check
- **Where:** `platform/integration/pass_invitation_start_test.go:31-52`; `deadlines.go:69-76` and `:168`.
- **Mechanism:** The maintenance query only picks events with waitlisted bookings, captured intents, or pending invitations past 58 hours. In this fixture, once Alice invites, no booking is waitlisted (Bob has none). With the fix, the pre-filter at `:74` doesn't match, so `ProcessDeadlines` skips the event entirely. `processDeadline` at `:168` never runs at the 0-hour and 57-hour steps. It only runs at 59 hours, where old and new logic agree.
- **Impact:** If `:168` went back to `b.CreatedAt.Before(...)`, every test in the set would still pass. In production, any event with a queue has waitlisted bookings, so it is always selected and the Go check is what actually decides. That is exactly the 90-hour scenario the requirement says the tests must prove.
- **Fix:** Keep the event selected by adding a waitlisted co-booking before calling `ProcessDeadlines`. For example, a third user with a profile registers `solo` while `amount=0`. Then assert Alice is still `waiting-for-couple` after the 0-hour and 57-hour ticks.

### F2 — Low: duplicated assignments
- **Where:** `mutations.go:135` repeats `:139` (`b.InvitationStartedAt = nil`), and `mutations.go:204-205` sets it twice in a row.
- **Mechanism:** Harmless at runtime, but it looks like a mechanical edit and may trip linters that flag duplicate assignments. Remove `:135` and `:205`.

### F3 — Low: the new-target assertion is too weak
- **Where:** `pass_invitation_start_test.go:98`.
- **Mechanism:** `initial` was moved back 24 hours by SQL (`:75`), so `After(initial)` would also pass if a new target wrongly got `CreatedAt` or any time in the last 24 hours. Compare against `repeated`'s timestamps, or check it is within a few seconds of the DB's `clock_timestamp()`.

### F4 — Low / informational: some assertions prove less than they look
- The "restart" at `:81-82` rebuilds a service that holds no state (`Service` is just a DB handle, `types.go:16-22`). Durability is really shown by the SQL-set value at `:75` being read back. That's adequate, but the comment overstates it.
- In the `decline` subtest, `result` at `:125` is Bob's empty booking (Bob has no row), so `assert.Nil` there checks nothing. The inviter check at `:126-128` is the real one.
- Exit by `admin_cancel` has no test. It goes through the same `tombstone` code as `cancel`, which is tested.

## Operational note (meets the requirement, flagged for awareness)
Invitations created by this platform before the migration will have a NULL start and use the `created_at` fallback. Any of those invited after a queue wait of more than 58 hours will expire on the first maintenance run after deploy. That's what "don't fabricate dates" means here. If it's unacceptable, the `created_at` of the matching `core.pass_notifications` `kind='invitation'` row is real evidence that a backfill could use.
