## Finding

**[P2] Expose shared service pause separately from durable per-recipient outcomes.** Frozen `after/platform/internal/adminmessage/job_progress.go:47-66` examines only `admin_message_deliveries.state` and `failure`. It does not read shared bot/chat pacing or the canonical delivery destination binding. `Paused` counts only items whose own saved outcome is `paused`, so it cannot show a shared pause affecting untouched items or an entire different job.

Concrete source-derived scenario: one delivery in job A receives a credential/configuration rejection with outcome `paused`. `delivery.Schedule` persists its reason in bot-wide `delivery_pacing` (`platform/internal/delivery/pacing.go:85-103`). The shared candidate query excludes every pending head for that bot while this reason is present (`platform/internal/delivery/queries/queue.sql:54-59`). All untouched recipients in job B retain their original domain `pending` state and empty failure. Reviewing B consequently returns `Queued=N`, `Paused=0`, `Deferred=0`, and EN/RU renders no indication that its service is paused. Even A shows only the rejected item's pause, rather than the shared scheduling condition. Accepted global queue telemetry already distinguishes shared pacing pauses (`delivery/observation.go`), but that information is not part of the authorized per-job API or Telegram progress view.

Keep the saved outcome counters truthful and add a separate safe shared-pause observation for affected pending recipients/job, using the canonical queue chat and owning bot binding. Do not overwrite terminal outcomes or expose raw provider diagnostics. Add a real-PG test in which the pacing pause is created by another job while this job's domain rows remain untouched, with EN/RU presentation assertions. The candidate test currently sets each domain state directly and never establishes shared pacing (`after/platform/integration/admin_message_progress_test.go:32-46`), so it cannot detect this gap.
