## Findings

### P2 — A queued off-page edit can retire a payment card after the user returns to its page

Location: candidate `platform/internal/bot/delivery_cards.go:303-304`; related candidate `platform/internal/bot/order_cards.go:46-47`.

The new branch renders `OrderOffPage` solely from the persisted notice. It never checks whether the order is still outside the current page. Start with an opened payment message whose current hash contains the live details. Handle Next without pumping the delivery queue, then handle Previous before that off-page edit runs. Returning to the page renders the original details, but `deliverOrderCardChecked` sees the existing message hash equal to that payload and returns without enqueueing a restoration. When the older queued intent finally dispatches, this branch edits the message to the off-page notice and projects `Retired: true`, although the order is now on the selected page. A later reconciliation may repair it, but the return operation itself leaves stale presentation after its queued effects settle. Cooldown makes this ordering practical.

Revalidate current pagination before rendering/admitting the off-page edit, or reconstruct the current selected presentation. Ensure an obsolete retirement cannot overwrite the selected page after the return payload was skipped by the hash optimization. Add a focused away/back test that admits both updates before draining deliveries. The new EN/RU test calls `handleOrderVisible` after every update, which drains work and excludes this ordering.

### P2 — Live off-page rendering bypasses current payment-source and payment-read checks

Location: candidate `platform/internal/bot/delivery_cards.go:303-304`; related candidate `platform/internal/bot/payment_card_redaction.go:27-40`.

The normal payment rendering path calls `paymentInstructionsWithSource`, which reads current payment instructions and runs `checkPaymentDelivery`. That check rereads `paymentSource`, compares its binding with the intent source, checks the current payment payload, and verifies source/history authorization. The new off-page branch returns before this path and only reads preferences. `bindBotCardSource` verifies the current history generation but does not reread the payment-source binding. The SQL family check only checks that the order still exists, belongs to the owner/event, and is not deleted; it does not replace these checks or the `actor.can_book` condition in `orders.Instructions`.

For example, enqueue an off-page intent with the original manual source (`nil`), then explicitly reopen the same card with a fresh derived source before dispatch. The old off-page intent remains admissible even though the persisted card source changed. Likewise, revoking `can_book` after enqueue does not prevent this branch from delivering its ordinary live-payment notice. This violates the requirement to preserve current source/payment/owner checks for live off-page retirement. The bounded deleted-card cleanup may be source-free; ordinary off-page payment retirement must retain its existing payment-read checks. Validate the current source binding and payment read before producing the off-page notice, and cover a binding replacement or current-rights revocation between enqueue and dispatch.
