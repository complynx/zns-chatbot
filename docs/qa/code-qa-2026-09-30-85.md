## Findings

1. **P2 — pass refresh SQL failure can still complete the follow-up.** `platform/internal/bot/pass_notifications.go:90-93` calls `refreshPassNotificationViews` before the new classification guard, but `platform/internal/bot/pass_notification_views.go:12-14` returns its direct `QueryRow(...).Scan(...)` error unchanged. If receipt storage succeeds and this later SQL operation returns an untyped connection failure such as `io.EOF`, `IsDatabaseFailure` returns false and `CompletePassNotificationFollowup` is invoked. A concrete PostgreSQL error instead propagates with driver diagnostics unsanitized. Apply `core.DatabaseOperationError` at that direct SQL boundary. Add a focused case that succeeds through receipt storage and fails the view-presence query; the submitted follow-up test injects failure at the first SQL connection and therefore never reaches this query.

2. **P2 — follow-up renderers can discard positively marked database failures before the new guards see them.** The calls at `platform/internal/bot/notifications.go:123`, `massage_notifications.go:113`, and `legacy_food_notifications.go:103` can enter existing domain-error adapters: `order_refund_cards.go:28-30` returns nil for a forbidden `RefundTasks` error; `massage.go:157-158` turns a client-status problem into a stale-view result; `legacy_food_callbacks.go:214-215` replaces a client-status problem with a queued unavailable notice. None checks `core.IsDatabaseFailure` first. The API client explicitly preserves database provenance on such problems (`appclient/client.go`, `coreResponseError`), so a database-marked 403 can disappear and the caller can then complete the notification follow-up after a known SQL failure. Check database provenance before those domain fallbacks, returning the marked error unchanged. Verify a marked 403 during each affected post-send render and retain the ordinary unmarked domain policy. These are rendering dependencies of the bounded patch, not findings about the excluded outer delivery loops.
