### Findings

**F1 — Medium (defect, found in source). The new registration lock step applies a size limit that the later source lock deliberately skips. Valid registration mutations can now fail.**
- `platform/internal/derivedmutation/registration.go:20-23`: the lock step calls `readsource.ExpandProposalSources`.
- `platform/internal/readsource/proposals.go:18-24`: that function returns `Merge(closures...)`.
- `platform/internal/readsource/capture.go:26-28`: `Merge` checks `Valid(result)` and returns `ErrLimit` when the combined result is too big.
- `platform/internal/readsource/authority.go:43-80`: `Valid` limits the total count to `MaxAuthorities` (group contents included) and the size to `MaxAuthorityBytes`.
- The later source lock (`lockSource`, via `lockProposalValidity`) takes a different path. It builds the same combined set with `proposalWindowAuthorities` (`proposals.go:99-105, 124-142`). That function's comment says it avoids the limit on purpose: *"a history window may combine many valid records… without applying the persisted-record budget to the window."*
- **How it fails:** a source can be valid and still reference several derived memories or proposals. Each of those can carry up to `MaxAuthorities` entries of its own. Their distinct combination can be over the limit. The lock step then returns `ErrLimit` before any domain check runs, even though `lockSource` would have accepted the same source.
- **Scope:** this is new behaviour in all three entry points: `CapturePassAdmission` (`registration_admission.go:29-38`), `ExecutePassBooking` (`registration.go:60`) and `AssignPass` (`registration.go:88`). Before this change they did no expansion here, so this failure could not happen.
- It fails closed, so there is no security impact. It is a correctness and availability regression. `ErrLimit` is a plain `errors.New` rather than a problem error, so it will probably reach callers as a 500. I did not check how it is mapped.
- **Fix:** build the lock-step set with the same unlimited combination (`proposalClosures` + `proposalWindowAuthorities`), for example through an exported helper. Then the lock step and `lockSource` always agree on the set. Add a test with two derived references whose combined size is over the limit.

**F2 — Medium (defect, found in source). A permanently revoked or unlinked owner can block receipt recovery for everyone and causes repeated identity calls.**
- `platform/internal/bot/delivery_worker.go:168-175`: `continueBotIntent` now calls `b.API.NotificationContext` for non-identity intents. If that fails, it returns the error without updating the row.
- `delivery_worker.go:130-131`: the batch query selects `state='sent' AND NOT continuation_done AND not_before<=clock_timestamp() ORDER BY not_before,… LIMIT 32`.
- Nothing in `ContinueBotIntentReceipts` (`:149-166`) moves `not_before` forward or retires the row after a failure.
- `platform/internal/bot/delivery_dispatch.go:117-128` runs this step on every delivery pass. The polling interval is `pollInterval = 300ms` (`bot.go:574`).
- **How it fails:** an owner whose identity is revoked for good (inactive or unlinked) now fails on every attempt. The row keeps its old `not_before`, so it stays at the front of the queue. With 32 or more such rows, every other pending receipt never gets processed. Even with fewer, each pass retries every blocked row, and each retry is a fresh identity call (probably a token exchange). Before this change, identity was not needed on this path, so this permanent failure could not happen here.
- The requirement to deny revoked identities is met: `TestBotDeliveryReceiptAuthenticatedRecovery` expects `ErrZitadelIdentity` and a later successful recovery. What's missing is backoff or a way to close the row.
- **Fix:** when the identity step fails, push `not_before` back with a backoff before returning. Or treat terminal identity errors like `sourceDenied` in `botdelivery.ApplyReceipt` (`receipts.go:37-43, 81-88`), which marks the row done without projecting. Add a test with more than 32 revoked-owner rows plus one healthy row.

**F3 — Low (nit). `restoreAdmittedProfile` reads a pointer without a nil check.**
- `platform/internal/agenthost/script_store.go:342-348` checks only `admitted.Profile` and then reads `intent.Profile.Value`.
- Today `admitted` comes from `cloneScriptCall(intent)`. Nothing I read creates a `Profile` where there wasn't one: `RedactProfileScript` (`script_redaction.go:112-118`) and `scrubRetiredCall` only copy an existing one. So it can't be triggered now, but a future change that sets `Profile` during admission would cause a panic. Add `&& intent.Profile != nil`.

### Requirements check (from source, not from running anything)
- **Lock order:** the expanded event union is locked before the actor locks, which also use the expanded set (`registration.go:20-31`). `lockSource` later expands the set again in the same transaction and re-checks current authorization, so revocation checks are kept (`service.go:49-58`; `causal.go:62-101`).
- **Private profile value:** `ScriptProfileMutation.Value` is tagged `json:"-"` (`script_types.go:166-171`), so the stored ledger can never contain it. `prepareLedgerChange` also scrubs the admitted record (`script_store.go:478`). The restore works on a copy made after commit (`:343-346`), so the ledger slice is not changed. `CompleteCall` compares identities with `json.Marshal`, which leaves the value out, so the comparisons still match.
- **Delivery:** `deliveryCompletionContext(live)` is `WithoutCancel(live)` with a timeout (`delivery_lifecycle.go:10-12`). It keeps the authenticated context values and drops cancellation, so cleanup still runs during shutdown. The receipt step only runs when the state is `Succeeded` and never calls Telegram again, so a successful send is not repeated. On the success path the identity is now exchanged twice (`:37` and `:170`). That is correct but adds an extra call.

### Uncertainties (not confirmed as defects)
- **Stale expansion:** `ExpandProposalSources` reads proposal and memory rows without locking them, and `lockSource` reads them again later (`proposals.go:59-97`). If a proposal's or memory's stored authorities could change between those two reads, `lockSource` could lock a new event after the actor locks, which risks a deadlock. The `submitted` flag only changes `Published`, not the event set. I did not confirm whether `knowledge_proposal_authorities` or memory evidence can be changed after they are written.
- I did not confirm that `NotificationContext` checks `core.zitadel_identities.active`. The test only assumes it does.
