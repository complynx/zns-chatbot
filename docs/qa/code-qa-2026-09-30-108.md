So this is not a superuser-only proof.
2. **Read and lifecycle coverage (lines 26–60), checked against `turns.sql`:**

3. **Bootstrap fix works:** `product-roles.sql:5` creates `interaction` before migrations run, so the `CREATE SCHEMA IF NOT EXISTS` in 068 (line 1) does nothing. The default privileges at lines 10–11 (for tables created by `postgres`) then apply to `saved_turns`.

5. **Housekeeping:** no suppressions, and no new dependencies that I could see (testify and pgx are already in use). Cleanup runs in the right order: the login connections close first, then `DROP DATABASE … WITH (FORCE)`, then the roles are dropped.

## Actionable findings
- **F1 (Medium, missing test for a requirement): the repair path is never tested.** The test only builds a fresh database from the bootstrap (lines 110–116). The situation the repair targets never appears: 068 created `interaction` owned by `postgres`, and `saved_turns` has no grants. So nothing automated shows that the repair script, and only it, makes a stand like that work. Suggested test: bootstrap *without* the new line 5 (or the old `product-roles.sql`), migrate, confirm access is denied, apply the repair script, then run the same Store lifecycle and meter-denial checks.
- **F2 (Medium, test fidelity): renaming the roles skips grants that migrations make by name.** Line 112 renames `zns_app`→`r46_app_*` and `zns_meter`→`r46_meter_*`. Migrations do grant by literal role name; for example, `084_bot_delivery_application_owner.sql:5-9` grants to `zns_app`/`zns_api`/`zns_runtime`. So the test's meter role probably has no grants at all, and the denial check at lines 64–75 is trivially true. It would not catch a migration that grants `zns_meter` access to `interaction`, or one that revokes `zns_app`. I haven't found where the real meter grants live, so that part is an unverified hypothesis. Also, the check never tries INSERT, and a schema-level denial (no USAGE) returns the same 42501 error as a table-level one.
- **F3 (Low–Medium, least privilege): the fresh bootstrap gives `zns_app` more than production or the repair does.** `product-roles.sql:5` makes `zns_app` the *owner* of `interaction`. A schema owner can CREATE objects there and DROP any table in it, including `saved_turns` (PostgreSQL lets the table owner, the schema owner or a superuser drop a table). Production creates the schema owned by `zns_migrator` and gives the runtime role USAGE only (`init-roles.sh:24-25`), and the repair gives USAGE only (line 4). This copies the existing sandbox pattern for `core`/`bot`, but it leaves fresh and repaired stands with different privileges. Suggestion: create the schema as `postgres` and add `GRANT USAGE ON SCHEMA interaction TO zns_app`.
- **F4 (Low, least privilege): DELETE is granted but not used.** The repair grants DELETE on `saved_turns` (line 5), and the default privileges do the same for future tables (bootstrap line 10, repair lines 6–7). `interaction.Store` never deletes from `saved_turns` (see turns.sql). This does match production's default privileges (`init-roles.sh:26`), so it is acceptable, but only if you accept production parity as the reason.
- **F5 (Low, coverage gap against "full lifecycle"):** these paths are not exercised:
  - MarkTerminal with `HistoryDeleted` (`DeleteDerivedReplies`, which needs DELETE on `bot.interactions`).
  - `ClearDerivedReplies` actually changing a row. The derived reply for update 2 is never created, so the UPDATE matches nothing.
  - The trusted branch, where an authoritative origin should give `SourceRevoked=false`. The authoritative origin inserted for update 1 is never checked against a terminal turn.
  - MarkTerminal inserting a new row, `ReplyOrigin`, and `ConsumedVoice` (reads `bot.media_intake`).
- **F6 (Low, environment coupling):** the bootstrap and repair hard-code `FOR ROLE postgres`. If `TEST_DATABASE_URL` connects as a different superuser, the migration tables won't get the grants and the test fails. That is a false failure, not a false pass. The repair likewise assumes the stand's migrator is `postgres`, which I could not confirm because I didn't read the sandbox compose files.
