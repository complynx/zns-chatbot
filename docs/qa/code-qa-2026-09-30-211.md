## Finding

**[P2] The selected apply deadline does not bound acquisition of the fake mutation mutex.** In R104 `final/internal/sandbox/edit_delay.go:247–253`, the provider creates a 20-second context, checks it once, and synchronously calls `writeAdmittedMessage`. That function immediately executes an unconditional `f.mu.Lock()` at `final/internal/sandbox/fake.go:288`. The mutex wait observes neither the provider context nor invalidation. Existing ordinary handlers hold this same mutex while calling `f.save(r.Context())`, for example `getUpdates` at lines 207–226 and `labInput` at lines 479–516. Those ordinary request contexts have no SQL-operation deadline; the configured HTTP read/write timeouts do not add one to the request context or interrupt a mutex wait.

A concrete failure sequence is: hold a database lock conflicting with the fake-state upsert; select a before-apply edit; allow an ordinary poll/input handler to enter its blocked save while owning `f.mu`; release the selected edit. Its 20-second context expires, but its handler remains blocked on `f.mu` until the ordinary save completes. Provider cancellation/invalidation also cannot end that wait. If the mutex later opens after expiration, the selected path still mutates the in-memory message and edit counter before its canceled save rejects. The fake-only timeout therefore does not provide the stated bounded provider work/cancellation behavior, and shutdown's active-handler join can retain this handler. The supplied tests use nil-DB fakes and do not cover this path.

Bound selected-path admission to the existing mutation critical section without leaving a detached waiting worker, and check the selected context before changing fake state after acquisition. Preserve ordinary fake policy and caller-independent selected work. Add a focused contention/cancellation check and real SQL-lock evidence for the stand. Do not fix this by increasing timeouts or treating the expired selected operation as remotely successful.
