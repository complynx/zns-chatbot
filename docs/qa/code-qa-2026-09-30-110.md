## Findings

1. **P2 — do not shorten an authoritative retry deadline.** `platform/internal/bot/inbox_retry.go:114-115` truncates every structured `retry_after >= 3600` to one hour; `:74` also truncates a `ControlError.NotBefore` deadline. A live-parent handler returning `&telegram.APIError{Code: 429, Parameters: telegram.ResponseParameters{RetryAfter: 7200}}` deterministically yields a one-hour inbox delay, and `deferInboxRow` persists that shorter deadline. The row can therefore be dispatched again an hour before the requested cooldown ends, including after restart. The existing unit cases explicitly expect truncation, so they do not prove the requirement that structured retry_after is honored. Preserve valid server deadlines; reuse the shared deadline policy or park unrepresentable deadlines instead of shortening them. Shared `delivery.Deadline` already explicitly rejects shortening. **Limit:** this is a demonstrated source-level scheduling violation, not proof of an early production wire request: a configured durable Telegram control scope can independently prevent the eventual request. That downstream protection does not preserve the inbox's promised deadline and is absent for the raw typed APIError path this implementation explicitly supports.

2. **P2 — specify the rollback restriction for retained quarantined rows.** `platform/internal/store/migrations/087_telegram_inbox_retries.sql:1-5` introduces terminal quarantine in an additive schema but supplies no old-reader transition/rollback restriction. The exact pre-change reader (`opus-r47-inbox-implementation-20260930.before.inbox.go:58`) selects every inbox row without a state/deadline filter. Reproduction path: quarantine a valid handler-failing update under the new runtime, stop it, and start the prior binary against the additive schema; its first drain dispatches that quarantined payload again and also disregards pending cooldowns. A malformed quarantined head instead reintroduces the global drain blockage. `docs/telegram-inbox.md` still describes the old global sequential behavior and gives no handling procedure for this transition. Document a stopped-writer upgrade and a supported rollback route that retains payloads and prevents the old reader from consuming quarantined/cooling rows; explicitly forbid a plain binary rollback once these states exist. **Limit:** this is a source-demonstrated compatibility hazard plus missing required operational contract, not an assertion that a deployment rollback was attempted. No destructive schema rollback is recommended.

## Other review observations

- Whole-batch persistence and received-cursor acknowledgement remain in one transaction; completed-row deletion and processed-cursor advancement remain atomic.
- Authoritative row ID is checked before dispatch; malformed and mismatched payloads retain the original JSON with fixed database diagnostics.
- Pending chat-head selection preserves same-chat FIFO while permitting unrelated due rows; null chat keys do not serialize unrelated unsupported updates. Five recorded failures terminate automatic handler retries. Restart leases are not recorded as handler failures.
- The reviewed classifier prioritizes recognized SQL provenance, parent cancellation, and credit configuration before poison accounting. Failure-transition SQL errors propagate; unavailable storage does not successfully increment the counter. Credit binding now sanitizes its database-operation failures.
- Migration casts are guarded by JSON type and numeric range checks. Runtime UPDATE grants and additive pending defaults are present. No new dependency or suppression appears in the reviewed diff.
- R48 source tests meaningfully exercise real runtime batch durability, unrelated-chat reply visibility, retained same-chat ordering, restart cooldown, and fatal SQL recovery with saved winner reuse. Internal tests additionally cover exhaustion, malformed/mismatched rows, inaccessible storage, service deferrals, and unsafe chat-key inputs. These are source observations, not test-pass claims.
- Domain handlers, receipts, authorization and outbound uncertainty mechanisms are not replaced by the retry scheduler.
