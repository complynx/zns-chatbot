## Findings

### P1 — Identity cancellation still discards an independent SQL failure

Changed call site: `platform/internal/bot/pass_menu_reconcile.go:25-28` (same pattern in the other reconciliation loops). Dependency: `platform/internal/appclient/client.go:160-172`.

`NotificationContext` calls `AuthenticateTelegram`, which passes a failed Links lookup through `clientBoundaryError`. That boundary returns `ctx.Err()` before checking SQL provenance. If the lookup produces a concrete SQL error or `core.ErrDatabase` and shutdown occurs before the boundary handles it, reconciliation receives only cancellation. The new `reconcileDatabaseFailure` cannot recover the lost provenance; it logs a warning and continues, and runtime cancellation can return success. This violates the explicit requirement that cancellation must not hide independent SQL failure.

Source evidence is especially direct: `platform/internal/appclient/cancellation_internal_test.go:103-115` supplies a marked SQL failure, cancels the context, and explicitly expects the marker to disappear. This existing test demonstrates the dependency behavior; it was read, not executed. Preserve positive SQL classification before consulting ambient context cancellation, while leaving plain cancellation nonfatal. Add an identity lookup race check in addition to the supplied inbox SQL cancellation check.

### P1 — Render-time SQL errors still reach the classifier without provenance

Changed call sites: `platform/internal/bot/profile_reconcile.go:74-78` and `platform/internal/bot/media_reconcile.go:43-47`. Dependencies: `platform/internal/bot/profile.go:188-191`, `platform/internal/bot/media_intake.go:68-71`, and `platform/internal/bot/orders.go:219-222`.

The reconciliation loops now stop only when `core.IsDatabaseFailure` recognizes the returned error. These called render/read functions still return SQL Scan errors unchanged. A broken existing connection can return EOF/network-read errors, and a Scan conversion can return an ordinary conversion error; neither is a PgError/ConnectError or marked ErrDatabase. Consequently a known SQL-origin failure is treated as a provider/domain warning, despite the newly wrapped initial enumeration query succeeding. The media case is particularly direct: `reconcileMediaView` calls `loadMediaUploadState`, forwards its raw SQL Scan error, and the outer loop swallows it. Mark the errors at these actual SQL boundaries (preserving expected ErrNoRows/cancellation), not at the mixed render boundary where generic provider EOF must remain nonfatal.

The new faulted pool tests fail the first enumeration/cleanup statement, so they do not exercise this later render-read path. The helper test explicitly establishes generic EOF as non-database, which is correct only if SQL callers first mark its origin.
