## Finding

**[P2] Do not let non-provider JSON encodings consume the one-shot hold.** `qa.local/go-resume-20260929/r104-delayed-provider/rev4/final/delayed_edit.py:179–205` decodes request bytes with Python `json.loads(body)`. Its bytes decoder accepts UTF-16/UTF-32 (including BOM encodings), and its default JSON parser accepts nonstandard NaN/Infinity constants. A UTF-16 encoding of `{"chat_id":101,"message_id":7,"text":"replacement"}` therefore becomes eligible and consumes a matching before_apply arm, while the unchanged Go fake's JSON decoder rejects those wire bytes. A UTF-8 body containing the same fields and `"message_thread_id":NaN` has the same mismatch. `platform/internal/sandbox/fake.go` calls `api.Decode` before resolving or editing; `platform/internal/api/api.go:36–48` uses Go encoding/json, which does not interpret UTF-16 JSON or accept NaN constants.

With before_apply, these malformed provider requests are held for release/expiry instead of immediately reaching the fake and returning its actual rejection. They also prevent the subsequent legitimate matching edit from becoming the selected one-shot request. On expiry, the malformed request never reaches the fake. This conflicts with the requested malformed-input pass-through and makes held:true unsuitable evidence that a valid known-ID provider edit was accepted. This is a source-derived finding, not an executed reproduction.

Keep the original body for forwarding, but make hold selection require provider-compatible JSON wire syntax (UTF-8 without a UTF-16/32 or UTF-8 BOM, and rejected nonstandard JSON constants); decoding/eligibility failure should bypass selection and forward unchanged. Add focused cases with the armed IDs/text for UTF-16/32 and NaN/Infinity, asserting unchanged bytes, actual rejection status/body, no held/forward_started selection, and an arm still available for the subsequent legitimate edit. Do not return a locally fabricated provider rejection or port the fake's destination/business policy into the proxy.
