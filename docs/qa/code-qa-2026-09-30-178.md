## Findings

1. **[P2] Validate journal metadata before storing request fields.** `qa.local/go-resume-20260929/r104-delayed-provider/delayed_edit.py:95-108` parses JSON but copies `chat_id` and `message_id` into the persistent journal without validating their type or size. For example, a token-authorized sendMessage with an object/string in chat_id stores that entire value before the fake rejects the request. That value can contain private text or a secret and can approach the 20 MiB body bound. A 512-event count is therefore neither a small metadata bound nor a no-payload guarantee; `/control/state` also copies/serializes those values. Validate the expected JSON object and bounded scalar ID fields before logging, and never journal raw invalid values. Keep invalid-input evidence to fixed reason codes and hashes. Validate response IDs before placing them in held_outcome as well.

2. **[P2] Bound incoming connection lifetime and admission independently of the container kill limits.** `delayed_edit.py:82-88,184-187` reads the declared body before route authorization, with no socket/read deadline, and uses an unrestricted ThreadingHTTPServer. A client declaring a body and then stalling retains its handler indefinitely; several concurrent allowed 20 MiB bodies can exhaust the 128 MiB container before parsing and serialization finish. The 600-second event wait does not bound these paths. `pids_limit: 64` limits eventual failure, but provides no bounded overload rejection or reserved ability to release/inspect the held edit. Add bounded connection/read/write handling and bounded request admission/body budgets, protecting operator controls from stalled ordinary requests. Keep the intentional post-body hold independent of app disconnect. Send control error responses outside stand.lock (currently lines 170 and 179), so network I/O never owns the shared state lock.

3. **[P2] Stop reporting the before-application barrier once release is accepted.** `delayed_edit.py:109-116,142-143,174-177` sets the release event without changing state or recording release. The handler then forwards while `/control/state` continues to report `held_before_apply` and the journal still has no upstream_response. This is exactly the runbook's purported NOT-sent barrier even though the upstream request is in flight or has already applied but its response has not arrived. If forward raises, the exception path leaves that stale state permanently. Transition atomically out of the held state on release, record bounded release/forward-start evidence, and move held failures to an explicit invalidated/unresolved state. Preserve the distinction between released, forwarded and known successful; do not infer a remote outcome from a local exception. Test the state while upstream is stalled after accepting the request and after an upstream error.
