## Findings

1. **P1 — Host admission does not bind a legitimate ingress or its historical generation.** `platform/internal/botdelivery/admin_page_results.go:53-73` reads the *current* conversation generation, authorizes only the admin-message source and owner/chat, and then persists the caller-supplied `Update`. The initial reference does not even contain `in.Update`; neither this method nor `lockSource` checks an ingress record or its actor/chat/page binding. `validateAdminPageResults` at line 158 only checks that Update is nonnegative. Thus a caller possessing the route's required credentials can submit an absent update, another actor's update, or an old pre-deletion update with an otherwise authorized original-source message. When no intent exists for that operation, lines 128-135 create a fresh manifest using today's generation, so the generation fence cannot reject that stale ingress. The bot-context check at `platform/internal/bot/admin_message_page.go:95-101` does not establish authority at the separately callable Host persistence boundary. Bind and lock an authenticated durable ingress/operation record (including bot, owner, chat, page ID/offset and its original generation) before first manifest creation; reject mismatches, missing ingress, and deletion-terminal/stale ingress. Preserve manifest replay after the inbox has been acknowledged through durable proof rather than trusting a raw ID. Add Host-boundary negative tests; current persistence tests use synthetic Update IDs without registering ingress and therefore do not prove this requirement.

2. **P2 — Canonical effect names still permit arbitrary keyboards and repeated navigation.** `platform/internal/botdelivery/admin_page_results.go:167-183` validates effect names, chat, parse mode, message ID and text size, but only forbids keyboards on page chunks. A valid `admin_page:<id>:<offset>` final effect can carry a URL/WebApp, callbacks to unrelated operations or IDs, unlimited rows, or callback data beyond Telegram's limit. Every following `admin_view:<id>:<n>` may also carry its own navigation/actions, including intermediate chunks. `telegram.PrepareSend` (`platform/internal/telegram/format.go:38-43`) validates text only. For example, a one-effect request with the correct final name, text `page`, and a button whose Data is 65 bytes passes this validator but is rejected by Telegram; a two-view request can put action keyboards on both view chunks and also passes. This violates the narrow canonical-effect endpoint and one-final-navigation contract even though the normal bot renderer currently constructs acceptable payloads. Validate bounded keyboard structure and canonical page/inspect/action callbacks bound to this ID/offset; forbid URL/WebApp and keyboards on intermediate view chunks; validate callback byte lengths and reject multiple action/navigation cards.
