## Findings

### P1 — A changed view loses the distinct old fallback target and its callback retirement

Location: `platform/internal/botdelivery/pass_receipt_retirement.go:57-72`; dependency `platform/internal/bot/delivery_intents.go:85-88`.

A successful fallback send creates message B after an attempted edit of existing private card A. The fallback transition clears `target_message_id`; retirement obtains A only through an UPDATE of the *current* pass_views row matching the original revision, source and chat. If a newer manual/menu revision replaces that binding while the provider send is in flight, original-source revocation still yields PassMenuDenied, but this UPDATE returns no row. Retirement registers B only and marks the parent's continuation complete. A receives no cleanup effect. Deleting original-revision callbacks is also conditional on that UPDATE succeeding, so those rows survive the same race.

This violates the requirement to atomically cover the exact observed receipt target and distinct old target despite view changes. Retain the originally admitted edit target as immutable provenance across fallback, independently of the current view binding. Register both known targets and delete the revoked revision's callbacks in the continuation transaction while preserving a newer view. Add a positive fallback receipt race with a newer view and original-source denial; assert cleanup cardinality for both A and B and deletion of old callbacks.

### P1 — A view change can hide the capability required by the successfully sent private payload

Location: `platform/internal/botdelivery/family_authority.go:177-202`; `platform/internal/botdelivery/receipts.go:40-48,75-79`.

Receipt authority is reconstructed from the current pass_views state. `lockPassMenu` requests proof_accept only when that current state says payment_queue (similarly admin_assign/takeover for their views). Neither the immutable reference nor the persisted rendered continuation identifies the capability required by the payload actually sent. If a payment_queue card is successfully sent, then pass_views changes to events with the same revision/source and proof_accept is revoked before receipt application, the current events state requires no capability. When the original derivation's own authorities remain valid, ApplyReceipt projects the successful private receipt and completes it without retirement. The private queue content/buttons remain visible. Keeping the revision but changing view is allowed by StorePassMenu and by render fallback; the added grant test itself demonstrates a home-source menu subsequently rendered as payment_queue.

Bind the successful rendered menu's required capability/event to canonical admission/receipt provenance, and recheck that immutable requirement before receipt projection. Harmless stale view changes must remain distinct from that definitive denial. Add the combined capability-revocation + changed-view receipt race, alongside its unchanged-authority positive control. Existing tests cover these two dimensions separately.
