## Finding

### [P2] Reject null or incomplete captured inline buttons before admission

Location: `platform/internal/notificationwire/types.go:31-35`.
Related path: `platform/internal/bot/notifications.go:46-50`; all four domains call the shared payload validator before BeginNotificationSend.

`Encode` treats successful `json.Unmarshal` into `telegram.Markup` as sufficient validation. That transport type consists of ordinary slices and structs with no keyboard validator. Consequently a captured payload such as `{"text":"Synthetic notification","markup":{"inline_keyboard":[[null]]}}` or `{"text":"Synthetic notification","markup":{"inline_keyboard":[[{}]]}}` passes `Decode`/`Encode`: Go unmarshals the null/empty button as a zero-value Button. The admitted wire is then reserialized as a button with empty text and no action, and PrepareSend validates text only.

Trigger: after an actual unknown send, stored inline markup is corrupted into a null or incomplete button while remaining valid JSON and type-decodable. On eligibility the projection and admission validator accept it, BeginNotificationSend commits `sending` and increments `uncertain_resends`, and the adapter contacts the provider with the invalid keyboard. Null button members are also normalized into different wire content. This violates the required visible pre-admission failure with no provider call, no resend charge and no guessed captured content. The existing corrupt-keyboard test covers a string in place of the keyboard, but not null/incomplete elements.

Fix: validate the decoded keyboard before returning success, including non-null rows/buttons, valid nonempty button text and a valid supported action. Reject malformed stored button fields instead of allowing struct zero values or omission to silently repair them. Keep valid empty keyboards supported. Add focused shared-payload cases and one integration case proving that a corrupted captured button does not reach BeginNotificationSend or transport.
