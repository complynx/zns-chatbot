## Finding

### P2 — Admission still misclassifies live-driver cancellation as caller cancellation

Location: `platform/internal/botdelivery/admission.go:373-377` (`lockPayloadActors`), with the same incomplete conversion in affected admission SQL boundaries at lines 184, 226, 264 and 266, and view/target checks in `family_authority.go:250` and `334`.

The new `lockPayloadActors` SQL read returns `core.DatabaseOperationError(err)`. That helper returns `context.Canceled` or `context.DeadlineExceeded` without consulting the caller context (`platform/internal/core/database_error.go:22-27`). Consequently, when this read fails with a driver-local cancellation while `ctx.Err() == nil`, admission/receipt authority returns a cancellation rather than `core.ErrDatabase`. This directly violates the requested distinction between caller cancellation and a live-driver database failure.

The consequence reaches the delivery error boundary. `botPreparationFailure` recognizes database errors before changing queue state, but this error fails that test; with a live caller it reaches the retry/postponement path instead (`platform/internal/bot/delivery_worker.go:109-146`). In receipt continuation, it can instead be returned as cancellation (`delivery_worker.go:207-208`). The receipt SQL/read tests added here exercise the corrected boundaries, but do not cover the new actor helper or remaining admission/view/target boundaries.

Use the context-aware SQL classifier at these affected boundaries, preserving explicitly handled absence first. Add focused fault tests for live cancellation/deadline, matching caller cancellation, and a positive PostgreSQL error accompanied by caller cancellation. This is one error-provenance finding, not a request for unrelated global error handling changes.
