**Verdict: changes requested.** The worker stop/join, ownership ordering and receipt durability look correct. One confirmed medium defect breaks the explicit AUD23 rule against blanket-classifying JSON errors. There are also two low-severity confirmed issues and some weak tests.

## Confirmed defects

**D1 (medium) — Corrupt stored JSON is reported as a database failure and stops the runtime.**
- **Where:**
  - `platform/internal/bot/inbox.go:57-62`: `Scan(&update)` into `telegram.Update`, then `inboxDatabaseError`.
  - `platform/internal/botdelivery/family_authority.go:83-85` (`readPassMenuFamily`, `Scan(&menu PassMenu)`) and `:241-243` (`lockViewBinding`, `Scan(&current PassMenu)`).
  - `platform/internal/botdelivery/results.go:185-187`: `Scan(&stored StoredResult)`.
- **Mechanism:** When pgx scans a json/jsonb column into a Go struct, it runs `json.Unmarshal` inside `Scan`. A decode failure comes back as an ordinary scan error. `core.DatabaseOperationError` (`core/database_error.go:21-38`) only spares NoRows, cancellation and serialization errors, so the decode error becomes `core.ErrDatabase`.
- **Consequence:** `runPolling` (`bot.go:627-629`) or the delivery worker (`delivery_lifecycle.go:27-29`) then stops the runtime.
  - **Poison update:** a bad `telegram_inbox` payload always sorts first, so every fresh runtime stops again with a misleading "database unavailable".
  - **`storeBotResult`:** it uses `ON CONFLICT DO NOTHING` and then reads back whatever row already exists, so an older incompatible `bot.interactions` content row triggers the same failure.
- **Inconsistency:** `botdelivery.Read` (`read.go:51-55`) deliberately keeps JSON errors unclassified, and `TestReadJSONErrorsKeepTheirProvenance` checks that. The other scan sites don't follow the same rule.
- **Fix direction:** scan into `[]byte`, mark only the SQL error, then unmarshal separately.

**D2 (low) — A cancelled receipt continuation is treated as a provider failure and gets postponed.**
- **Where:** `platform/internal/bot/delivery_worker.go:186-203`.
- **Mechanism:** Any error that isn't a database failure, including `context.Canceled` during normal shutdown, runs an uncancellable UPDATE (`deliveryCompletionContext`) that pushes `not_before` forward by `Delivery.Fallback`.
- **Paths affected:** a cancelled `ContinueBotIntentReceipts` iteration (`:173`) and `DeliverBotIntent` with a `Succeeded` intent (`:31-32`).
- **Effect:** no receipt is lost, but continuation on the next runtime is delayed by `Fallback`. Shutdown also does up to 5s of extra database work before ownership is released. The comment at `:193-194` says only identity/application unavailability should cause this.
- **Fix direction:** return early when `ctx.Err() != nil` or the error is a cancellation.

**D3 (low, complexity) — Dead branch and a no-op wrapper.**
- `bot.go:653-655`: the `core.IsDatabaseFailure` check in `handlePollError` can never run, because `runPolling:627-629` already returned for that case.
- `inbox.go:98-100`: `inboxDatabaseError(_ context.Context, …)` only forwards to `core.DatabaseOperationError` and ignores its context. Its test name, `TestBackgroundDatabaseInboxResultAfterCancellation`, suggests cancellation behaviour the function doesn't have.

## Verified correct
- **Stop/join before ownership release:** in `Run` (`bot.go:582-618`) the deferred calls run in this order: `finishBotDelivery` (stops and joins the worker, then reads the fatal result), `unlock`, `conn.Release`, `creditCutoverRunResult`, `cancel`.
  - The worker is joined before the advisory lock is released.
  - A fatal worker result is read only after the join (`delivery_lifecycle.go:46-54`).
  - The fatal handler sends without blocking into a 1-slot buffer and cancels the runtime.
- **Cancellation doesn't erase a known SQL failure:**
  - `runPolling` checks for database failure before `ctx.Err()`.
  - `creditCutoverRunResult:63` keeps database failures even after cancellation.
  - `botPreparationFailure:109-111` classifies before its `ctx.Err()` check.
  - `dispatchDeliveryPass:41-45` stops the pass before later healthy heads and keeps provider failures alongside.
- **Receipts and duplicate effects:**
  - If Telegram succeeded but `finishBotIntent` then fails in the database, the transaction rolls back and the intent stays `Sending`.
  - `RecoverBotIntents` then marks it `unknown` (Uncertain) rather than resending.
  - Admission failures in `beginAttempt` cause no Telegram call and no postponement.
  - `DeliverBotIntent:64` persists the outcome with an uncancellable completion context derived from `live`.
- **Privacy:** worker, poll and dispatch paths replace database errors with the bare `core.ErrDatabase` before logging or returning, so driver text isn't exposed. The warning logs only carry errors that aren't database failures.
- **Marking stays at SQL call sites:** marks sit only on direct Exec/QueryRow/Begin/Commit. Helper, provider and JSON-marshal errors pass through unchanged (except D1). NoRows handling and `familyMissing` are preserved.

## Hypotheses (not proven)
- **H1 — Serialization conflicts and deadlocks now stop the runtime.** `ErrDatabaseSerialization` counts as `ErrDatabase`, and deadlocks (SQLSTATE 40P01) become `ErrDatabase`. So a transient deadlock between ingress and the worker, which used to be retried on the next pass, now restarts the runtime. Deterministic per-row SQL errors (data or integrity exceptions) would stop it on every restart. I couldn't read the caller's restart behaviour (`platform/cmd/bot/main.go` doesn't exist).
- **H2 — Shutdown could be misreported as a database failure.** If the pool uses pgx's cancel-request handling for contexts, a server-side "query cancelled" error (SQLSTATE 57014) may not wrap `context.Canceled`. Normal shutdown would then report `ErrDatabase` and trigger the worker's fatal path. I didn't check the pool configuration.
- **H3 — Non-AUD23 changes in scoped files are unverified.**
  - Refund authority: `admission.go:116-122,155-163` and `family_authority.go:115-116,285-302`.
  - Pass-redaction exact-reference and edit-only checks: `family_authority.go:93-103,168`.
  - `interaction.ErrInvalidSavedTurn` now counts as terminal: `delivery_worker.go:124`.

  If the pass-redaction producer sets `Language` or `Generation`, every redaction would be rejected as stale and cancelled. If `ErrInvalidSavedTurn` also wraps old-format decode errors, those intents would be cancelled permanently. I couldn't find the producer or the `interaction` definition.
- **H4 — Postponing `not_before` on `sent` rows could slow other chats.** This happens only if some rate-limiting code reads `bot.delivery_intents.not_before` for sent rows. I found no evidence of that.
