## Findings

### P1 — Preserve SQL provenance in every delivery recovery/read/postponement boundary

Location: `platform/internal/bot/delivery_dispatch.go:135-138,141-147`; producers in `delivery_intents.go:119-156,162-194`, `delivery_worker.go:27-29,72-74,159-171`, and dependency `platform/internal/botdelivery/read.go:35-36`.

The new worker termination path depends on `core.IsDatabaseFailure`, which intentionally does not classify generic transport errors such as `io.EOF`. Several functions feeding this path still return those errors directly from SQL. For example, `RecoverBotIntents` returns raw errors from Begin, row Scan, UPDATE, and Commit; `postponeBotIntent` does likewise. `botdelivery.Read` returns its SQL Scan error unchanged and also returns JSON decoding errors, so its result is a mixed boundary.

A connection closing during a recovery SELECT or receipt-lock SELECT can therefore return `io.EOF`/a generic connection-closed error. The worker logs it as recovery/pass pending and continues instead of reporting `ErrDatabase` and cancelling ingress. This does not require the separate advisory-lock connection to fail. The receipt persistence test covers begin, update, and commit, but not the intervening `botdelivery.Read` SQL operation, so that test does not close this gap.

Fix: mark and sanitize errors at the actual SQL statements in these producers (including inside `botdelivery.Read` before its JSON decode). Preserve absence, cancellation, decoding, and domain errors distinctly; do not blanket-convert the mixed helper result. Add focused fault coverage for an uncovered recovery SQL statement and the receipt-lock read, proving worker termination and preservation of durable intent state.

### P1 — Joined cancellation still masks raw PostgreSQL failures in delivery dispatch

Location: `platform/internal/bot/delivery_dispatch.go:141-147`, with aggregation at `:25-34,48-52` and dependency `platform/internal/core/database_error.go:62-69`.

`dispatchDeliveryPass` accumulates dispatch failures and appends cancellation when shutdown starts. The new consumer calls `IsDatabaseFailure` on that joined error. The classifier checks for `context.Canceled`/`DeadlineExceeded` before looking for `*pgconn.PgError` or `*pgconn.ConnectError`, and returns false. Thus `errors.Join(&pgconn.PgError{Code: "08006"}, context.Canceled)` is treated as non-database even though it contains an independent SQL failure.

This is reachable through the still-raw `botdelivery.Read` or `postponeBotIntent` errors: an owner attempt returns a PostgreSQL failure, cancellation occurs before the next dispatch-loop iteration, and the join retains both errors. `dispatchQueuedDeliveries` then returns nil (and suppresses its warning because the context is cancelled); the worker emits no fatal result and `Run` can finish successfully. The added dispatcher test uses already-normalized `core.ErrDatabase`, whose early classifier branch bypasses the bug, rather than a concrete raw PostgreSQL error.

Fix: normalize each observed SQL failure before aggregation, or make the classifier preserve a concrete SQL failure in a separate joined-error branch while still treating a cancellation-only SQL operation as ordinary cancellation. Cover a raw PostgreSQL failure joined with cancellation in the dispatcher and verify a safe fatal result reaches finalization.

## Positive observations and limits

- `Run` defers delivery stop/join after lock acquisition, so it executes before advisory unlock and connection release. `finishBotDelivery` joins before reading the fatal channel, including failures from bounded receipt completion after cancellation.
- Inbox statement wrappers use SQL origin rather than ambient context state. The poll path checks database failure before its cancellation exit.
- Completion uses `context.WithoutCancel` with a timeout and retains authenticated context values. Continuation re-resolves the recipient before applying non-identity receipts, and the new retry scheduling UPDATE is guarded by state, attempt, message ID, and completion flag.
- The supplied tests cover fatal callback propagation, provider errors remaining nonfatal, completion joining, direct SQL transport errors at selected boundaries, background admission failure recovery, and ordered inbox SQL failure followed by cancellation. They were inspected, not executed.
- Existing raw-error startup/view-reconciliation paths were observed while tracing dependencies; this review does not certify that every database boundary throughout the repository has been migrated. No functional or runtime acceptance is claimed.
