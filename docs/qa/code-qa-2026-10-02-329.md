## Findings

### P2 — Confirmed negative replay can reapply shared pacing after preflight changes the owner failure

Primary location: `platform/internal/orders/notification_delivery.go:169-177`. Equivalent guards: `platform/internal/passbooking/notification_delivery.go:254-262`, `platform/internal/legacyfood/notification_delivery.go:211-219`, and `platform/internal/massage/notification_delivery.go:223-231`.

The replay guard requires the mutable owner failure to equal the provider reason even when `last_confirmed_attempt` already equals the incoming generation. The same generation can legitimately survive later preparation once its three additional sends are consumed: `platform/internal/orders/queries/notification_delivery.sql:25-28` explicitly increments it by zero. The adapter performs `NotificationContext` before Begin (`platform/internal/bot/notifications.go:167-170`), and an ordinary identity-provider EOF becomes a valid preflight Deferred completion for that same generation (`:108-116`, `:128-142`). The pending-state outcome rules accept it, and Finish writes `notification_preflight_unavailable` into the owner failure and releases the preparation lease.

A finite source-derived counterexample is:

1. An initial uncertain send is followed by three actual 429 sends. The last actual generation G has `last_confirmed_attempt=G`, `uncertain_resends=3`, pending state, and failure `telegram_rate_limit`.
2. After the final provider cooldown, Prepare retains G. The identity lookup fails with an ordinary provider EOF. The adapter completes a preflight deferral, changing failure to `notification_preflight_unavailable` without another send.
3. Replay the original canonical 429 receipt for G, with exactly its original reason and retry_after. The equality guard fails solely because the owner failure changed. `notificationOutcomeAllowed` still accepts Deferred from pending (`orders/notification_delivery.go:242-253`). The handler calls Finish, which reaches `delivery.Schedule` and recomputes the cooldown from the replay time (`platform/internal/delivery/pacing.go:93-135`). It changes failure back, clears any lease, projects the queue and extends both bot and chat pacing. No new provider call occurred.

This is not inert and does not return a typed conflict. It can delay the exhausted owner, its follower, and unrelated bot traffic using a receipt already recorded as confirmed. The original requirement says repeated canonical negative receipts must leave owner, queue, pacing, deadlines and followers unchanged across preparation/recovery/generations. Fence confirmed provider completion by generation independently of mutable preflight/policy fields; preserve permitted preflight handling separately. Add a focused assertion for a final canonical 429 replay after an actual adapter preflight failure, checking complete owner/queue/pacing snapshots.

Existing final-429 replay tests at `platform/integration/notification_uncertain_retry_test.go:892-910` and `:1035-1048` preserve the failure reason between the original response and replay. They do not falsify this transition.

### P2 — Late success revives recovered pending work after current rights or source revocation

Primary location: `platform/internal/orders/notification_delivery.go:182-190`, with the insufficient late-success predicate at `:217-220`. Equivalent paths: `platform/internal/passbooking/notification_delivery.go:267-275` / `:302-305`, `platform/internal/legacyfood/notification_delivery.go:224-232` / `:259-262`, and `platform/internal/massage/notification_delivery.go:236-244` / `:271-274`.

Complete locks only the exact notification attempt. It neither locks nor observes the current recipient/source authority before accepting a late positive for a recovered pending generation. `notificationLateSuccess` checks pending state, absent lease, matching uncertainty generation and no confirmation, but no current eligibility. `finishLateNotificationSuccess` calls `delivery.FinishUncertainSuccess`, then writes state `sent`, positive receipt/text, a new lease and `followup_pending=true` through `FinishNotificationDelivery` (`platform/internal/orders/queries/notification_delivery.sql:43-58`).

A source-derived counterexample needs no forged receipt: hold a genuine provider success while its admitted send lease expires; recovery observes the still-current source and changes that generation to pending with no lease; revoke `core.users.can_book` (or the applicable domain source/reviewer permission); then release the genuine success response before another Prepare/Begin/recovery cancellation. The old generation still passes every late-success predicate. Complete changes the revoked owner's pending delivery to sent and creates follow-up work. The terminal metadata-only branch cannot help because no maintenance invocation has yet materialized cancellation in the owner state.

The original requirement explicitly includes source-revoked owners among those that may accept only metadata for their actual attempt without revival, and requires current rights/source validity at send boundaries. The late completion currently depends on an unrelated future maintenance call to enforce that policy. Revalidate authority for recovered late completion using the established authority-before-owner lock order, and retain only permitted receipt metadata if current eligibility is lost. Add a focused genuine held-success/recovery/revocation/release case. This finding concerns durable state and follow-up revival; it does not assert that later adapter permission checks leak private history.

The existing terminal receipt test at `platform/integration/notification_uncertain_retry_test.go:695-758` revokes rights before a recovery call that already sets cancelled. It does not exercise revocation after recovery but before the late positive response.
