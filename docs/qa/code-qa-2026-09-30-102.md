## What the diffs change
1. **The restarted bot now keeps its full configuration** (knowledge diff lines 17–31 and 56–64; saved-knowledge diff line 17). The old code rebuilt the bot with only `DB`, `API`, `Host`, `TG` and `Model`. `setup()` (`platform_test.go:274-276`) also sets `Delivery: syntheticDeliverySettings()`, and the rebuild dropped it. So the "restarted" bot ran with empty delivery settings. The new `restarted := *f.b; restarted.Model = …` keeps `Delivery` and all other fields, and only swaps the model.
   - This is safe. `bot.Bot` (`bot.go:35-55`) contains no mutex and no in-process state that could leak between runs. The pointer fields (`BrowserAuth`, `Lineup`, `Host.Local*`) are nil in `setup`. `Host.UserToken` looks up `result.b` when called, so it follows the new `f.b`.
   - An existing test already uses the same pattern (`pass_menu_test.go:169`).
   - The unused `bot` import is removed. No new dependencies, no lint suppressions, and fewer lines overall.
2. **Delivery is now actually drained in the knowledge tests.** `handle` becomes `handlePassVisible` (`knowledge_authorization_test.go:357,359,404`), and `drainPassNotices` is added after `Render` (`:400`). Before this, the absence checks in `assertKnowledgeAnswerAbsent` (`:310-315`) could pass simply because nothing had been delivered to the chat yet. Now they look at delivered cards.
3. **The existing assertions are not weakened:**
   - The recovery model still requires `Reads[0].Proposals`, i.e. authorized private context survives the outage (`:349-353`).
   - The model is called exactly once across two retries (`:358,360`).
   - Quota rows are compared exactly, row by row (`:361`).
   - The saved turn is `Ready`, with no `SystemNotice` and the expected text (`:364-366`).
   - Revocation: zero model calls (`:398`), quota unchanged (`:402`), and a fresh request adds exactly one quota row (`:406`).
   - Saved knowledge: one domain effect, one operation row, no model inputs and no assessments (`saved_knowledge…:143-151`).

## Findings
**F1 (Medium, coverage gap against "actual durable delivery").** In `saved_knowledge_attachment_recovery_test.go`, the success branch (`:125-141`) calls `f.b.Handle` directly and only checks `memory_sources` rows. Nothing asserts that:
- the `knowledge_reply` row is written after the attachment finally succeeds (the only reply check is `assertSavedKnowledgeReady`, which requires *zero* replies before completion, `:173`), or
- the reply reaches the chat (`chatMessages` is never used; no pump or drain).

The diff keeps `Delivery` on the restarted bot, but this test never exercises it. A regression that completes the sources but loses or never queues the user-facing reply would still pass. The `source_revoked` and `history_deleted` branches (`:110-119`) likewise don't check what the user sees.

**F2 (Low, exactly-once check is incomplete).** After the successful call (`:130`) and the replay (`:140`), `transport.attachments` is not checked; you'd expect it to stay at 3. The link count stays at 1 either way (`:141`), so an extra attach request on replay would go unnoticed. The "exactly once" guarantee is enforced only at the database row, not at the HTTP effect.

**F3 (Low, a negative check only).** In `assertProviderRevocation` (`:395-401`), the terminal notice for the revoked turn (`deliverPassTerminalNotice`, `bot.go:147-151`) is never positively checked as delivered. Only the absence of private text is checked. The later fresh `handlePassVisible` plus the `Contains` at `:409` shows that delivery works at all. I assume, without having confirmed it in the helper code, that messages to one chat are delivered in order (`delivery_queue_test.go:90`), so earlier items would be flushed first. If so, the final absence check at `:410` is meaningful.

**F4 (Low, weak error check).** `require.Error` at `saved_knowledge…:121` accepts any error. The `attachments == 1` check at `:122` stops the obvious bypass through the failing attachment path. Still, an unrelated early failure would pass as "permission checked". Asserting the specific error code would close that.

**Hypotheses (not verified):**
- If `handlePassVisible` or `drainPassNotices` only pump pass-domain notices and not bot cards, the absence checks in the knowledge tests would again pass without anything being delivered. I couldn't read their definitions. The positive `Contains` checks at `:369` and `:409` suggest bot cards do get delivered.
- The model callbacks call `require` from inside the model. That is only acceptable if `Handle` calls the model on the test goroutine. This code existed before the diff and I didn't confirm it.

## Verdict
No blocking defects in the scoped diffs. The restart configuration and the durable-delivery drain are correct improvements, and none of the privacy, access-control, quota or no-duplicate assertions are weakened. F1 is a real gap: the saved-knowledge recovery path doesn't show that the reply is durably delivered. I recommend closing F1 and F2 before this stage is accepted.
