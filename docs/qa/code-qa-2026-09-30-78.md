## What checks out

**Correctness and security**
- Both branches now return `core.DatabaseOperationError(err)`. For a Begin failure, that function returns only fixed values:
  - `context.Canceled` or `context.DeadlineExceeded` if the error wraps them (so cancellation still behaves as before);
  - `ErrDatabaseSerialization` for SQLSTATE 40001;
  - otherwise the bare `core.ErrDatabase` ("database unavailable") (`core/database_error.go:21-38`).
- The original driver error is dropped, so no driver diagnostics can leak through these two branches. The `pgx.ErrNoRows` passthrough can't happen on Begin.
- Only the Begin errors themselves are marked. Errors from the helper and provider calls around them are unchanged:
  - validation (`invalidSource()`);
  - `CapturePassAdmission`;
  - `ResolveRegistrationIntake`;
  - `lockRegistrationPrelude`;
  - `PrepareInTx` / `PrepareAssignmentInTx`;
  - `commitPrepared`.

**Order and transactions**
- **Order is unchanged.** The diff only changes the two `return` lines. `ExecutePassBooking` still runs source validation → `CapturePassAdmission` → `ResolveRegistrationIntake` → Begin (`registration.go:34-49`). `AssignPass` still runs intake → validation → Begin (`registration.go:70-77`).
- **Transactions are handled correctly.** On a Begin failure the function returns before the `defer tx.Rollback` line (lines 53 and 81), so it never calls Rollback on a nil transaction. Lock order and replay happen after Begin and are not touched.

**Dependencies, complexity and suppressions**
- **Dependencies:** the `core` import added to `registration.go` is already used by the package (`service.go:17`), so there is no new edge or import cycle. The test uses `pgxpool` (already imported in `service.go:14`) and `testify` (already in `go.mod`). Nothing new is added to `go.mod`.
- **Complexity:** minimal. The change is one wrapping call per branch, the same pattern as `passbooking/service.go:59-62` and `passbooking/admission.go:42-45`.
- **Suppressions:** none (no `nolint` or similar).

**The new test**
- It doesn't need a network. `BeforeConnect` returns `io.EOF` before any dial.
- It reaches the Begin branch:
  - With a zero `passbooking.Service`, `Intake` is nil, so intake resolution returns nil (`intake.go:11-16`).
  - The source is valid, because `Generation` is 0 and not nil, and `Authorities` is an empty non-nil slice (`derivation.go:11-13`; `authority.go:43-80` returns true for an empty slice).
- `require.Equal(t, core.ErrDatabase, err)` checks for the exact sentinel, which proves no driver error is wrapped inside.
- The second case checks that `invalid_derivation` is still returned and is not classified as a database failure.

## Findings

### F1 (Low, test gap): the `ExecutePassBooking` Begin branch has no test
- **Where:** `platform/internal/derivedmutation/registration.go:49-52`; the only test is `registration_database_internal_test.go:17-35`.
- **Evidence:** the test only calls `AssignPass` (lines 27 and 30). Nothing in the new test runs the `ExecutePassBooking` branch. I could only use Read, not search, so I can't rule out coverage somewhere else.
- **Why it matters:** if someone reverts line 51 to `return passbooking.Booking{}, err`, no test in this diff will catch it.
- **Fix:** in the same test, add a call like `(Service{DB: db}).ExecutePassBooking(t.Context(), "bob", passbooking.Command{Name: "cancel", Event: "dance"}, source)` and assert `require.Equal(t, core.ErrDatabase, err)`.
  - The command must be one that doesn't start a registration (not `solo` or `invite`). For those, `CapturePassAdmission` returns early (`registration_admission.go:18-20`; `passbooking/admission.go:34`) and the call reaches line 49.
  - With `solo` or `invite`, the call would instead fail at the Begin inside `CapturePassAdmission` (see O1), which proves something different.

### F2 (Informational, optional): no cancellation test for these branches
- Cancellation is kept by `DatabaseOperationError` (`database_error.go:25-30`), but the new test doesn't check it.
- You could add a case with an already-cancelled context and assert `require.ErrorIs(err, context.Canceled)` and `require.False(core.IsDatabaseFailure(err))`.
- Whether `pgxpool` Begin returns the context error in that case depends on the library's internals, which I couldn't read (see Limitations). So this is a suggestion, not a defect.
