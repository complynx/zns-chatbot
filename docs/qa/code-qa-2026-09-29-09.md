## Findings

### F1 — Medium (verified test weakness): the forged-authority test can pass without proving the intended guard ran
`platform/integration/pass_redaction_delivery_test.go:15-47`
- **No positive control.** Every subtest expects an error. There is no unforged case in the same fixture (`pass_views` row inserted by hand at `:19-20`, alice on chat 101) that is shown to succeed and create one intent. If that fixture were broken, all six cases would still pass: for example a missing `core.users` row makes `admission.go:119-121` return a raw `ErrNoRows`, and a bad row or client/transport failure would also produce an error.
- **The error is not identified.** `:41` uses `require.Error`, so any failure counts. The test never checks for `bot_delivery_stale` / `ErrStale`.
- **Some cases don't isolate the new code.**
  - `source`: the forged `Derivation` has `PrivateHistory:false`, while the stored source has `private_history:true` (`derivation.go:6`). It would also be rejected by the old `DeepEqual` rule.
  - `generation` and `authorities`: the old rule rejected any nil-source redaction against a view that has a source, so these fail before and after the change. Only a positive case shows the new behaviour ("redaction allowed without a valid source").
  - `foreign_chat` (`:31-32`): rejected by the `core.users` telegram_id check (`admission.go:123-125`), not by target binding. `EnqueueCard` never checks the target (`cards.go:37-41`); that happens only in `begin` (`admission.go:180-184`).
- **Fix:**
  1. Add a `valid` scenario expecting `NoError` and exactly one intent.
  2. Assert the stale error code for the stale-guard cases.
  3. Build the `source` forgery with `PrivateHistory:true`, so only the new rule can reject it.

### F2 — Low (coverage gap): the requirements about wrong target and missing target are not tested in scope
The scoped tests do not cover:
- editing a forged or foreign target message ID (for example chat 101 with Target 999);
- a revision change between enqueue and delivery;
- "target gone must not become a new send" (`delivery_worker.go:92-93`).

The enqueue-level test can't cover the first one: `EnqueueCard` accepts any Target, and `begin` later replaces it with the rendered one. These guards need tests that go through `pumpBotDeliveries` with an intent already queued. Other tests may cover this; without Grep I could not confirm.

### F3 — Low (hardening, not exploitable as far as I can see): the redaction reference is only partly canonical
`family_authority.go:58-61` limits only `Source`, `Generation` and `Authorities`. A structurally valid `pass_redaction` reference may still carry:
- any `CardKey`;
- `Notice`, `Event`, `Object`, `Version`, `Update`, `ProofAttempt`;
- `Continuation` fields such as `Tokens`, `ViewHash`, `Key` and `Document`.

These are stored in `bot.delivery_intents.reference`. They are never rendered (`delivery_render.go`), and the receipt uses the rendered continuation (`delivery_intents.go:93-111`). However:
- a non-`passes` `CardKey` avoids the pending-receipt serialization check (`admission.go:202-209`) and the enqueue advisory lock (`cards.go:44-47`) shared with `pass_card` intents;
- `Version` is passed to `AdminMessages.DeliveryAuthorities` (`:42`). I did not verify that it returns nothing for this family.

**Fix:** for `pass_redaction`, require `CardKey == familyPasses` and every other field at its zero value. Allow only `Continuation{Kind: pass_redaction, Revision: <the reference revision>}`.

### Nit
`family_authority.go:57` computes `DeepEqual` and then throws it away for redaction. A simple if/else would read more clearly.
