## What holds (verified by reading source)

- **Binding to actor, key, target, attempt and version.** `PaymentCompletionReceipt` calls `PrepareInTx`, which does `authorize()` for `proof_accept`/`proof_reject` against `core.pass_payment_admins … FOR SHARE` (`passbooking/service.go:252-259`). It then looks up the replay row by `(event, actor, key_hash)` and requires `request_hash == hash(json(command))` (`service.go:138-160`). The request hash covers Target, TargetVersion, PaymentAttempt and Key, so changing any of them causes `idempotency_conflict`. A new key gives `Found=false`.
- **Transition proof.** `target.Version == TargetVersion+1` (`payment_completion_receipt.go:39`), and `touch` adds only one version per transaction (`types.go:108-113`). The SQL checks the decision, `reviewed_by=actor`, that the booking is still attached, and that `assigned_at` matches the participant snapshot (`:47-52`).
- **Incarnation.** `paymentReceiptSource` requires the admitted source to contain the exact `Before` authority, including `CreatedAt` (`derivedmutation/pass_payment_receipt.go:34-62`).
- **Hard-coded `Action: commandProofAccept` for reject is correct.** `validPaymentAuthority` only allows `PaymentAttempt` with `Action == proof_accept` (`read_authority_types.go:98-105`), so queue authorities always carry that action.
- **Replay.** The probe runs in a transaction that is always rolled back and never calls `Apply`. On the completion path nothing is re-executed.
- **Privacy.** `paymentReceiptCall` shows the model only `{operation_id, complete, result:{decision}}` (`script_registration_completion.go:520-533`). Retired records go through `omitRegistrationPayload`. The HTTP response carries only authority metadata, and only to the authenticated owner, who must be a payment admin.
- **Fencing.** Only an authority exactly equal to `payment.Before` is rebased (`:281-286`). Other stale or revoked authorities stay in the validation clone, and `authorizeNewRecord` checks them (`:172-193`, `:433`). The unit test checks that a different attempt is not rebased.

## Verified findings

### F1 — Medium (CI gate): line too long for the `golines` formatter
- **Where:** `platform/internal/agenthost/script_registration_completion.go:469`
- **Problem:** The return expression is about 170 characters long. `.golangci.yml:27,44-47` turns on `golines` with `max-len: 120`, so format checking will flag this line. Because it is code rather than a string literal, golines can and will rewrite it.
- **Fix:** Split the check into one boolean per operation, or use a small lookup such as `map[toolName]commandName`.

### F2 — Medium: the main acceptance test does not check the requirements it claims to cover
- **Where:** `platform/integration/script_pass_completion_diagnostic_test.go:134-146`
- **What the test does:**
  - Line 134 only checks `len(model.inputs) == 2`. The message says "committed decision must reach a fresh model without retired review output", but nothing checks that the second input contains `decision:"accepted"`, or that review content (attempt, proof, submitter) is missing from it.
  - Lines 139-146 count *any* `core.pass_booking_operations` row for `bob`. They don't check the admitted command's key.
  - Nothing checks the ledger afterwards: that the trusted call has `ResultAuthorities == [After]`, and that the review run is omitted with `source_changed`.
- **Impact:** The test would still pass if the trusted receipt were wrong or if review output leaked into the model, as long as the model was called twice.
- **Fix:** Parse `model.inputs[1].Script.Runs`. Assert that the payment call's result JSON is exactly `{operation_id, complete:true, result:{decision:"accepted"}}` and that the review call is redacted. Filter the operation count by `key_hash`.

### F3 — Low: the negative scope tests don't show why they fail, and several cases are missing
- **Where:** `script_pass_completion_diagnostic_test.go:274`
- **Weak assertion:** `err != nil || !receipt.Found` accepts any failure. The cases fail for different reasons, and none of those reasons is asserted:
  - `target` and `attempt` fail on `idempotency_conflict`, so the attempt check in the SQL is never reached;
  - `actor` fails on `forbidden` because alice is not an admin;
  - `new_version` fails on `source_stale`;
  - `recreated` fails on `invalid_derivation`.

  If the setup broke, these cases would still pass. Assert the specific `ProblemError` code for each.
- **Missing cases:**
  - `proof_reject` / `"rejected"`.
  - A couple (two-participant) attempt, where the partner is touched too.
  - A causal-group source.
  - Revocation *between* commit and completion, run through the `ScriptStore` path rather than just the probe.
  - An unrelated revoked authority in the same record, which must stay fenced end to end.
  - Calling completion twice (replay).
- **Unit test gaps:** `TestPaymentCompletionRebasesOnlyExactAttempt` (`script_registration_completion_internal_test.go:130-168`) doesn't cover a different `CreatedAt` or the causal recursion.

### F4 — Low: a NULL `assigned_at` becomes a generic error instead of `source_stale`
- **Where:** `platform/internal/passbooking/payment_completion_receipt.go:47-53`
- **Mechanism:** `b.assigned_at=member.assigned_at` evaluates to NULL if either side is NULL. If the other checks are true, the whole `AND` is NULL, and scanning NULL into a `bool` fails. The code then returns an untyped error instead of `conflict("source_stale")`.
- **Evidence:** `paymentParticipants` guards the same comparison with `COALESCE(…,false)` (`payments.go:148-149`), so NULLs clearly occur. `Payment` also allows legacy metadata joins.
- **Fix:** Use `COALESCE(<expr>, false)`.

### F5 — Low: a consistency check that can never fail, and its failure branch skips retirement
- **Where:** `script_registration_completion.go:490-503`
- **Mechanism:** `PaymentCompletionReceipt` builds `Before`, `After`, `Attempt` and `Decision` straight from `command` and `target` (`payment_completion_receipt.go:59-76`). So this check can only fail if the transport corrupted the data. If it ever did fail, it returns bare `s.StaleError` without `retirementError`, unlike the stale path inside `commitRegistrationTransition` (`:101-104`).
- **Fix:** Remove the check, or route the failure through retirement consistently.

### F6 — Low: inconsistent error mapping in the HTTP adapter
- **Where:** `platform/internal/appclient/derived_payment_receipt.go:18-20, 33-34`
- **Mechanism:** Every other passbooking derived adapter wraps its HTTP result in `registrationHTTPResult(...)` (for example `appclient/derived_receipts.go:74-75, 89-90`). This one returns the raw error. I couldn't find where `registrationHTTPResult` is defined, so I can't say exactly what differs. The risk is that HTTP deployments map errors differently from `LocalDerived` deployments, which go through `orderApplicationError`.
