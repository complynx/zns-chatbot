# Code QA review: pass redaction delivery (read-only)

**Verdict: Conditional pass. No blocking defect found; 1 Medium finding and 5 Low findings below.**

The fix works as intended. Before it, `prepareFamily` compared the stored tombstone source with `reference.Source` (always nil for redaction). So any tombstone that kept a source was always stale. Now a redaction reference must carry no source, generation or authorities, and the tombstone checks still apply: redacted state, revision, view equality and canonical target. The retry path keeps the target saved on attempt 1. I ran no tests, builds or commands, and nothing here shows the tests pass.

## Implementation path checked

- **Admission** (`admission.go:90-145`): chat must match `core.users.telegram_id` (123-125). `lockPassMenu` requires `Redacted` (`family_authority.go:150-154`). `lockViewBinding` re-reads the view `FOR SHARE` and compares revision and state (219-230).
- **Source check** (`family_authority.go:87-93`): redaction rejects any source, generation or authorities. Other families still compare the source exactly. Since `Source` and `Generation` are nil, deleting history can't block the fixed notice. That is intended: the notice has no private content.
- **Target on first attempt** (`admission.go:180-184` → `family_authority.go:264-291`): the rendered target must equal `pass_views.chat_id/message_id`. `beginAttempt` then writes the canonical target and switches to edit (`admission.go:223-226`).
- **Target on retry**: attempt ≥1 skips the target lock, and `Attempt != 1` blocks any override, so the saved target is reused. `finishBotIntent` keeps phase and target unless there was a fallback (`bot/delivery_intents.go:84-87`). A 429 goes through `telegram.DeliveryOutcome` and is deferred. "Message to edit not found" on redaction is `Rejected`, never a send (`bot/delivery_worker.go:92-93`).
- **Renderer**: it rebuilds the fixed localized text with no buttons. It takes `message_id` from `pass_views` and returns `ErrStale` if it is ≤0 (`bot/delivery_render.go:31-60`).
- **Queue timing**: `DeliveryCandidates` and `queueAdmission` use the database clock (`delivery/queries/queue.sql:56`, `delivery/queue.go:131-137`), so the retry test waits on the real persisted deadline.

## Findings

### F1 — Medium: a cross-owner target is accepted and rewritten, not denied, and the test locks this in
- **Where:** `platform/integration/pass_redaction_delivery_test.go:95-98, 124-133`; `platform/internal/botdelivery/cards.go:37-39`; `admission.go:223-226`.
- **What happens:** `EnqueueCard` stores `in.Target` without checking it. The target is compared with the canonical row only at first-attempt begin, using the *renderer's* target, not the stored one. `beginAttempt` then overwrites it.
- **Evidence:** in the `foreign_target` scenario, enqueueing chat 202's message ID succeeds (`require.NoError`) and the intent ends `Succeeded`.
- **Impact:** what reaches Telegram is safe: it edits the canonical message. But the requirement says cross-owner references are *denied*. Here the forged value is accepted, persisted in `target_message_id` until attempt 1, and the test certifies that behaviour.
- **Fix:** for `familyPassRedaction` at enqueue, require `in.Target > 0` and run `lockRenderedTarget(ctx, tx, i, in.Target)` inside `EnqueueCard`. Change the test to expect `bot_delivery_stale` and zero intents. If rewriting is the intended contract, update the requirement text instead.

### F2 — Low: "a missing target never becomes a send" is only enforced by the bot renderer, not the authority layer
- **Where:** `family_authority.go:281-289` (together with `admission.go:223`).
- **Mechanism:** for redaction, the check `chat != i.Chat || message != target` passes when `pass_views.message_id = 0` and the target is 0. `beginAttempt` then keeps `phase=send` if the intent was enqueued without a target, and `sendBotIntent` would call `Send`.
- **Why it doesn't happen today:** only `renderBotPassRedaction` (`delivery_render.go:53-55`) and `renderRedactedPassMenu` (`pass_menu_redaction.go:84-86`) block it.
- **Uncertainty:** whether `message_id` can be 0 depends on the schema, which I couldn't locate. `StorePassMenu` inserts without it. Reaching this path needs a caller that skips the bot renderer, i.e. the bot process itself, so this is hardening rather than an exploitable bug.
- **Fix:** in `lockRenderedTarget`, and in `beginAttempt` for redaction, require `target > 0` and phase edit, and return `ErrStale` otherwise.

### F3 — Low: unused reference fields are not normalised for redaction
- **Where:** `passMenuSourceMatches` (`family_authority.go:87-91`).
- **Mechanism:** only Source, Generation and Authorities are constrained. `Event`, `Object`, `Version`, `Update`, `Notice`, `Continuation` and others are free.
- **Impact:** `EnqueueCard` deduplicates on the full reference JSON (`cards.go:55-57`), so varying these fields creates several redaction intents for the same card. Each is an idempotent fixed-text edit, so there is no privacy impact, just queue noise and a weaker binding.
- **Fix:** for redaction, reject any field other than `Kind`, `Family`, `CardKey`, `Revision` and the expected `Continuation`.

### F4 — Low: test gaps against the requirements
- **Target missing at begin:** no test covers a canonical `message_id` of 0, or a `Target` of 0 at enqueue. The "target gone" cases only cover the provider's "message to edit not found" reply.
- **Revision change during retry:** the stale-revision check is only tested before the first attempt (`:99-102`). Nothing tests a revision bump while the intent is deferred after the 429.
- **Reference shape:** the handcrafted reference (`:28-33`) has an empty `Continuation`. Production sets `Continuation{Kind:"pass_redaction", Revision}` (`bot/delivery_cards.go:102`, `pass_menu_redaction.go:91-92`), so the tested binding is not the production one.
- **Positive control:** the "valid" case (`:65-73`) only proves the intent is admitted, not delivered. Delivery is covered by `RetriesAfterActualDeadline/sent`, which is acceptable.

### F5 — Low: comparing the Go clock with database timestamps may make the retry test flaky
- **Where:** `pass_redaction_delivery_test.go:223` and `:229`.
- **Mechanism:** `deadline` comes from the database clock, but the assertions compare it with `time.Now()` in Go. If PostgreSQL's clock runs ahead of the test process (e.g. Docker Desktop/WSL2 on this Windows host), line 229 can fail even though the queue correctly found the intent eligible. If it runs behind by about 1s, line 223 can fail.
- **Fix:** compare against `SELECT clock_timestamp()`, or rely only on the candidate and attempt assertions.

### F6 — Low (uncertain): `require` is called inside the HTTP transport
- **Where:** `redactionRetryTransport.RoundTrip` (`:167-176`).
- **Risk:** it calls `require`, which uses `t.FailNow`, and updates plain `int` counters. That is only safe if `pumpBotDeliveries` sends on the test goroutine. I couldn't find that helper, so this is unverified. Using `assert` plus atomic counters would remove the risk.
- **Nit:** the comment at `:149` says "rejected edit", but the first edit is a 429 deferral.
