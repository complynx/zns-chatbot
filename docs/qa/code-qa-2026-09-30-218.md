### P1 — mutable menu mismatch still masks actual payload capability revocation before admission

`final/platform/internal/botdelivery/admission.go:112-115` returns generic `ErrStale` when the rendered `PassCardReceipt` differs from `PassCardBinding(f.menu.RegistrationMenu, ...)`. This happens before the actual rendered capability check at lines 156-159, immutable source checks and history fences. The new canonical binding is therefore not yet persisted.

Concrete sequence: an existing source-bound private payment queue card is displayed; a refresh reconstructs the payment queue with a valid `proof_accept` grant and produces a rendered receipt with that capability. After construction, but before Begin, change the same revision's current view to `events` and revoke the payment-admin grant. Begin sees the events view, compares its empty capability to the rendered queue capability, and returns generic stale. `bot/delivery_worker.go:238-242` requests retirement, but `bot/pass_menu_redaction.go:116-124` rechecks only `i.Reference.Source`. That original source can be a home-menu derivation without the later payment-queue capability (the new tests already use this shape). A valid source returns nil and skips retirement. The refresh is cancelled, while the previous private queue card and its callbacks remain visible. Restoration of the grant does not fix the already terminal refresh.

The successful-receipt path correctly uses the canonical payload capability after view replacement; the pre-admission path still treats a view mismatch as authoritative before checking that capability. Check actual rendered capability/source/history first under the existing lock order, preserve a definitive denial across the boundary, then return ordinary view staleness only when those checks pass. Ensure the retirement path receives enough validated payload authority to retire the exact prior target without retiring unrelated valid cards. Add a pre-Begin combined view-change/grant-revocation case and a valid-grant control; the combined tests in `integration/pass_receipt_retirement_test.go:219-359` currently change state only after the successful private send.

The same early-return problem exists for absent view rows at receipt continuation: `family_authority.go:85-87` returns `pgx.ErrNoRows`; `admission.go:103-105` does not recognize it as `viewStale`, then `familyMissing` converts it to generic stale before immutable source/history/canonical capability checks. `receipts.go:37-43,59-71` sets continuation done without retiring actual successful targets. Thus a revoked source plus missing mutable projection permanently skips cleanup. The schema in `platform/internal/store/migrations/032_pass_ui.sql` does not cascade view deletion to buttons. There is no current product view-deletion caller found; this second case is a static recovery limitation, not an asserted ordinary UI flow.
