## Verified findings

### F1 — Medium: the owned-deletion path skips the new "only stale" guard
- **Where:** `platform/internal/agenthost/script.go:125-132`, and `script_knowledge_completion.go:201-231`
- **How it happens:**
  - The failure check (`onlyScriptStale`) only runs inside `projectRetiredMemory` (line 133).
  - The earlier branch at lines 126-131 runs whenever `errors.Is(err, StaleError)` is true. That includes combined errors such as `errors.Join(stale, <access-check error>)` from `script_ledger.go:152`, or `errors.Join(stale, <persist error>)` from `script_ledger.go:141`.
  - If `ownPrivateDeletion` finds a current memo or document deletion receipt, `Perform` returns `AddContext(...)`, which is success.
  - `ownPrivateDeletion` also accepts any retirement (`scriptRetired`: pass, history or memory). It never checks that the deletion caused the retirement, so a concurrent permission or history retirement in a script that deleted a memo also ends as success.
- **Impact:** A storage or authorization failure joined with stale is hidden whenever `AddContext`'s fresh reload succeeds (for example, after a transient failure). A real permission retirement becomes a successful turn.
- **Limit on impact:** `AddContext` reloads through `LoadAuthorized`, so a failure that persists will come back as an error. No private data is exposed.
- **Fix:** Require `onlyScriptStale(err, ...)` before `ownPrivateDeletion` runs. Also check the retirement cause (for example, the record is retired for history/memory reasons and no access change was found).

### F2 — Medium: memory projection can't tell a permission retirement apart
- **Where:** `script_retired_projection.go:38-40`, `script_store.go:138-148`, `script_ledger.go:120-142`, `script_store.go:465-467`
- **How it happens:**
  - `memoryRetirementProjection` ignores `PassRedacted`.
  - A memory retirement found in `CompleteRun` goes through `prepareLedgerChange` → `retirementError` → `persistRetirement`. That calls `RedactPassScript` on every matching record, so a memory retirement is also stored with `PassRedacted=true`.
  - The stored shapes for "permission retired" and "memory retired" therefore overlap. When an access change and any memory-state change happen together, the result is projected as success.
  - The fresh `Records()` call doesn't re-check access for records that are already retired (`reauthorize` skips them, `script_store.go:99`).
- **Test gap:** `script_retired_projection_internal_test.go:36` only covers `PassRedacted` alone. It never covers `PassRedacted+MemoryRedacted`, which is the shape actually stored for memory retirement, so it overstates how well permission retirement is excluded.
- **Impact:** A permission retirement can end as success (the content is still redacted). This is an edge case, but it directly contradicts the acceptance scope.
- **Fix:** Store the retirement cause separately (for example, a distinct access-retired flag), or re-run the access check for the target record before projecting.

### F3 — Medium (test quality): the durable privacy test can pass vacuously
- **Where:** `platform/integration/script_knowledge_completion_test.go:133` and `139-143`
- **How it happens:**
  - `_ = f.b.Handle(...)` throws away the result, so the test never states whether a history retirement ends in an error or in success.
  - The privacy loop runs over `model.inputs[1:]` without first requiring `len(model.inputs) >= 2`.
  - A history retirement in `Perform` is not projected (`HistoryRedacted` blocks it), so the likely outcome is a stale error with one model input. The loop then checks nothing. With zero inputs, `[1:]` panics.
- **Impact:** The test doesn't show that deleted content stays out of the next context, or that retirement doesn't become success. That is exactly the "without weakened assertions" criterion.
- **Fix:** Assert the expected `Handle` error (for example, `ErrorIs(..., appclient.ErrReadStale)`) and the exact number of inputs. Also scan the whole input and `bot.interactions`, not just `input.Script`.

### F4 — Low (test determinism): the history-cache race barrier fires too early
- **Where:** `platform/internal/bot/history_cache_postgres_internal_test.go:48-55` and `129-148`
- **How it happens:**
  - `completionStarted` fires on `/v1/memory/deletions`, which is the first I/O in `CompleteRun` (`script_store.go:261`).
  - `DeleteContent` then races with the rest of the flow: the generation read and authorization in `prepareLedgerChange`, then the advisory lock in `commitLedger`.
  - Which path gets tested (generation mismatch before the lock, or a revision conflict at the lock) depends on scheduling. The barrier suggests the test forces the lock-blocked case, but it doesn't.
- **Unverified risk:** `commitLedger` only compares raw ledger bytes (`script_ledger.go:54`). Generation and authorization are checked before the lock, which is intentional per lines 36-37. If `DeleteContent` doesn't rewrite `bot.interactions`, a late completion could commit after the generation bump. The next `Records()` call reconciles it and the pre-provider exposure fence limits the damage. I couldn't find `DeleteContent`, so this is not confirmed.
- **Fix:** Signal from a hook placed after authorization, just before `LockScript`, or assert which path was taken.

### F5 — Low (coverage): modern read binding is missing negative cases for rights and preparation
- **Where:** `script_modern_read_binding_internal_test.go:24`, `modern_read_admission_test.go:16-48`
- **What is covered:** Execution-time snapshot, cursor and target changes, and immutability of the in-memory request.
- **What is not covered:**
  - Preparation rejecting a checkpoint snapshot mismatch (`script_modern_orders.go:521-523`).
  - A fabricated or unknown cursor at preparation.
  - Review rights revoked between preparation and execution (`ReviewOrder`).
  - A full `AdmitCall` → `CompleteCall` identity round trip for a read.
- The integration test only covers the happy path, and it dereferences `ModernOrder` without a nil check (line 40).
- Reading the code, execution does re-read with the owner's current rights, compare the fingerprint, and leave the request unchanged (`script_modern_orders.go:459-498`). The tests just don't prove the rights part.

### F6 — Low (complexity): the checkpoint query scans the owner's whole ledger
- **Where:** `script_modern_order_reads.go:38-46`
- **Problem:** `jsonb_array_elements` expands every `script_runs` row the owner has, across all updates, before `ORDER BY ... LIMIT 1`. Cost grows with retained history.
- **Fix:** Bound by recent update or add a supporting index or retention limit.

## Checked with no defect found
- **`onlyScriptStale`:** handles nested `errors.Join` from `retirementError`/`authorizeLedger`. It rejects stale combined with cancellation, access or persist errors. `ErrReadStale` is a plain sentinel.
- **`projectRetiredMemory`:**
  - Checks `ctx.Err()` first.
  - Reloads through freshly authorized `Records()`.
  - Neither completes the rejected write nor resumes the VM.
  - `RedactDeletedScript` clears code, input and results.
  - Retired records are skipped by knowledge-call recovery and refresh.
- **Deleted memo reads:** `KnowledgeReader.RefreshKnowledge` redacts them by deletion state and replaces them with a fresh `Memos` read. That explains `RETAINED-PRIVATE-MEMO` appearing in the delete-then-list test.
- **Modern order reads:**
  - Cursor and snapshot are bound in `Prepare`, before `AdmitCall`.
  - `scriptCallIdentity` includes the target, cursor, snapshot, version and source.
  - Retired calls are left out of the checkpoint chain (`result` uses `omitempty`, and history redaction sets an error).
  - A stale read clears `input.ModernOrder` before validating.
