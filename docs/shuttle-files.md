# Durable attachment references

Manifest `mvp-8` introduced the static `zinusya_files` module with owner-scoped
`info` and `fetch` reads. Arguments use an opaque UUID `external_id`. Fetch returns
an authenticated relative download path, actual content MIME, size and SHA-256;
Loom imports bytes only when the agent explicitly requests the file. Initial
message input contains caption and reference metadata, never file bytes, bot
credentials or Telegram file IDs.

Supported primary message forms are photo, document, audio, voice, video,
video note and animation. Photos select the largest area variant, independent of
array order. Telegram's animation/document compatibility alias creates one
reference. Unsupported stickers and other unsupported message forms keep the
existing error path. Custom emoji keep their ordinary Unicode text fallback.
The agent decides whether content is payment evidence, avatar or casual media;
no business classification is inferred from a menu or old waiting context.

Explicit avatar requests now use [the separate avatar module](shuttle-avatars.md)
and its durable generated JPEGs. Original attachment bytes still depend on Telegram;
generated bytes survive its cache loss. See [native acceptance](shuttle-avatar-qa-2026-10-14.md).

Intake commits the accepted request, opaque file reference, owner, task and queue
job together. Duplicate update IDs keep the original task/reference. Each record
preserves the original Telegram message ID and UTC sent time, plus server acceptance
time. Processing after IAM/Loom downtime or bot restart does not replace the sent
time. These trusted transport times are the basis for future payment deadlines;
a model-provided date is not an alternative source.

Filename and declared MIME are untrusted metadata. The download descriptor uses
content-detected MIME and SHA-256. Language follows the linguistic caption; without
one the agent uses previous conversation language, then the bot/Telegram fallback.
The existing ru/be/uk to ru and other languages to en mapping supplies that fallback.

Every info, fetch and content read verifies the current active account, bot,
organization and exact owner. Revocation is checked again after the remote read.
Administrators cannot read arbitrary other users' attachments through this module.
Ambassadors use the separate payment-evidence routes with current event authority
and an explicitly submitted proof. This module has no general file-owner bypass.

After authorization, a saved Telegram size above 20 MiB rejects a content or fetch
read with HTTP 413 before Telegram IO. Metadata remains available to the owner.
Unknown and exact-limit declared sizes still use the bounded remote reader;
declared size does not replace its metadata and actual-body limits. An explicit
getFile size refusal also returns HTTP 413 when the saved size is unknown. Only
a validated failure envelope with code 400, HTTP 400 or 200, and the exact
`Bad Request: file is too big` description receives that classification. The
description is not retained or returned. Other refusals and malformed responses
keep their existing unavailable handling; send errors are unchanged.
For these remote reads the Telegram client calls getFile afresh, contains token-bearing URLs,
rejects traversal and redirects, and bounds metadata and downloaded bodies.
The local reader ceiling is 20 MiB. Telegram documents a cloud download ceiling
of 20 MB and refreshable temporary paths in its
[getFile contract](https://core.telegram.org/bots/api#getfile).
The local ceiling does not promise that every file below it is downloadable from
Telegram. Other source failures still return unavailable. See the separate
[real 21 MiB document acceptance](shuttle-file-limits-qa-2026-10-15.md) and
[unknown-size cloud-refusal acceptance](shuttle-cloud-file-qa-2026-10-15.md).
Files are served as attachments with nosniff, private/no-store and sandbox CSP;
HTML is not an application page. The Go implementation adds no media libraries.

The fetch method declares external_disclosure=true for its returned artifact so
Loom can extract bounded text or attach a derived image when assisting the user.
This does not override Loom's live user/run disclosure policy. The info method
returns metadata only. File access still requires the active owner; importing or
processing a file does not grant payment authority or confirm money.

No file bytes or temporary download URLs are stored in Shuttle PostgreSQL.
References and source provenance remain with message history. A missing or
inaccessible Telegram source returns an unavailable result while metadata survives.
Loom file helpers can re-fetch using the stable service/module/fetch/external-ID
reference after their temporary handle expires.

Source failure does not mark the durable reference permanently lost or cache a
failed result. An explicit later fetch of the same UUID can succeed after source
access returns. A descriptor is not an availability guarantee: its content read
refreshes Telegram metadata and can fail independently. The owned
[source/refetch acceptance](shuttle-file-recovery-qa-2026-10-15.md) covers unavailable
fetch/content, a restarted API, restored original bytes and real Loom reimport
after an explicitly expired temporary artifact. It proves explicit retry, not
automatic model recovery or permanent-source-loss classification.

Migration 00010 adds the child file-reference table. Apply it before the candidate.
A rollback must retain/export provenance and stop new intake: older binaries do
not understand attachment-bearing task requests. Do not claim they can safely
finish new attachment tasks.
