# Внешний аудит — 29 сентября 2026

Полный read-only аудит Go-платформы, архитектуры, документации и локальных записей по запросу Даниила. Пять независимых проверок: ядро бота, доменные пакеты, воркеры/инфраструктура/CI, архитектура, документация и локальные записи. Код не менялся; сборка образов, стенды и PG-тесты не запускались.

**Для исполнителя, не для QA.** Этот файл содержит находки и подсказки исправлений. По [AGENTS.md](../AGENTS.md) его нельзя передавать независимым Code QA / Functional QA рецензентам.

**Какое дерево проверялось.** Аудиторы кода смотрели `platform/` (миграции до 066). Актуальный кандидат — `qa.local/architecture-stage-cd-composed-acceptance/source` (до 083). Находки с пометкой **[CD ✓]** перепроверены в кандидате и там присутствуют; остальные перед исправлением нужно сверить с объединённым составом — часть могла уже измениться.

Уже решено и в работу не входит: постоянные разрешения подтверждены Даниилом (срок откладывания дефектов ограничен финализацией рефакторинга — внесено в DEFERRED/PROGRESS); токен тестового бота Даниил перевыпустит сам — агентам его не трогать.

## P0 — сохранность работы

**AUD-01. Go-платформы нет в Git.** `git ls-files platform` = 0; все 695 коммитов — Python-бот; HEAD `9491c79` не запушен. Актуальный код только в игнорируемом `qa.local` (≈2,6 ГБ, ~95 полных копий исходников) плюс несколько отдельных кандидатов из [restart-handoff](restart-handoff.md). Интеграция — ручное слияние снимков по SHA256-манифестам, одна копия на одном компьютере; `git clean -X` или сбой диска уничтожат работу. CI (`.github/workflows/platform.yml`) тоже не закоммичен и ни разу не выполнялся.
Сделать: объединить кандидата и дельты из handoff в `platform/`, локальный коммит на `feature/go-platform-sandbox` (разрешено); дальше Git — единственный источник правды, новых деревьев-снимков не заводить, манифест → хеш коммита. Перед коммитом решить судьбу 12 МБ фото в `platform/internal/miniapp/foodphotos/`, тестовых медиа в `platform/testdata/media`, `PROGRESS_HISTORY.md` (523 КБ) и `docs/fqa-scenarios.md` (195 КБ).

**AUD-02. Параллельные кандидаты расходятся быстрее, чем сливаются.** До прохождения одним объединённым составом compile/tests/PG/lint не открывать новые независимые кандидаты; QA — по объединённому составу, а не по каждой дельте.

## P1 — дефекты кода

**AUD-10. [CD ✓] Критично: одно сбойное обновление останавливает бота для всех.** `internal/bot/inbox.go` `drainInbox` всегда берёт самую старую строку `bot.telegram_inbox`; при любой ошибке, кроме terminal-plan, `poll` возвращается до `getUpdates`, `Run` повторяет ту же строку каждые 300 мс. Нет счётчика попыток, dead-letter и пропуска. Сценарий: пользователь заблокировал бота во время плана → Telegram 403 в `editOrSend` → никто больше не получает ответов. То же при прочих постоянных 400, не-JSON ответе шлюза, 4xx API. `retry_after` у 429 на этом пути игнорируется.
Сделать: классифицировать ошибки (постоянные → dead-letter/terminal с записью, временные → backoff с учётом `retry_after`), лимит попыток; тест на 403 в середине очереди.

**AUD-11. Высокая: каждый цикл перерисовывает все представления всех пользователей.** `bot.go:Run` → `reconcileAllViews` / `reconcileViews` → `Render` на каждую строку `bot.messages` (≥5 API-вызовов), в режиме Zitadel — `Zitadel.Exchange` на каждый вызов без кэша (`identity/zitadel.go`). То же для pass/order/profile/media/knowledge/massage. Всё последовательно в цикле обработки обновлений; `bot.messages` не очищается. При сотнях пользователей — тысячи HTTP-вызовов и обменов токенов за цикл.
Сделать: перерисовывать только изменившееся (события/версии), кэшировать токены до истечения, очистка старых `bot.messages`.

**AUD-12. [CD ✓] Средняя: свободный текст «model: …» / «language: …» не доходит до агента.** `internal/bot/model_settings.go` (`strings.HasPrefix(in.text, "model:")` без проверки callback) и `language.go` `isLanguageAction`. «model: reset» сбрасывает настройку модели; «language: какие языки ты знаешь?» открывает выбор языка. Нарушает правило «свободный текст интерпретирует агент». Причина — цепочка префиксов в `dispatchUpdate`, зависящая от порядка.
Сделать: callback-префиксы сопоставлять только для `u.Callback != nil`.

**AUD-13. [CD ✓] Средне-высокая: одна старая попытка без цены навсегда блокирует бюджет.** `internal/credits/policy.go` `usageAt`: `cost IS NULL AND reserved IS NULL AND state<>'not_sent'` без фильтра `period_start`. Попытки до enforcement и неудачные вызовы без usage всегда такие (`Begin` не ставит `ReservedNanoUSD`, `priceUsage` выходит рано). После включения enforcement пользователь получает `credits_limit_reached` во всех будущих месяцах до ручной сверки. То же для потерявших unlimited. Тестов на `LegacyBudget` нет.

**AUD-14. Средняя: ошибки `reserveBound` маскируются.** `credits/enforce.go:46-49`: для лимитированных любая ошибка (битый JSON цены, ошибка БД) → `ErrUnpriced`; для unlimited ошибка отбрасывается, хотя транзакция уже может быть прервана.

**AUD-15. Средняя: сбой между Reserve и Dispatch держит резерв до конца месяца.** `credits/call.go:43-50`; освобождение только ручное (`operator.go` `releaseReserved`). Нужна автоматическая сверка зависших `reserved`.

**AUD-16. Средняя: orders `reconcile` пересчитывает всё событие на каждую команду** под `FOR UPDATE` события (`orders/service.go` ~550–615): все заказы × запросы вместимости. На масштабе фестиваля сериализует все записи события. Там же вытеснение молча снимает оплаченную допуслугу (`capacity_reservations.go` `claimCapacity`) без записи о возврате — паритет с Python, но нужно продуктовое решение Даниила.

**AUD-17. Средняя: исполнитель скриптов обслуживает один скрипт на всю систему.** `internal/scriptservice/service.go` `busy: make(chan struct{}, 1)`, занятый слот → сразу 503; один запуск держит слот до ~7 с. Два одновременных агентных хода со скриптами → второй падает. Нужна ограниченная конкурентность или короткая очередь.

## P2 — архитектура

Направление (модульный монолит, транзакции в доменах, без фреймворков, sqlc, строгий lint) верное; исполнение перегружено. Масштаб: ~98 тыс. строк Go + 84 тыс. тестов против ~15 тыс. Python; 82 миграции до релиза, 9 бинарников, 7 Dockerfile, ~10 контейнеров.

- **AUD-50. Loopback HTTP внутри процесса.** Прямые вызовы только для History/Knowledge/Orders/Registration (`appclient/client.go`); остальные ~8 доменов идут bot → appclient HTTP → api → сервис с обменом токена на каждый вызов. Одна операция описана в 4–6 местах. Сделать: in-process вызовы `appservices` через один авторизатор; HTTP-клиент оставить для Mini App/браузера. Ожидаемо −3–4 тыс. строк.
- **AUD-51. `bot` — god-package:** ~23,7 тыс. строк, 177 файлов, 39 внутренних импортов, 42 `script_*` файла (6,4 тыс. строк), три пути данных (`DB`, `API`, `Host`), прямой SQL в `core.` и `credits.`. Перенос host-policy запланирован в mid-C audit, но не сделан. Цель: только ввод-вывод Telegram, отрисовка и собственное хранилище, < 10 тыс. строк.
- **AUD-52. Outbox скопирован 4 раза** (`orders`, `massage`, `legacyfood`, `passbooking` — `dbgen/notification_delivery.sql.go`, 11 одинаковых запросов). Свести в один `delivery/outbox` с доменными колбэками.
- **AUD-53. Обратные зависимости:** `conversation → readsource → {passbooking, massage, legacyfood}`, `store → orders`, `agent` импортирует orders/passbooking/legacyfood/knowledge, `appclient/identity → telegram`, `miniapp → api`; `derivedmutation` импортирует 15 доменов. Добавить depguard/правило слоёв.
- **AUD-54. Пересечения:** `agent` и `agenthost` (10,7 тыс. строк) дублируют knowledge/history/script/evidence. Имена вводят в заблуждение: `passbooking` = регистрация, `passes` = профили, `workflow` = бронирование слотов; предлагается `registration` (+ ingress/native/allocation), `passprofile`. `sticker*` — 5 пакетов → 2; decoder/broker образы → один образ с режимами.
- **AUD-55.** Перед первым релизом схлопнуть миграции в одну baseline; импортёр — под неё.
- **AUD-56.** Zitadel — жёсткая runtime-зависимость для продукта с Telegram-only identity: сбой IdP = сбой бота. Продуктовое решение Даниила; минимум — не обменивать токен для доверенных in-process вызовов.
- **AUD-57.** Риски перехода: откат после первых записей Go небезопасен (`go-deployment.md`), реальные Telegram/модель/ASR не проверялись, импортёр Mongo→PG целиком не принят, CPU-лимиты контейнеров не измерены.

## Что проверено и в порядке

Деньги — целые (`int64`, nano-USD, `big.Int`); вместимость — блокировки строк, а не check-then-insert; идемпотентность через хеш запроса; Telegram-отправки вне транзакций, через outbox; SQL параметризован; проверка `initData` по документации Telegram, `hmac.Equal`/constant-time везде; админ-действия авторизуются на сервере; inbox сохраняется до сдвига offset. Песочница скриптов (свежая VM, без сети/ФС/таймеров, повторная проверка allowlist на хосте, read-only контейнер без root) и медиа (ffmpeg без shell, allowlist протоколов, лимиты размеров) сделаны тщательно. `go vet` и `gofmt` чистые; все ~30 подавлений линтера узко обоснованы; CI с минимальными правами, govulncheck, `-race` на реальном PG. Prompt injection, реальных секретов в коммитуемых файлах, реальных персональных данных, нестандартных git-хуков не найдено. Выборочные QA-отчёты честно ограничивают вердикт объёмом.
