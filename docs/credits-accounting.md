# Credits and paid-operation accounting

Research date: 2026-09-26; integration update: 2026-09-27. The credit lifecycle and diagnostic successor are integrated in the Go tree after independent scoped reviews. The full lifecycle Functional QA evidence and fresh diagnostic/recovery QA are recorded in PROGRESS_HISTORY.md. Combined Go units and credit/domain PostgreSQL checks passed; whole-product and final external-provider acceptance remain separate. Earlier shadow/enforcement inventories below are historical development records, not current feature gaps.

## Current runtime contract

Migration065 and the final candidate add authenticated remote attribution, conservative ASR bounds, immutable operator corrections/reconciliation, aggregate reports and explicit cutover. An update records its quota mode before paid work. Before the cutover it uses the legacy question budget; afterward new updates use credits. Retries retain their original mode. Unknown cost remains unknown and dispatched unresolved attempts retain their holds.

Tariff registration and safe dispatch are separate checks. An operator may register a historical tariff that lacks a bound suitable for a new finite request. Dispatch requires explicit reviewed bounds; registration alone does not authorize spending.

- `asr_tokens`: `min_input_tokens=0`, `0 < hard_input_limit <= max_input_tokens`, `hard_output_limit > 0`, explicit audio/text/output rates, nonempty `bound_source`, empty `service_tier`. No duration-to-token estimate is inferred.
- `audio_seconds`: positive `hard_audio_seconds`, explicit per-second rate and conversion, nonempty `bound_source`, empty `service_tier`.
- Rates and conversions are rational strings. Conversion revisions and provenance remain immutable. No production tariff or invented provider maximum is bundled.

## Minimal owning service

Add one application-owned `internal/credits` service, injected by runtime composition. It owns budget policy, reservation/settlement, prices/conversions and reports. It does not own business ACL, model prompts, media decoding or provider transport. Do not build a generic workflow/command bus, payment wallet, provider marketplace or tokenization framework.

Use explicit typed calls such as `Reserve(scope, operation, priceSelection, upperBound)`, `MarkDispatched(attempt, fence)`, `Settle(attempt, measuredUsage)` and `ReleaseNotSent(attempt)`. They run short database transactions; no transaction spans provider network work. A provider adapter receives only its reserved attempt identity and typed usage sink. The host supplies attribution; the model, uploaded files and script arguments cannot choose payer, price, unlimited status or settlement values.

Required durable records can remain four small tables:

1. Account policy per owner/system/campaign: finite mode or unlimited, allowance version, chosen period boundary, enabled state. Zero is a real finite allowance, not an alias for unlimited. Superadmin status makes the effective personal policy unlimited while current authority holds; an explicit grant can also make a nonadmin unlimited. Revocation affects new reservations immediately.
2. Paid attempts: logical operation key plus dispatch sequence, actor, payer, subject type/ID, provider/model, price/conversion versions, state, fencing version, reserved amount, original usage counters/units, provider request identifier, timestamps, settlement basis and uncertainty. Unique attempt key makes settlement idempotent. Business operation identity and provider attempt identity are separate.
3. Immutable price/conversion revisions: provider/model/version/service tier, billing dimension, source currency/unit, exact rate numerator/denominator, effective interval, source reference and content hash. The same revision record can snapshot a provider-to-canonical conversion; no plugin registry is needed.
4. Audited adjustments/allowance changes: authorized actor, reason code, idempotency key and signed amount referencing an attempt or policy. Never edit settled history to hide a correction. This is a narrow audit table, not event sourcing for the application.

Availability queries can initially aggregate indexed attempts within the chosen period. Lock the payer row when reserving so simultaneous processes cannot both consume the last balance. Use settled debit plus active reservation/unknown hold; do not hold locks while calling the provider. A materialized balance cache is unnecessary until measured query cost justifies it. Concurrency must use the same lock order for user/system/campaign budgets if multiple caps apply.

## Exact usage, price precision and conversion

Preserve raw typed numeric usage and its provider units separately from original monetary cost, canonical credit debit and uncertainty. Distinguish `provider_reported_usage`, `locally_estimated_cost`, `provider_reported_charge`, `reconciled_invoice`, `known_free`, and `unknown`; do not call all of them actual cost. Token counts allow a price-list estimate, not proof of the final provider invoice after contractual discounts, taxes or later adjustments.

Use integer counts and rational/decimal arithmetic, never float64. Rates are exact decimal strings parsed into bounded integer numerator/denominator. Compute the complete request amount before rounding once to the selected canonical precision; validate overflow. Use integer nano-USD for canonical monetary API-balance accounting, with rational intermediate arithmetic for finer-than-nanounit rates. Preserve other providers' original currency/unit separately. The storage scale is 10^9 nanounits per USD; it does not alter the user's one-to-one API-balance semantics. Keep the unrounded components so display rounding cannot alter ledger totals. Reservation rounds upward; settlement follows one documented, tested rule without per-token rounding drift.

For a Responses request with input I, cache-read C, independently identified cache-write W and output O, estimate `(I-C-W)*inputRate + C*cacheReadRate + W*cacheWriteRate + O*outputRate`, plus only documented extra billed line items. Validate nonnegative counters and disjoint subsets. When a model has no separately billed cache-write dimension, W is zero by that model's documented contract; when the dimension applies but cannot be measured, W is unknown rather than invented. Never count cached input twice. Cache-write pricing is a replacement input category on supported models, not an additive surcharge to already charged uncached tokens. [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

Reasoning tokens are included in output usage; retain their breakdown for reporting but do not add them again. An incomplete response can consume paid reasoning without visible output. `max_output_tokens` bounds generated tokens including reasoning, but does not bound all input/media/tool cost by itself. [Reasoning guide](https://developers.openai.com/api/docs/guides/reasoning).

Reserve assuming no cache benefit unless an exact contract guarantees it, and include the highest applicable cache-write category. Resolve long-context thresholds, service tier, modality and tool charges from the chosen price revision. Audio units may be tokens, milliseconds or seconds according to the exact provider model; do not apply a displayed estimated per-minute figure as an exact universal ASR bill. Rate catalog ingestion is an explicit reviewed operator update with effective date; never silently fetch prices during a user request. [API pricing](https://developers.openai.com/api/docs/pricing?tab=suite).

Another provider's converter preserves original provider amount/unit, original currency, price version, conversion ratio/version/source and canonical amount. No default 1:1 mapping for an unknown provider. An unchanged OpenAI identity conversion is still an explicit version. A missing price/converter leaves measurable usage unpriced; paid finite-budget work must fail closed before dispatch if it cannot obtain a safe reserve. Unlimited users still need accounting metadata and operational dispatch bounds; they must not silently turn unpriced paid activity into zero-cost activity.

## Reserve, send, settle and crash semantics

Assign a trusted logical operation key from owner/update/turn/operation, or campaign/recipient/render revision, or media object/transcription revision. Existing `agent.RequestScope` has owner/update/turn for sandbox transport metadata; introduce a separate accounting scope instead of treating that fixture context as an authorization token. Summary keys include the batch/window version; explicit retry increments dispatch sequence.

Before a paid send: recheck business ACL and current model permission, validate resource limits, resolve payer/price, and atomically reserve a conservative maximum. Input bounds must include the final authorized prompt and multimedia evidence, not the original user text alone. Prefer local model-aware token counting plus a safe margin or an enforceable documented bound. Any paid token-counting endpoint is itself metered. Unknown input upper bounds must stop finite-budget dispatch; an estimate presented as a guaranteed ceiling is insufficient.

Mark dispatch durably before sending. Settle returned usage even if result parsing, business validation, downstream sending or persistence fails. Refusal/incomplete output is not free. Settlement can exceed reservation if provider measurement shows overrun: record truthful cost and negative availability, block later finite reservations, and flag the estimator defect; never discard excess usage. Release a reservation only when definitely not sent or the provider confirms no charge. Cancellation after dispatch is uncertain until measured/reconciled.

The database cannot atomically commit an upstream charge. After a crash following dispatch, keep an unknown-usage hold with attempt identity and evidence. Expiry may flag it for reconciliation; it must not automatically turn unknown into free spend. Reconcile from available provider receipts/usage exports; if exact per-attempt linkage is unavailable, retain uncertainty and use an explicit audited adjustment under operator policy. Avoid unlimited silent retry of an uncertain attempt.

Business replay reads the existing result/attempt and does not debit twice. A genuine paid retry gets a new attempt and reserve, even if it belongs to the same Telegram update. Provider idempotency headers only eliminate another charge if that provider explicitly guarantees it; do not infer the guarantee from local keys or request IDs. Automatic HTTP/SDK retries must be disabled or observable at this dispatch boundary. Fencing rejects a stale worker's second settlement, but does not pretend an already sent duplicate request could not be billed.

OpenAI account/project hard limits are an additional provider-level control, not an authoritative per-user ledger; official enforcement can propagate with a small overshoot. Billing/credit-exhaustion errors need balance/policy correction, not blind retry. [Spend limits](https://developers.openai.com/api/docs/guides/spend-limits).

## Attribution, unlimited mode and reports

- User conversation: actor and payer are the requesting user by default; all selection/planning/summary/ASR/classifier steps aggregate under its operation. Whether maintenance summaries remain user-funded is a policy decision, not an accidental call-site default.
- Admin campaign: actor is the initiating admin, beneficiary may be recipient, payer is the selected campaign/system account or admin according to reviewed policy. Rendering many recipients cannot quietly spend recipients' balances. Keep campaign attribution even when the admin is unlimited.
- Background/shared work: use an explicit system account and job key, never a fabricated user. Embedding/index ingestion, if added, belongs here unless an operator intentionally assigns a campaign.
- Local helper/cache hit: retain operational telemetry or a typed known-free accounting outcome when useful, with no phantom provider charge.

Unlimited bypasses only the personal finite-credit comparison. Always retain paid attempts, measured counters, cost estimates, provider charges and unknown holds. It does not bypass domain ACL, model entitlements, service rate limits, maximum output/media sizes, script CPU limits, per-operation maximum exposure or global emergency stop. Superadmin revocation removes the implicit unlimited status for future calls; it cannot undo past provider spend.

Proposed product contract: `/usage` and an owner-only typed `usage.own` read return current policy, settled amount, reserved amount, unknown amount/count, available credits when finite, period boundary and breakdown by operation. EN/RU display explicitly labels estimated versus provider-confirmed cost. Admin usage/report/policy actions require live superadmin or separately granted accounting capability, checked in discovery/help/bindings and on each call. Ordinary users must not see admin tool names. Do not let ownership parameters override authenticated principal.

Administrative reports aggregate by payer, operation, provider/model, period and campaign, with bounded complete pagination. Show reconciliation differences and unpriced/unknown work separately. Logs and metrics contain finite operation/status counts only; private ledger rows may contain authorized pseudonymous actor/request references but no prompts, profiles, transcripts, provider bodies or secrets. Keep provider invoice import privilege separate from routine self-usage queries. Price corrections create a new version or explicit adjustment; historical reports retain the rate used then.

## Migration and architecture ordering

1. **Contract and shadow accounting before enforcement:** retain the confirmed monetary API-balance unit and finalize allowance policy; define the priced call inventory and wire typed usage envelopes. Add additive credit tables and versioned price fixtures. Capture all actual provider calls, including ASR/API naming and failed-result usage. Old question quota continues as its existing safety limit during this explicitly temporary shadow stage. Unknown/uncaptured paths block a claim of complete accounting.
2. **Architecture B composition:** runtime constructs credits service and injects metered provider clients into the existing main application/API/broker boundaries. Complete one assistant scenario including selection, planning, summary and its report. Do not hide quota SQL inside Telegram transport or teach media decoder the application database. Keep this behavior change gated separately from unrelated structural moves.
3. **Architecture C agent host:** agent host owns logical attribution and loop identifiers; provider adapters own per-dispatch measurement; credits owns accounting decisions. Extend the same contract to knowledge retries, broadcasts and ASR. Remote adapters preserve trusted receipts; no double counting at proxy and actual provider. Prove full inventory before enabling global cost enforcement.
4. **Cutover:** add explicit migration version/time per account or deployment; new operations use credits policy, previously reserved legacy updates retain their chosen old/new policy. Do not reinterpret the same update under two budgets. Replace remaining-question UI and config only after the credits path covers every paid entry point. Unsupported old config must fail with a migration message rather than silently creating an allowance.
5. **Lifecycle/reconciliation:** align with architecture D for draining, unknown sent work, restart and settlement retries. Keep old count rows read-only for audit. They provide question counts only: no invented historical token usage, credits, monetary spend, backdated debit or reset refund. Architecture E removal of the importer must not remove runtime accounting or reconciliation.

Roll back enforcement by explicit policy mode while retaining accounting rows and known/unknown costs; never remove receipts or clear holds to obtain a green balance. Running an old binary that skips mandatory paid-call accounting is not a safe mixed-version rollout. Quiesce/drain dispatch and preserve migration epoch when changing owners.

## Independent acceptance contract

Code QA: verify every real provider send has an authorized reservation, exact price/conversion version and typed receipt; no float arithmetic, double reasoning/cache charge, token fabrication, cross-owner spending, broad unlimited bypass, network calls under ledger locks or raw-error leakage. Review dependency/SDK retry behavior and SQL fencing. Tests must use actual PostgreSQL for simultaneous last-balance reserves, duplicate/stale settlement, role revocation, period-boundary concurrency and crash/unknown-state transitions.

Functional QA: use a Telegram-like EN/RU stand and a fake paid provider with controlled usage and delayed/failing responses. Exercise manual and agent entry paths, multiple model turns, selection, classifier retry, summary, ASR, visual input and large broadcast naming. Verify finite exhaustion and truthful partial failure, unlimited user/superadmin spend reporting, ordinary-user hidden admin names, live grant/revoke, complete paged history, delayed usage, lost response, process restart, same-operation replay versus actual paid retry, price revision and provider conversion. Expected charges come from independently specified synthetic rate/usage fixtures, not production rates or implementation constants. No real billing required.

The stage is complete only when no paid entry point bypasses accounting, both QA gates pass, and the public policy decisions below are resolved. A dashboard alone or replacing the question counter alone is not completion.

## Remaining policy choices

1. Cutover handling for existing users and in-flight legacy reservations. The ordinary-user default is already selected: 1 API-balance credit per UTC month, no carryover, configurable.
2. Campaign/system funding and who may allocate it; whether shared/maintenance summaries debit users or system budget.
3. Unknown-usage hold review SLA, who can adjust it and what finite users see while unresolved.
4. Global operational exposure limits for unlimited accounts and whether any account-specific commercial discounts affect the canonical conversion.
