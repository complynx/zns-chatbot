# Functional QA scenario inventory and coverage pilot

## Global acceptance inventory

The global scope is broader than the nine-case Stage B seed. The table below is
a neutral requirement inventory, not a record of passed tests. Each row is a
family: the lead must split its named outcomes into separate cases and reconcile
them with the frozen scope before execution. Historical evidence reconciliation
and retention are tracked separately in [the evidence registry](qa-evidence-registry.md).
Do not give that historical registry or its reports to source-blind reviewers.

For **every UI outcome**, require EN/mouse, EN/emulated-touch, RU/mouse and
RU/emulated-touch, observed Telegram-like messages/buttons/edits and current
authoritative state. Physical touch remains separately unverified unless tested.
Language-independent invariants use an explicit independent/none cell; they do
not replace UI cells. For every mutation, distinguish exact retry/replay, restart
after completion, and interruption at the effect boundary; do not infer one from
another. Record owner, ordinary user, applicable event-specific role, unrelated
event role, global admin without the domain role, and revoked authority as
applicable. Mark inapplicable dimensions with a reason rather than omitting them.

Each case records its contract and exact candidate, fixture/actor/event identities,
input modality, correlated request/update/message/effect IDs, before/after state,
expected outcome, observed outcome, status, evidence and limitations. Old passes
remain attached to their old candidate. Failed, skipped, blocked, pending and
uncorrelated observations never become passes through catalog maintenance.

- `qa.orchestration.read-command-safety` (operator): use explicit read cmdlets or uniquely named helpers whose resolution is checked; aliases take precedence over functions. If immutable candidate bytes change during review, stop, preserve incident evidence, restore only manifest-matching authoritative copies and verify the complete manifest before resumption. Interrupted review is not acceptance.

## Run

From `platform`, using the installed Node runtime:

```powershell
node --test scripts/fqa/coverage.test.mjs
node scripts/fqa/coverage-cli.mjs --catalog scripts/fqa/scenarios.stage-b.json --results C:/qa/run/results.json --evidence-root C:/qa/run/evidence --candidate sha256:EXACT-FROZEN-MANIFEST
```

All four CLI arguments are required. The candidate is an exact opaque identity supplied independently by the caller (for example a frozen manifest digest). The validator compares it with report and cell identities; it does not recompute the candidate digest or inspect a running stand. Catalog/results must be explicit local regular JSON files; evidence lives under one explicit local directory. All three input paths reject network prefixes, Windows device names and alternate streams before filesystem access. Input ancestors cannot be symbolic links or junctions. Output is JSON on stdout. Exit 0 means the declared coverage is complete; exit 1 means incomplete coverage, invalid input or an I/O error. Nothing is written or fetched.

Storage prerequisite: the operator supplies paths on a trusted local filesystem. The CLI rejects explicit network path syntax; it does not establish the physical backing of a drive letter or mounted filesystem. Do not point it at mapped network drives or network-backed mounts. It starts no network client, but filesystem locality is an environment property, not a guarantee provided by path validation. This small QA utility is not a filesystem sandbox.

## Contract, version 1

Catalog: `{ "version": 1, "scenarios": [...] }`. Each scenario has a stable lowercase dotted/hyphenated `id`, nonempty `cells`, and nonempty unique `requiredEvidence` kind names. Every declared cell is required. Optional `resources` and `barriers` are unique string arrays, documenting fixture ownership and exclusive operations; they do not lock or schedule anything. Optional descriptive fields such as `expectation` and `source` are for reviewers.

A cell is `{ "locale": "en", "input": "mouse" }`. Locales are `en`, `ru`, or `independent`; input modes are `mouse`, `touch`, or `none`. Explicit cells avoid multiplying language-independent invariants. The main Stage B UI journey declares all EN/RU × mouse/touch cells. Touch evidence must state whether it is emulation or physical touch; the validator cannot establish that. An HTTP-only record does not establish a required Telegram-like rendered journey.

Results contain a matching candidate and an array of cell records:

```json
{
  "version": 1,
  "candidate": "sha256:EXACT-FROZEN-MANIFEST",
  "results": [
    {
      "id": "stage-b.orders.handoff",
      "locale": "en",
      "input": "mouse",
      "candidate": "sha256:EXACT-FROZEN-MANIFEST",
      "status": "pending",
      "errors": [],
      "evidence": [],
      "durationsMs": { "setup": 0, "run": 0, "evidence": 0, "cleanup": 0 }
    }
  ]
}
```

This example is deliberately incomplete. Status is `pending`, `passed`, `failed`, `blocked` or `skipped`; only `passed` can close a cell. Always include `errors`, with recorded harness/product errors as nonempty strings. A pass with any recorded error fails validation. Preserve failed attempts separately rather than hiding them with retries. Optional phase durations are finite nonnegative measured milliseconds; omit unmeasured phases. No speedup is inferred.

Evidence records use `{ "kind": "ui-journey", "path": "en/mouse/journey.json" }`. Each required kind needs at least one nonempty regular file. Multiple records per kind are allowed. Record candidate, fixture identities, correlated update/message/order IDs, steps, observations and limitations in those artifacts so the reviewer can evaluate attribution. A single file may legitimately support several kinds; the validator cannot judge whether it does. Empty, missing or unsafe files fail validation even in nonpassing records. Paths are portable relative names using `/`; traversal, absolute/network paths, Windows devices, alternate streams and symbolic links/junctions within the evidence tree are rejected. Keep the evidence directory immutable while validating; this is a read-only completeness check, not a security boundary against concurrent filesystem mutation.

Missing/duplicate/unknown scenarios or cells, mismatched candidates, malformed requirements, invalid timing/resource declarations, missing evidence kinds and incomplete statuses fail closed. The pure `validateCoverage` API accepts an externally supplied map of verified evidence file metadata; only the CLI gathers that metadata from the filesystem. Do not construct the metadata map from an untrusted report.

No runner, retries, stand controls, permission changes, scheduling or integration with existing gates is included. Adoption needs independent review and a lead-approved complete catalog. Existing evidence and active acceptance stands are untouched.
