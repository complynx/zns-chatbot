Оценки: production NO-GO. Codex: функциональная реализация 85–95%, архитектурная 75–85%, остаток 25–45 инженерных дней по 8 часов. Opus: общий охват 70–85%, остаток 43–89 дней, наиболее вероятно 55–70. Оценки используют разные знаменатели; их не усредняем. Это объём работы, не календарный срок. Сравнение, основания и неопределённость.

  • Доменные возможности: заказы, память/знания, история, профили/пассы, массаж, food, рассылки, browser authentication, модельные настройки и источники проходили профильные gates/QA в исторических составах. Границы, история.
  • Сохранение Go-кода: C7/D + intake и именованные дельты объединены в platform/, composed commit b99c4822ba9110dde5009e0aac738797cbb5ae66. Исходники отслеживаются Git; AUD-01 по сохранению выполнен. Provenance и assets.
  • CI и quality coverage: охват authored roots и tools/migrate внесён; syntax/ESLint/Prettier и Code QA №1 прошли. QA №1 — static only, без runtime acceptance.
  • Developer gates: compile платформы и импортера, pinned formatter и пять focused PG-сценариев прошли; это не полный gate и не Functional QA.
  • Отдельный importer: standalone PG-прогон прошёл за 49.845s, go vet — exit 0. Итоговая миграционная приёмка всего runtime отдельно.
  • Окружение: synthetic PostgreSQL healthy на локальном 55432; прежние стенды удалены, продуктовый Telegram-like FQA стенд ещё нужен.

  • Функции и полный паритет: закрыть инвентаризацию, manual → agent → manual, права, retries/restart, persistence, EN/RU и mouse/touch.
  • Финальный импорт и identity: полный повтор на итоговой схеме, reconciliation всех доменов, сохранность данных и удаление импортера.
  • Системная приёмка: Telegram-like UI, ограниченные DB-роли, failures/concurrency, актуальность карточек; затем разрешённые реальные модель/ASR и тестовый Telegram.
  • Выпуск: production configuration, observability, CPU/resource limits, runbook, backup/rollback и rehearsed cutover. Push, публикация и production deployment — только с финальным разрешением.
  • Переносимые доказательства: AUD-63; локальные qa.local деревья не публикуются целиком. После первого выпуска — отдельный UX-аудит, не условие первого релиза.

Вопросы для решения

Решения ниже пока не согласованы. Отсутствие ответа не означает одобрение. Ожидает только зависимый этап; независимая работа продолжается. Инженерные проверки и выбор реализации ведёт агент, отдельное разрешение на них не требуется.

  1. AUD-16 — оплаченная допуслуга при вытеснении. Какой результат нужен пользователю: сохранять оплаченную допуслугу либо снимать её с явной фиксацией обязательства возврата? Существующее поведение снимает её без такой записи; окончательный вариант зависит от подтверждения текущего сценария.
  2. AUD-24 — срок приглашения после очереди. От какой даты считать срок: первоначальной регистрации или фактического приглашения? Сейчас долго ожидавший пользователь может получить уже истёкшее приглашение.
  3. AUD-23 — временный сбой БД. При подтверждённом transient failure допустим перезапуск всего приложения, включая Mini App/API, или нужен режим восстановления без остановки остальных компонентов? Сначала агент проверяет фактическое поведение и последствия; retry-механизм выбирается в реализации.
  4. AUD-56 — роль Zitadel. Сохраняем обязательную доступность Zitadel для runtime или нужна возможность продолжать доверенные внутренние операции во время его сбоя? Границы прав сохраняются в обоих случаях; точный безопасный вариант требует инженерной проверки.
  5. AUD-67 — отдельные Python-изменения. Нужны ли ещё для текущего Python production ветки fix/massage-byn-prices и feature/orders-extras-deadline, или сохраняем их без отдельного выпуска? Изменения не удаляются и не публикуются без решения.
