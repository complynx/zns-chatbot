# Rules

- KISS. Type-safe. Preserve active behavior; partial port != parity.
- Go: pinned golangci-lint, Golden + Nebius linters, testify.
- JS: ESLint, Prettier, Playwright. Real PostgreSQL integration tests.
- QA owns slow/medium-long test classification and affected-domain mappings. Developers own runner mechanics. A classifier authors changes; separate fresh reviewers accept them. Preserve mandatory full/final gates and budgets. See docs/coordination-process.md.
- UI i18n: en + ru minimum. Catalog keys. Both locales in Functional QA.
- Free text/media: agent interprets intent. Pending form = hint, never trap next message.
- Update `management.local/PROGRESS.html` after stage gates, plan changes, blockers. Built != accepted.
- Keep management.local/PROGRESS.html plain semantic HTML without CSS or JavaScript. Use sections "Готово", "Сейчас", "Что ещё предстоит", "Вопросы для решения" with short task descriptions; distinguish historical scoped acceptance from current proof. Keep detailed evidence in reports/history. PROGRESS.md is a link only.
- Add unresolved choices that require Daniel to "Вопросы для решения" in management.local/PROGRESS.html, with known options and dependencies. Pending is not approved. Wait only on dependent work; continue independent work. Do not turn ordinary engineering decisions or unverified findings into approval requirements.
- Permission-wait correction (2026-10-05): defer approval-only checks and only their dependent execution/acceptance, never the whole development plan by default. Reassign waiting developers to independent approved source work, verified defects, remaining-requirement analysis or test preparation. Before declaring the whole goal blocked, inspect the unmet scope and prove no meaningful safe independent action remains; finished assignments alone are not that proof. Waiting is not active work. Deferred checks remain mandatory and unpassed; never bypass approval or QA gates. Reuse confirmed standing permissions within their scope instead of asking for each corrected source version.
- `noqa`, `nolint`, `eslint-disable`, `@ts-ignore`, exclusions: very rare. Fix code first. Exception: smallest scope, concrete reason, Code QA review. Never weaken gates for green results.

- Synthetic stand data and stands may be changed or deleted when this does not conflict with another test. Assign stand/data ownership before concurrent work; isolate conflicting scenarios. This supersedes the earlier no-deletion pause constraint for synthetic test resources. Production remains separately authorized.

- Synthetic QA directory policy (Daniel, 2026-10-07): do not require special directory ACLs or repeated permission for ordinary owned local preparation. Declare file/stand ownership; other agents must not modify those paths. Preserve immutable input hashes, read-only mounts, sole writers and no secret publication. Retire ACL-only admission gates in reviewed successors, not by editing frozen or running checks. Production access and independent Code/Functional acceptance remain unchanged.

- Working progress and Kanban live only in ignored `management.local/PROGRESS.html` and `management.local/KANBAN.html`. Never stage them or recreate tracked root copies. Keep operational metrics, assignment/review counters, worker acknowledgments and current estimates in management.local too; tracked documents may contain stable links. Keep stable contracts and final acceptance reports in Git.

# Two QA gates per stage

- Reviewer reuse override (Daniel, 2026-10-07): use a small persistent reviewer/developer pool with rotation across nodes and cross-review. Code reviewers may retain their own previous source-review context; a new agent/context is not required for each patch. Authors must never accept their own work. Review current diff, changed dependencies and affected producer/consumer interfaces; reuse exact unchanged-body coverage instead of rereading whole closures. Full stage/final requirements and separate implementation-blind Functional QA remain mandatory. This overrides fresh-agent/fork-none requirements below for Code QA, not independence from authors or original acceptance scope.

- Behavioral test policy (Daniel, 2026-10-07): tests must demonstrate functional capabilities, not freeze implementation structure. Remove assertions of incidental AST shape, internal call order, private method sets or exact implementation layout. Preserve observable results, authorization, transactions, persistence, failure handling, read-only effects and bounded completion. Original capability requirements and full/final acceptance remain; incidental structural test/assertion counts are not immutable gates. Deleted structural checks are not recorded as passed. QA classifies coverage; developers make scoped test edits, and cross-review checks that required behavior still has evidence.

- Risk-based scope (Daniel, 2026-10-07): required scenarios cover normal operation, app replacement/restart during message processing, retries and ordinary dependency failures. Keep basic atomicity, persistence, permissions and duplicate-money/effect protection. Targeted SIGKILL at a precise internal transaction step and combinatorial rare races are separate optional diagnostics unless a named business requirement or established high-impact risk requires them. Simplify the system rather than adding generic recovery machinery for those speculative cases. QA maps behavior coverage; optional/deleted cases are not PASS and do not block unrelated capabilities.

- Restart scope override (Daniel, 2026-10-07): normal acceptance restarts are always graceful with a shutdown window of at most 5 seconds. Prove in-flight message completion or safe redelivery without lost/duplicate effects after normal replacement. A forced kill or shutdown timeout is FAIL, not a passed graceful restart. Do not add mandatory SIGKILL matrices or arbitrary internal crash points; business interruption outcomes may use cancellation, dependency failures or persisted-state recovery. Preserve existing tighter limits and no simultaneous old/new writers.

- Shutdown latency target (Daniel, 2026-10-07): ordinary process shutdown should normally finish within 1 second; 5 seconds is a hard graceful ceiling, not a fixed wait. Cancel work promptly, retain replayable input/effects and return as soon as physical completion is observed. Measure actual latency; do not add artificial sleeps or a new timing framework. Expensive build/test/data operations are not ordinary shutdown latency.

- Short-operation latency target (Daniel, 2026-10-07): most ordinary short processes and local control operations should normally complete within 1 second. Finish on observed completion/readiness, not fixed sleeps. Use existing duration evidence to investigate materially slow operations; do not add a timing framework or apply this target to builds, imports or full test suites. This target does not replace the 5-second hard graceful-shutdown ceiling or authorize forced termination.

Follow the approved C–E then remaining-parity sequence; do not invent unrelated features. Declare disjoint file ownership, refill capability assignments as they finish, and keep independent review gates. Use separate Codex review runs if slots become limiting, or report the concrete sustained slot requirement to Daniel. All assignments remain Codex-only under the temporary override below.
